# Day 20 — Orchestration MCP: несколько серверов и длинный флоу

Задание: зарегистрировать несколько MCP-серверов, сделать так, чтобы агент сам выбирал нужный
инструмент, корректно маршрутизировал запросы и выполнял длинный флоу. Проверить сценарий, где
используются инструменты **с разных серверов**, и корректность выбора и порядка вызовов.

Взяли сценарий из своей же практики: **завести задачу в указанной очереди трекера по кадру Figma**.
Первый сервер даёт дизайн-данные (локальный Figma-мост), второй — операции трекера
(`sl-tracker-mcp` из дня 17). Агент идёт по цепочке из восьми вызовов, и порядок в ней критичен.

## 1. Что выяснилось на ресёрче

| Находка | Значение |
|---|---|
| `sl-figma-plugin` — **это MCP** | Плагин сам не MCP, но репозиторий содержит `mcp-server.js`: MCP-сервер **stdio, без npm-зависимостей**, 8 инструментов. Архитектура: `Claude Code ⇄ stdio MCP ⇄ mcp-server.js ⇄ HTTP localhost:3055 ⇄ ui.html ⇄ plugin.js ⇄ Figma API` |
| Инструменты моста | `get_document_info`, `get_selection`, `get_colors`, `get_typography`, `get_css`, `get_styles`, `export_image`, `dump_design` |
| Выделение, а не ссылка | `get_selection`/`get_colors`/`get_typography` читают **текущее выделение**; `node_id` принимают `get_css` и `export_image`; `dump_design` — файл целиком |
| Слепок на сервере | `/opt/sl-claude-box/workspace/figma`: файл VKR, 88 кадров, 6.3 МБ, страницы Prototype/Design/Style Guide; **PNG-рендеров нет**. Это продукт того же `dump_design` |
| Харнесс умеет stdio | В `@deepseek-ai/dsh-mcp-client` два транспорта: `streamable-http` и `stdio` (`command`, `args`, `env`, `cwd`), а `env` мержится с окружением родителя (`buildChildEnv`) |
| dsh-term умел только HTTP | Оверлей генерировался жёстко с `transport: streamable-http`; флаг `--mcp` при этом **повторяемый** (`opts.mcp = [...(opts.mcp ?? []), next()]`) |
| `nexus-digest` запущен | Их сервис дайджеста живёт 24/7, но порт наружу не публикуется — как третий сервер он потребует Caddy-маршрут |

## 2. Что сделано

### 2.1. stdio-пресеты в dsh-term

Добавлен пресет `figma`: `transport: stdio`, `command: node`, путь к `mcp-server.js` с
переопределением через `SL_FIGMA_MCP_SCRIPT` (раскладка у каждого своя). Оверлей теперь собирает
оба транспорта, `--mcp-check` принимает список (`figma,sltracker`) или `all`, а справка и README
перечисляют доступные пресеты.

```powershell
dsh-term --mcp figma --mcp sltracker
```

```
mcp: включён figma, sltracker · stdio · локальный | read-write, toolsets=all
  mcp: figma · 8 tools · сырые схемы ≈ 923 → в промпте ≈ 425 tokens · figma-bridge · 827 мс
  mcp: sltracker · 8 tools · сырые схемы ≈ 1.4k → в промпте ≈ 656 tokens · sl-tracker-mcp
```

Два сервера — ≈1.1k токенов в каждом запросе: включаются на время работы, а не по умолчанию.

### 2.2. Скилл с закреплённым порядком вызовов

`.dsh/SKILLS/task-from-figma.md` + команда `/task-from-figma <ОЧЕРЕДЬ> <ссылка|текст>`.
Вид скилла — **роль**: команда делает детерминированную часть, вызовы делает агент.

| # | Инструмент | Сервер |
|---|---|---|
| 1 | `get_document_info` — мост жив? | figma |
| 2 | `get_selection` — дерево кадра (размеры, auto-layout, стили) | figma |
| 3 | `get_colors` — цвета с именами стилей и переменных | figma |
| 4 | `get_typography` — шрифты, кегли, line-height | figma |
| 5 | `list_queues` — очередь существует? взять имена статусов | sltracker |
| 6 | `create_task(queue=<из команды>, description=факты числами)` | sltracker |
| 7 | `add_comment(key` **из ответа шага 6**`, ссылка на кадр)` | sltracker |
| 8 | `get_task(key` из шага 6`) — проверка результата | sltracker |

Почему порядок именно такой и почему он в скилле, а не «на усмотрение модели»:

- **1–4 до записи**: задача без фактов дизайна бесполезна; чтение идёт от дешёвого к подробному;
- **5 до 6**: ключ очереди проверяется по справочнику, а не угадывается;
- **6 до 7 и 8**: ключ задачи появляется только в ответе `create_task` — это и есть данные,
  которые передаются из шага в шаг (то, что задание называет «корректностью передачи данных»);
- **8 последним**: без перечитывания нельзя утверждать, что записалось нужное.

Детерминированная часть команды: разбор очереди из аргумента, извлечение `node-id` из ссылки
(`1:23` / `1-23` / `%3A` → `1-23`, как в боте SLNexus), проверка, что подключены **оба** сервера,
чтение спецификации и сборка промпта с порядком. Дальше — работа агента.

### 2.3. Флаг `--figma-node`

Разбор ссылки без сессии и без модели — чтобы проверять и отлаживать скилл, не тратя токены:

```
$ node dsh-term/dsh-term.mjs --figma-node "https://www.figma.com/design/AbC/VKR?node-id=1143%3A5786"
node-id: 1143-5786
```

## 3. Дефект, который нашёлся только на живой сессии

Первый прогон дал:

```
mcp: figma: соединение не удалось — процесс завершился с кодом 1:
  [figma-bridge] HTTP error: listen EADDRINUSE: address already in use 127.0.0.1:3055
```

При этом порт был свободен и до, и после прогона — то есть объяснение «кто-то держит порт»
не подходило. Инструментированный враппер вокруг `mcp-server.js` показал правду:

```
11:57:54.839 spawn pid=34068 ppid=19228  ← РОДИТЕЛЬ: dsh ... --patch dsh-term-mcp.patch.yml
11:57:56.210 spawn pid=7296  ppid=43472  ← РОДИТЕЛЬ: dsh-term\dsh-term.mjs -p ... --mcp figma
11:57:56.301 exit  pid=7296  code=1      ← второй упал на занятом порту
11:57:56.825 exit  pid=34068 code=0
```

Сервер спавнили **двое**: сам харнесс (он и владеет портом) и **зонд dsh-term**, который для
замера цены инструментов запускает процесс. Для HTTP-сервера это безвредно, для stdio с
фиксированным портом — нет, причём пользователь видел ошибку *зонда*, а не реальную проблему.

Исправлено: зонд stdio-серверов выполняется **до** спавна рантайма (занимает порт на доли секунды
и отпускает его до старта харнесса), фоновая проверка такие серверы уже не перезапускает,
`/mcp refresh` локальный сервер не трогает. После правки:

```
mcp: figma · 8 tools · ≈ 425 tokens · stdio · локальный · figma-bridge · 827 мс · mcp__figma__*
```

**Побочный вывод для эксплуатации:** порт у моста фиксированный (`127.0.0.1:3055`), сервер
одноэкземплярный — dsh-term и Claude Code одновременно мост не удержат. Записано в README.

## 4. Проверки

| Что | Чем проверено | Результат |
|---|---|---|
| Харнесс принимает stdio-оверлей | живая сессия `--mcp figma --mcp sltracker` | оба сервера подключены, ошибок нет |
| Локальный мост отвечает | `--mcp-check figma` | `figma-bridge · protocol OK`, 8 инструментов, ≈425 токенов |
| Оба сервера в одном оверлее | `--mcp-check figma,sltracker --offline` | `id: mcp-figma` (stdio) + `id: mcp-sltracker` (http) |
| Путь переопределяется | `SL_FIGMA_MCP_SCRIPT=…` в тесте | в `args` уходит новый путь |
| Нет скрипта — внятная ошибка | `--mcp-check figma` с несуществующим путём | код 1, «не найден … укажи путь» |
| Разбор ссылки Figma | `--figma-node` на трёх формах | `1:23`, `1%3A23`, `1-23` → `1-23` |
| Двойной спавн устранён | враппер считал запуски; после правки | первый — зонд до рантайма, второй — харнесс, конфликта нет |
| Регресс | все тесты dsh-term | 5 файлов зелёные, `mcp.test.mjs` — **34 проверки** (было 18) |

## 5. Честный статус

- **Проверено**: регистрация двух серверов в одной сессии, оба транспорта, порядок спавна,
  разбор ссылки, 34 теста, документация.
- **Не продемонстрировано**: сам длинный флоу целиком. Он требует **открытой Figma Desktop
  с панелью плагина** (мост читает текущее выделение или файл, в котором открыт кадр) и хода
  модели. Прогон `/task-from-figma MOBILE <ссылка>` — следующий шаг, и его результат (задача
  в очереди MOBILE с описанием из спеки) нужно добавить в этот отчёт.
- Ограничение, которое стоит держать в голове: пока Figma открыта только у пользователя, «мост»
  живёт на его машине — это не 24/7. Для серверного варианта нужен MCP-сервер над оффлайн-слепком
  (`sl-figma-mcp`), но это отдельная работа, а не день 20.

## Файлы

- `dsh-term/dsh-term.mjs` — stdio-пресеты (`transport`, `command`, `args`, `env`), пресет `figma`,
  зонд stdio до спавна рантайма, `--mcp-check` списком и `all`, `--figma-node`, команда
  `/task-from-figma`, скилл-роль `taskFromFigma`.
- `dsh-term/tests/mcp.test.mjs` — 34 проверки: оба транспорта в одном оверлее, переопределение пути,
  ошибка при отсутствии скрипта, три формы `node-id`.
- `.dsh/SKILLS/task-from-figma.md` — спецификация скилла: порядок вызовов, правила, приёмка.
- `.dsh/SKILLS/README.md` — реестр скиллов и описание роли.
- `dsh-term/README.md` — раздел «Несколько серверов и локальный stdio», ограничение одноэкземплярности.
