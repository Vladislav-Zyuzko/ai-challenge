# Управление контекстом: компрессия истории

## Что сделано

Агент (`dsh-term`) умеет работать со сжатием истории: последние N токенов диалога
передаются «как есть», остальное заменяется summary, который хранится отдельно и
подставляется в запрос вместо полной истории.

Управление и наблюдаемость добавлены в CLI:

| Что | Как |
|---|---|
| Режим компрессии | `--compress on` (по умолчанию) · `off` · `<ratio 0..1>` |
| Размер «хвоста как есть» | `--compress-keep <токены>` (по умолчанию 50000 — примерно половина порога и ≈5% окна 1M) |
| Настройки харнессу | генерируемый на лету патч-оверлей `dsh --patch` (Program Files не правится) |
| Что видно в выводе | `· context compacted: shadowed 4.2k → summary 843 (net ≈ −3.4k, call 14.4k)` — `net` = снято с окна, `call` = стоимость вызова суммаризатора; `· tool output pruned: …`; ошибки компакции |
| Метрики хода | `tokens: in (cache …) / out`, `requests`, `compression: N summarize calls[, K failed], X tokens` (это ЦЕНА компакций, не вычитание из окна), `context: N / 1M (P%)` |
| Команда `/context` | режим и пороги, заполнение окна, расход, последний summary |

Компрессию выполняет плагин рантайма `compaction-basic` (порог `thresholdRatio × contextWindow`,
хвост `retainTokens`, summary отдельным событием `compaction/summary`); dsh-term задаёт политику
и показывает результат.

## Как проверялось

Один и тот же сценарий (`turns.txt`, 8 ходов) прогонялся трижды в чистых home:
«иголка» `KX-42` в начале, 5 описаний по 300 слов, затем два контрольных вопроса
(код проекта; сколько тем и что было пятым). Метрики берутся из вывода dsh-term и из
логов сессий, качество — из ответов на контрольные вопросы (вопрос → ответ по логу).

| Метрика | без сжатия | со сжатием (агрессивно) | со сжатием (умеренно) |
|---|---|---|---|
| Суммарный вход агента | 1.37M | 494.9k | 965.8k |
| Суммарный выход | 27.0k | 21.9k | 26.9k |
| Финальный контекст | 46.3k | 10.1k | 15.1k |
| Компакций / отказов | 0 / 0 | 61 / 25 | 4 / 0 |
| Стоимость суммаризации | — | 689.2k | 68.2k |
| **Итого (агент + суммаризация)** | **1.40M** | **1.21M (−13.7%)** | **1.06M (−24.1%)** |
| Контрольные вопросы | 3/3 | 3/3 | — |

Режимы: агрессивный — `--compress 0.009 --compress-keep 300`; умеренный — `--compress 0.02 --compress-keep 3000`.

## Выводы

1. **Компрессия сохраняет смысл диалога**: «иголка» из первого хода (`KX-42`) и структура
   диалога (число тем, пятая тема) восстановлены в обоих режимах — 3/3 против 3/3.
2. **Контекст и расход падают, но не бесплатно**: агрессивный режим сокращает контекст на
   78% и вход агента на 64%, однако вызовы суммаризатора съедают 689k токенов, поэтому
   чистая экономия — 13.7%.
3. **Политика важнее «силы» сжатия**: умеренные настройки дали лучший чистый результат
   (24.1%) при 4 компакциях и без отказов. Агрессивные почти на каждом ходу сжимали
   крошечные участки, 25 попыток были отклонены (summary больше сжимаемого фрагмента),
   а потраченные на попытку токены не возвращаются.
4. **Практическое правило**: порог должен быть заметно выше системного промпта (~8k токенов),
   а `retainTokens` — заметно меньше типичного объёма истории; иначе сжимать нечего.
5. Компрессия «спит», пока контекст ниже порога: при окне 1M и дефолтном `thresholdRatio 0.1`
   это ~100k токенов, поэтому в коротких сессиях выигрыша нет вовсе.

## Воспроизведение

```powershell
# оба режима одним скриптом (пишет runs/*.txt)
Invoke-Expression (Get-Content .\run_ab.ps1 -Raw)
# умеренная политика
dsh-term --compress 0.02 --compress-keep 3000   # сценарий из turns.txt
# разбор и отчёт
node .\analyze.mjs      # → result.md
```

Файлы: `input.md` (задание и методика), `turns.txt` (сценарий), `run_ab.ps1` (прогон A/B),
`analyze.mjs` (разбор метрик и качества), `runs/*.txt` (сырые выводы), `result.md` (подробное сравнение).
