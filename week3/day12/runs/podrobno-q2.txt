# Стоит ли отдельная ветка под правку в одну строку

Короткий ответ: размер диффа — плохой критерий. Решает не «одна строка или сто», а то, защищена ли основная ветка, есть ли CI и ревью, и не сломает ли ваша правка работу коллегам. Одна строка может быть опечаткой в комментарии, а может быть сменой условия `>` на `>=` в расчёте платежа — цена ошибки различается на порядки, а дифф одинаковый.

## Разбор по пунктам

**1. Защищённая ветка и обязательное ревью — ветка обязательна.** Если в настройках репозитория на `main` включены branch protection rules и required status checks, прямой push просто не пройдёт, а если у вас есть право обхода — обходить его ради одной строки почти всегда плохая идея. Проверить можно командой `gh api repos/{owner}/{repo}/branches/main/protection` (нужны права администратора) или глазами в Settings → Branches.

**2. Есть CI, который запускается на pull request — ветка окупается.** Тогда ветка даёт вам бесплатную проверку: линтер, тесты, сборка прогоняются до попадания в `main`. Если же CI настроен только на push в `main` (типично для мелких проектов), ветка не добавляет проверок, а только откладывает момент, когда вы узнаете о поломке.

**3. Trunk-based development меняет ответ на противоположный.** Исследования DORA и практика trunk-based разработки прямо рекомендуют короткоживущие ветки (меньше суток) или прямые коммиты в trunk с парным ревью. В такой модели однострочная правка — идеальный кандидат на прямой коммит, потому что ветка живёт час, а накладные расходы на PR и merge создаёт всё равно.

**4. Хотфикс в продакшене — ветка обязательна независимо от размера.** Если `main` уже уехал вперёд с незарелиженными изменениями, а чинить надо версию в проде, вы ветвитесь от тега и потом переносите правку в `main` через `cherry-pick`. Прямой коммит в `main` здесь просто не решает задачу: исправление уедет в следующий релиз, а не в текущий.

**5. Одиночный проект без CI — ветка чаще всего лишний ритуал.** Если вы единственный автор, `main` не защищён, тестов нет, а развернуться можно откатом — ветка добавит два действия и ничего не даст. Но оговорка: «нет тестов» и «нет ревью» означает, что единственная страховка — это возможность быстро откатить, поэтому хотя бы убедитесь, что `git revert` действительно решает проблему.

**6. Размер диффа на Windows может оказаться ложным.** Правка одной строки иногда превращается в дифф на весь файл из-за смены окончаний строк CRLF↔LF. Перед коммитом смотрите `git diff --stat`: если изменилась тысяча строк вместо одной, дело в переводах строк, а не в вашей правке (`git config core.autocrlf`, файл `.gitattributes`).

**7. Отдельный вопрос — куда именно класть правку.** Если изменение логически относится к последнему коммиту, который ещё никому не отправлен, чище не создавать новый коммит, а использовать `git commit --fixup <sha>` с последующим `git rebase -i --autosquash`. Это применимо только к неопубликованным коммитам: переписывание уже отправленной истории ломает коллегам `pull`.

## Пример: три сценария в командах

Вариант А — прямой коммит в `main` (личный или небольшой проект без защиты):

```powershell
git switch main
git pull --ff-only
# правите одну строку в src/config.js
git add src/config.js
git commit -m "fix(config): таймаут ретрая 30ms -> 300ms, ретраи не успевали"
git push
```

Вариант Б — ветка и PR (командный репозиторий, `main` защищён):

```powershell
git switch -c fix/retry-timeout main
# правите одну строку
git add -p                      # -p даёт просмотреть дифф по кускам, полезно при CRLF-сюрпризах
git commit -m "fix(config): таймаут ретрая 30ms -> 300ms"
git push -u origin fix/retry-timeout
gh pr create --fill --base main
```

Вариант В — хотфикс от релизного тега с переносом в `main`:

```powershell
git fetch --tags
git switch -c hotfix/1.4.2 v1.4.2
# правите одну строку
git commit -am "fix: таймаут ретрая 30ms -> 300ms"
git push -u origin hotfix/1.4.2
# после мержа и тега 1.4.3 переносите то же в main:
git switch main; git pull --ff-only
git cherry-pick <short-sha-из-хотфикса>
```

Если вы уже посреди другой работы и не хотите её трогать, удобен `git worktree add ..\hotfix-142 -b hotfix/1.4.2 v1.4.2`: отдельная рабочая копия рядом, текущие незакоммиченные изменения остаются на месте.

## Что учесть

- **Не путайте гранулярность коммита и ветку.** Одна строка — образцово атомарный коммит; вопрос ветки про то, как изменение попадает в общую ветку и кто его видит до слияния.
- **Осторожно с `git push --force` в `main`.** Если вы переписываете опубликованный коммит ради «одной строки», у всех, кто уже сделал `pull`, история разойдётся; им придётся разбираться с расхождением вручную.
- **Асимметрия издержек реальна, но не бесконечна.** Ветка стоит секунды вашего времени, но ещё и минуты CI и внимание ревьюера — при потоке однострочных правок это заметно.
- **Опасность обратного уклона.** «Это же одна строка» — типичная причина правок в `main` в пятницу вечером; полезно завести правило: любой коммит в защищённую ветку идёт через PR, независимо от объёма.
- **Что можно проверить самому:** `git log --first-parent --oneline -10` — наличие merge-коммитов подскажет, используется ли PR-процесс; наличие `.github/workflows/*.yml` с триггером `pull_request` — работает ли CI на ветках; `git diff --stat` — не распух ли дифф из-за переводов строк; `git config core.autocrlf` и `.gitattributes` — как репозиторий обходится с CRLF в вашем Windows.

## Итого

1. В командном репозитории с защищённым `main` и CI на pull request заводите ветку всегда, даже под одну строку: цена — секунды, выигрыш — проверка и след в истории.
2. В личном проекте без защиты и CI одна строка спокойно идёт прямо в `main`, а если правка относится к неотправленному последнему коммиту — используйте `--fixup` и `rebase --autosquash` вместо нового коммита.
3. Хотфикс в проде — отдельная ветка от тега с `cherry-pick` в `main`; это единственный случай, где размер диффа вообще не влияет на решение.
