# Проект: как харнесс строит продукт

Верхнеуровневое описание работы харнесса. Отвечает на вопрос «как вообще из запроса
пользователя получается инструмент»; детали узла — в `node.md`, этапы и переходы —
в `state-machine.md`, термины — в `glossary.md`.

## Зачем это нужно

Две проблемы, которые решает рекурсивный харнесс:

1. **Контекст.** Большая задача не помещается в один контекст и не может быть
   спланирована целиком «в голове». Рекурсия делит её так, чтобы каждый агент видел
   только свой срез: правила своего продукта, свои инструменты, свой план.
2. **Сборка.** Работа, разбитая на части, легко превращается в набор несогласованных
   кусков. Поэтому каждый узел обязан иметь контракт, а каждый внутренний узел обязан
   собрать своих детей и проверить стыки до сдачи родителю.

Замыкание модели: **продукт подзадачи становится инструментом для родителя**.
Проект считается выполненным, когда он сам прошёл приёмку и стал инструментом.

## Две части и их взаимодействие

| Часть | Где живёт | Отвечает за | Зависит от продукта? |
|---|---|---|---|
| Процедурный харнесс | `.dsh/.harness/` | роли, этапы, критерии, правила использования инструментов | нет — переносится между проектами |
| Харнесс продукта | `.project-harness/` | product-rules, tools-rules, make-rules, вложенные узлы, отчёты | да — это сам продукт |

Процедурный харнесс **не знает** о конкретном продукте; харнесс продукта **не содержит**
правил процесса — он ссылается на них. Поэтому:

- `.harness/` можно версионировать и переносить как отдельный инструмент;
- в узле фиксируется `harness_version`, по которой он строился (см. `node.md`).

## Три вопроса

Перед любой работой — и на корне, и в каждом узле — отвечаем на три вопроса:

1. **Что нужно сделать?** → `product-rules.md`: правила поведения продукта, контракт,
   инварианты (`I1`, `I2`, …).
2. **Чем это делать?** → `tools-rules.md`: какие внешние инструменты нужны, со ссылками
   на `.harness/tools-bank/<tool>-rules.md` и заметками, актуальными для узла.
3. **Как из инструментов сделать продукт?** → `make-rules.md`: план — задачи,
   зависимости, атомарность, бюджет.

Пока на все три вопроса нет ответа в письменном виде, реализация не начинается.

## Рекурсия и атомарность

Каждая задача плана проверяется вопросом: **достаточно ли product-rules инструментов,
чтобы выполнить её без собственного плана?**

- **Достаточно** → задача атомарна, исполняется исполнителем (агентом нужного инструмента).
- **Недостаточно** → из задачи создаётся дочерний узел: родитель пишет для него срез
  product-rules и срез tools-rules, и запускается архитектор узла с чистым контекстом.

Пример: «реализовать авторизацию» → не атомарно (правила Flutter не объясняют, как
сделать авторизацию) → узел «авторизация» → в его плане «профиль пользователя» → тоже
не атомарно → узел «профиль» → в его плане «модель `ProfileUser`» → **атомарно**: язык
и его правила описывают, как объявить класс с известными полями, и проверка очевидна
(компиляция + тест).

Атомарность определяется не «размером», а четырьмя условиями (подробно — `node.md`):

1. нет неизвестных — рецепт известен целиком;
2. предусловия выполнимы сейчас (доступны инструменты, данные, права);
3. есть дешёвая проверка результата;
4. провал локален — не рушит план.

Плюс экономический порог: дробить стоит, только если ожидаемая стоимость ошибки при
«сделать сразу» выше стоимости планирования, контрактов, проверки и накладных расходов
на контекст. Иначе дробится ерунда.

## Полный цикл проекта

Полная последовательность этапов и переходов — в `state-machine.md`. Кратко:

1. **Спецификация (корень).** Архитектор проекта вместе с пользователем формирует
   первородные `product-rules.md` и `tools-rules.md` корневого узла. Результат —
   `specification-report.md`.
2. **Планирование.** Архитектор узла пишет `make-rules.md`; критик проверяет план
   отдельной сессией; возражения закрываются письменно. Результат — `planning-report.md`.
3. **Реализация.** Для каждой задачи: атомарная → исполнителю; неатомарная → дочерний
   узел, который проходит те же этапы. Архитектор узла оркестрирует и проверяет
   слаженность продукта. Результат — `realization-report.md`.
4. **Верификация.** Тестировщик пишет проверки от спеки и инвариантов, запускает,
   собирает доказательства. Результат — `verification-report.md`.
5. **Приёмка.** Родитель проверяет продукт против контракта. Принято → архитектор узла
   публикует инструкцию по использованию, продукт становится инструментом. Результат —
   `acceptance-report.md`.

Корневой узел отличается только тем, что его «родитель» — пользователь.

## Роли

| Роль | Файл | Кратко |
|---|---|---|
| Архитектор проекта | `agents/project-architect.md` | корневой узел, связь с пользователем, приёмка верхнего уровня |
| Архитектор узла | `agents/node-architect.md` | владелец узла: спека-срез, план, оркестрация, сдача |
| Критик | `agents/critic.md` | проверка плана: полнота, исполнимость, риски |
| Тестировщик | `agents/tester.md` | проверки от спеки, доказательства, право забраковать спеку |
| Исполнитель | `tools-bank/<tool>-rules.md` (позже) | агент одного инструмента, исполняет атомарные задачи |

## Инварианты харнесса

Харнесс подчиняется своим же правилам, поэтому его инварианты — проверяемые утверждения:

- **H1.** Ни один продукт не принимается без контракта, зафиксированного родителем.
- **H2.** Каждый этап заканчивается репортом до начала следующего этапа.
- **H3.** Исполнителю передаётся одна задача и срез правил, а не история узла.
- **H4.** Сумма бюджетов дочерних узлов не превышает бюджет родителя минус резерв.
- **H5.** Продукт становится инструментом только после приёмки и публикации `usage.md`.
- **H6.** У каждого артефакта ровно один писатель; история отчётов не перезаписывается.
- **H7.** В отчётах каждое утверждение о проверке имеет воспроизводимое доказательство
  (команда, артефакт, ссылка на инвариант).

## Границы (чего харнесс не делает)

- не заменяет систему контроля версий и CI — он лишь требует доказательств;
- не ведёт документацию продукта для людей (это продуктовая задача, а не процесс);
- не хранит знания о конкретном проекте в `.harness/` — только в узлах продукта;
- не гарантирует правильность product-rules: за продуктовую ценность отвечает
  архитектор проекта вместе с пользователем.

## Состояние реализации

- ✅ процедурный харнесс: роли, этапы, критерии (этот каталог);
- ⏳ `tools-bank/` — правила использования внешних инструментов и исполнители;
- ⏳ `.project-harness/` — пример корневого узла продукта;
- ⏳ раннер — чтение состояния узла по отчётам, распределение бюджета, эскалации.
