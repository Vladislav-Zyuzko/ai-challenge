# local-ai-service — локальная LLM как приватный сервис (день 30)

Локальная модель, вынесенная за сервисный слой: с ключом, лимитами, логами и веб-чатом,
но без VPS и без выхода модели в сеть напрямую.

```
клиенты                        сервисный слой                        модель
────────                       ──────────────                        ──────
dsh-term   (CLI)  ─┐
doc-index  (RAG)  ─┼─ HTTP ──▶ LiteLLM :4000 ──── HTTP ────▶ Ollama :11434
Open WebUI (чат)  ─┤           ключ, rpm,                   (только 127.0.0.1)
curl / скрипты    ─┘           лимит параллелизма,
                               лимит контекста, логи
```

Главное архитектурное решение: **наружу смотрит сервис, а не модель**. Ollama слушает
`127.0.0.1:11434` и снаружи недоступен — это проверяется скриптом, а не подразумевается.
Если бы порт модели был открыт, ключи и лимиты обходились бы одним curl-ом.

## Запуск

```powershell
python -m venv .venv
.\.venv\Scripts\pip install "litellm[proxy]"
Copy-Item .env.example .env          # и поменять LITELLM_MASTER_KEY

.\scripts\service.ps1 start          # сам сервис
docker compose up -d                 # веб-чат на http://127.0.0.1:3000
```

Проверки (каждая пишет JSON в `out/`):

```powershell
node scripts/check-network.mjs       # доступ по сети, ключ, приватность порта модели
node scripts/load-test.mjs --url=http://127.0.0.1:11434 --model=qwen3:8b   # очередь модели
node scripts/load-test.mjs           # поведение сервиса под нагрузкой (429)
node scripts/check-limits.mjs        # ключ, rate limit, длина ответа
node scripts/check-context.mjs       # что реально происходит с длинным контекстом
node scripts/check-chat.mjs          # сквозной путь чат → сервис → модель
```

Клиенты из этого же репозитория:

```powershell
# RAG-клиент через сервис (ключ берётся из DSH_AI_SERVICE_KEY)
$env:DSH_TERM_OLLAMA = 'http://127.0.0.1:4000'
$env:DSH_AI_SERVICE_KEY = '<LITELLM_MASTER_KEY>'
python -m doc_index brief "что такое MCP?" --backend local --llm-model rag-brief

# CLI-клиент: /model и --llm-check видят модели сервиса
node dsh-term/dsh-term.mjs --ollama-url http://127.0.0.1:4000 --llm-check
```

## Что настроено в `litellm/config.yaml`

| Ограничение | Значение | Что делает |
|---|---|---|
| `rpm` | 6 на модель | шесть запросов в минуту: на CPU это защита, а не жадность |
| `max_parallel_requests` | 1 | один запрос в работе; остальные получают мгновенный 429 вместо тихой очереди |
| `max_input_tokens` | 8192 | **только объявлено**: см. «Что не работает» ниже |
| `max_tokens` | 700 | значение по умолчанию; клиент может попросить больше |
| `reasoning_effort` | `none` | без этого весь ответ уходит в скрытые рассуждения, а чат показывает пустоту |
| `drop_params` | `true` | лишние поля клиента не роняют запрос |

## Что проверено и что из этого следует

- **Доступ по сети.** Запрос из другого сетевого стека (контейнер через
  `host.docker.internal`) получает 200; порт модели снаружи недоступен.
- **Стабильность.** Напрямую в Ollama задержка растёт **линейно** с числом параллельных
  запросов (p50 1.0 → 2.1 → 4.1 с при 1/2/4/8), а суммарная пропускная способность стоит
  на месте — около **1 ответа в секунду**. Это очередь, а не параллелизм: ошибок нет,
  но и ускорения нет. Поэтому на сервисе стоит лимит параллелизма: лучше быстрый отказ,
  чем молчаливое ожидание.
- **Rate limit** действительно отдаёт 429 (всплеск из девяти запросов → один 200 и восемь
  429), но **без заголовка `Retry-After`**: клиент не знает, когда повторять. Это
  единственная проверка, которая не проходит.
- **Ключ.** Запрос без ключа и с неверным ключом до модели не доходит. Коды ответа при
  этом некрасивые (500 и 400 «No connected db»), потому что без базы LiteLLM не умеет
  проверять виртуальные ключи и не отвечает 401. Лечится подключением Postgres — в этот
  раз сознательно не подключал.
- **Контекст.** Объявленный лимит 8192 сервис **не применяет**: запрос на ~10 тысяч токенов
  был принят и обработан. Настоящий предел задаёт окно модели, и превышение выглядит как
  **молчаливая обрезка**: `qwen3:8b` (окно 4096) срезал промпт из 5266 токенов до 2050,
  а `rag-brief:8b` (окно 8192) принял все 5266. Ошибки не будет — ответ просто станет хуже.
- **Чат.** Open WebUI собран в контейнере и ходит в сервис как обычный OpenAI-клиент с
  ключом. Первый пользователь становится администратором; учётка создаётся `check-chat.mjs`
  и лежит в `.env` (в репозиторий не попадает).

## Что не работает (и почему это записано, а не спрятано)

1. **Нет `Retry-After`** в 429 — клиентам приходится угадывать паузу.
2. **`max_input_tokens` и `max_tokens` из конфига — не запрет, а значение по умолчанию.**
   Реальный предел контекста — окно модели, реальный предел ответа — то, что попросил клиент.
3. **Коды отказа без базы** не 401, а 400/500.
4. **Публичного адреса нет** — это осознанно: сервис рассчитан на локальную сеть или
   приватную сеть (Tailscale/WireGuard). Для доступа с других устройств нужен либо
   адрес в локальной сети, либо оверлейная сеть.
5. **LAN-адрес этой машины недоступен даже ей самой**: активный VPN (`AmneziaVPN`) держит
   маршрут к `10.0.1.0/24`, поэтому проверка «по сетевому адресу» честно показывает
   «не отвечает». Порт при этом открыт в файрволе:
   `New-NetFirewallRule -DisplayName 'local-ai-service (LiteLLM 4000)' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 4000 -Profile Any -RemoteAddress LocalSubnet`.

## Найденные по дороге дефекты

- **PowerShell-скрипт с кириллицей без BOM не разбирается**: длинное тире `—` в UTF-8 даёт
  байт `0x94`, который в cp1251 — «умная» кавычка `”`, а PowerShell считает её концом строки.
  Лечится BOM (так записаны остальные боевые `.ps1` в репозитории).
- **LiteLLM не стартует на русской Windows**: его баннер содержит псевдографику, консоль
  cp1251 её не кодирует, и старт падает с `UnicodeEncodeError`. Нужны `PYTHONIOENCODING=utf-8`
  и `PYTHONUTF8=1`.
- **`python -m litellm` не существует** (у пакета нет `__main__`) — запускать надо `litellm.exe`.
- **`reasoning_effort: none` обязателен на стороне сервиса**: иначе клиент получает пустой
  `content` и весь ответ в скрытом `reasoning_content`.
- **`Get-Content`/`Set-Content` в PowerShell 5.1 портит UTF-8** при чтении-записи файла:
  кириллица превращается в мусор. Правки текста делать инструментами с явным UTF-8.
