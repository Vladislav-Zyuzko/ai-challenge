# Банк инструментов (заготовка)

Здесь живут правила использования **внешних инструментов** и описания исполнителей —
агентов, которые владеют одним инструментом. Раздел намеренно пуст: сначала правила
процесса, инструменты — следующим шагом.

## Что появится

```
tools-bank/
  tools-index.md          # карта: название инструмента → краткое описание → ссылка на правила
  <tool>-rules.md         # правила работы с инструментом (flutter, react, js, …)
  <tool>-executor.md      # роль исполнителя: как ставится задача, что он возвращает
```

## Требования к `<tool>-rules.md`

Файл — это **инструкция по использованию**, а не обзор технологии. Минимум:

1. **Назначение** — для каких задач инструмент уместен, для каких нет.
2. **Предусловия среды** — что должно быть установлено и настроено; как проверить
   (health-check командой).
3. **Как ставить задачу** — что нужно сообщить исполнителю, чтобы он сделал работу
   (вход, ожидаемый результат, границы).
4. **Как проверять результат** — дешёвые проверки: сборка, тесты, линтер, запуск.
5. **Лучшие практики и грабли** — короткие, конкретные, проверенные на практике.
6. **Ограничения** — чего инструмент не умеет, где ломается, что требует ручных шагов.
7. **Версия и статус** — `active` / `deprecated`, с какой версии актуально.

Инструмент без предусловий и проверки считается недоступным: предусловия входят в
контракт узла со средой (`tools-rules.md` узла).

## Требования к `<tool>-executor.md`

- один инструмент — один исполнитель; на узел создаётся по агенту на инструмент,
  а не по агенту на операцию;
- системный промпт исполнителя = правила инструмента; задача приходит отдельным пакетом
  (одна задача, её рецепт и проверка) и не остаётся в контексте после сдачи;
- исполнитель возвращает: что сделано, где лежит, результат проверки, что осталось
  незакрытым.

Ссылки на эти файлы дают узлы продукта в своих `tools-rules.md`.
