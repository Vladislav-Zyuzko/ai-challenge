# Коротко: да, почти всегда стоит — но решает не размер правки, а риск

Размер диффа — плохой критерий для решения о ветке. Одна строка в условии оплаты, в SQL-миграции или в regex валидации может стоить дороже, чем 300 строк правок в README. Поэтому вопрос корректнее ставить так: «есть ли у этой правки последствия, которые нужно изолировать, отревьюить или откатить отдельно?» Если да — ветка. Если нет — можно и в основную.

## Разбор по пунктам

**1. Ветка в git почти ничего не стоит.** Ветка — это файл с 40-символьным SHA в `.git/refs/heads/`, создание мгновенно и не копирует файлы. Поэтому аргумент «лень заводить ветку ради одной строки» технически неверен: экономия нулевая, а изоляция реальная. Проверить можно самому: `git branch new-fix && git log --oneline -1 new-fix` — обе ветки указывают на один коммит.

**2. Главная ценность — не изоляция кода, а точка ревью и отката.** Отдельная ветка даёт вам Pull Request: коллега видит ровно одну строку в контексте, CI прогоняет тесты именно на этом изменении, а история остаётся линейной. Откат тоже становится точечным — `git revert <sha>` вместо разбора смешанного коммита. Альтернатива «закоммитить прямо в main» эти возможности съедает: если в том же коммите случайно окажутся ещё правки, откатывать придётся всё.

**3. Защищённые ветки и CI часто не оставляют выбора.** В большинстве командных репозиториев на `main` включены branch protection rules и обязательные проверки, так что `git push origin main` просто отклонится с ошибкой вида `protected branch hook declined`. Тогда вопрос «стоит ли» превращается в «как иначе», и ответ — только через ветку и PR. Проверить: Settings → Branches в GitHub/GitLab либо наличие `.github/workflows/*.yml` в дереве проекта.

**4. Когда ветку можно не заводить.** Личный репозиторий без CI и без других контрибьюторов, правка опечатки в README, обновление версии в конфиге, локальный эксперимент, который вы не собираетесь пушить. Здесь цена ветки — лишний шаг, а выгода нулевая. Второй легитимный случай: правка логически принадлежит уже открытой ветке (вы дописываете свою же фичу) — тогда не плодите новую, коммитьте в текущую.

**5. Осторожно с «мелкими» hotfix-ами в проде.** Именно там соблазн закоммитить в main напрямую максимален, а последствия — самые дорогие: во время инцидента нет времени на ревью, но потом никто не помнит, почему строка изменилась. Практика — отдельная ветка `hotfix/...` и ускоренный, но всё же оформленный merge. Это не бюрократия: сообщение коммита и PR-описание остаются единственным объяснением «почему».

**6. Trunk-based vs GitHub Flow — влияет на длину жизни ветки, а не на её существование.** В trunk-based разработке ветки живут часы, но они всё равно есть. В GitHub Flow ветка + PR — базовый ритуал. Обе модели сходятся в одном: короткая ветка под одно изменение, быстрый merge, без долгоживущих ответвлений.

## Пример: типовой цикл для правки в одну строку

```bash
# 1. Убедиться, что стартуете от актуального main
git switch main
git pull --ff-only

# 2. Ветка под конкретную правку, имя говорит о сути
git switch -c fix/typo-in-readme

# 3. Правка и коммит
#    (редактируете файл)
git add README.md
git commit -m "docs: fix typo in installation section"

# 4. Публикация и PR
git push -u origin fix/typo-in-readme
gh pr create --fill

# 5. После merge — уборка
git switch main
git pull --ff-only
git branch -d fix/typo-in-readme
```

Если правка оказалась ошибочной уже после merge, откат делается отдельным коммитом, а не переписыванием истории:

```bash
git revert <sha>          # создаёт коммит, отменяющий изменения
git push origin main
```

Последнее важно: `git commit --amend` и `git push --force` на общей ветке переписывают историю у всех — на опубликованном main этого делать нельзя, только `revert`.

## Что учесть

- **Rebase или merge перед PR.** Если main ушёл вперёд, `git rebase main` внутри своей ветки держит историю линейной и часто позволяет merge без конфликтов. Force-push после rebase допустим только в свою личную ветку, пока она не смержена и никто другой на ней не работает.
- **Squash при merge.** Для однострочных правок squash-merge даёт в main один осмысленный коммит вместо «wip», «fix», «fix2». Это настраивается в самом репозитории (GitHub: кнопка «Squash and merge», GitLab: опция проекта).
- **Переименования и переносы файлов.** Git может показать правку одной строки, хотя вы переместили файл — тогда ревьюер увидит большой дифф. `git diff -M` и `git mv` отдельным коммитом помогают не путать семантику и перемещение.
- **Правила команды важнее ваших предпочтений.** Посмотрите `CONTRIBUTING.md` и историю `git log --oneline -20`: если все коммиты идут через PR, не будьте исключением. Это проверяется за минуту и снимает спор.

## Итого

- Заводите ветку, если правка попадёт в общий удалённый репозиторий, есть CI, защита веток, ревью или хоть малейший риск последствий — стоимость ветки нулевая, а выгода в ревью и точечном откате реальна.
- Не заводите, если это личный репозиторий без проверок, правка косметическая и вы не собираетесь её ревьюить; либо если правка логически продолжает уже открытую вами ветку.
- Критерий выбора — риск и необходимость отдельного отката, а не количество строк: одна строка в логике оплаты опаснее сотни строк в документации.
