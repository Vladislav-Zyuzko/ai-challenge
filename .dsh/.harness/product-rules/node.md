# Узел

Узел — единица работы харнесса: задача, для которой нужны собственные правила, план
и приёмка. Структура узла **одинакова на всех уровнях вложенности** — в этом суть
рекурсии: корневой узел проекта и узел `профиль-пользователя-node` устроены идентично.

## Имена и расположение

- корневой узел проекта — `.project-harness/` (у него нет родителя);
- дочерние узлы — `<смысловой-слаг>-node/` внутри `nodes/` родителя;
- слаг: латиница/цифры/дефис, короткий и смысловой (`auth-node`, `user-profile-node`);
  переименование узла после создания запрещено (на слаг ссылаются контракты и отчёты).

## Структура

```
<узел>/
  product-rules.md            # ЧТО: правила поведения + контракт + инварианты (результат спецификации)
  product-rules-index.md      # карта спеки узла: краткое описание → ссылка (для среза и навигации)
  tools-rules.md              # ЧЕМ: карта инструментов + заметки по использованию в этом узле
  make-rules.md               # КАК: план (архитектор узла + критик)
  nodes-index.md              # карта дочерних узлов: slug, назначение, контракт, статус
  nodes/                      # вложенные узлы (та же структура)
  usage.md                    # как пользоваться продуктом — появляется при приёмке
  node-reports/               # артефакты этапов (см. state-machine.md)
    specification-report.md   # пишет родитель, читает архитектор узла
    planning-report.md        # пишет архитектор узла (включая возражения критика и их закрытие)
    realization-report.md     # пишет архитектор узла (исполнители передают ему результаты), дописывается
    verification-report.md    # пишет тестировщик
    acceptance-report.md      # пишут архитектор узла и родитель
```

Узел **не содержит** правил процесса (роли, этапы, критерии) — они в `.dsh/.harness/`.
Ссылки на них даются относительными путями.

## product-rules.md: обязательные секции

1. **Назначение** — что это за продукт и зачем он нужен (1–3 абзаца).
2. **Контракт и инварианты** — обязательная секция:
   - что продукт обещает наружу: входы, выходы, поведение, границы;
   - инварианты `I1…In` — проверяемые утверждения (без способа проверки инвариант
     не считается инвариантом).
3. **Область и границы** — что входит в узел и **что явно не входит** (out-of-scope
   обязателен: без него дети расширяют себе задачу).
4. **Зависимости и соседи** — какие инструменты соседей и родителя разрешено использовать
   (по их `usage.md`) и какие данные узел получает извне.
5. **Срез спецификации** — какие файлы/секции родительской спеки мигрировали в узел
   (ссылки), с указанием, что именно из них относится к делу.

Если узел вырос и контракт перестал помещаться в один файл, он выносится в
`contract.md` рядом, а в `product-rules.md` остаётся ссылка. Инварианты остаются
нумерованными в одном месте.

## tools-rules.md: формат

```markdown
## Инструменты
| Инструмент | Зачем в узле | Правила использования | Предусловия |
|---|---|---|---|
| flutter | UI мобильного клиента | .harness/tools-bank/flutter-rules.md | SDK установлен, версия ≥ X |

## Заметки узла
- локальные особенности применения (то, чего нет в общих правилах инструмента)
```

Инструмент без предусловий не считается доступным: предусловия — часть контракта узла
со средой (и то, что проверяется health-check'ом перед использованием).

## make-rules.md: формат плана

План — не список «сделать то-то», а таблица задач с зависимостями:

```markdown
| id | Задача | Родитель | Атомарна | Рецепт и проверка (для атомарных) | Зависит от | Исполнитель | Бюджет | Файлы во владении |
|----|--------|----------|----------|-----------------------------------|------------|-------------|--------|-------------------|
| T1 | …      | I1,I3    | да/нет   | рецепт: … / проверка: …           | —          | flutter     | 5%     | lib/auth/**       |
```

Обязательные свойства плана:

- каждая задача ссылается на инварианты, которые она закрывает (или на задачу
  интеграции) — иначе непонятно, зачем она;
- неатомарные задачи превращаются в дочерние узлы, а не «делаются как-нибудь»;
- для атомарных названы **рецепт** и **проверка** (иначе это ложная атомарность);
- есть задача интеграции: собрать детей и проверить стыки до сдачи родителю;
- зависимости образуют DAG; независимые задачи помечаются как параллельные;
- у задач, которые пишут файлы, указано владение (`files_owned`) — два исполнителя
  не должны править один файл одновременно;
- бюджет: сумма долей по задачам + резерв на интеграцию ≤ бюджет узла.

## Срез: как родитель передаёт правила вниз

Срез пишет **родитель**, а не выбирает ребёнок. В срез входят:

1. фрагменты product-rules, относящиеся к задаче (со ссылками на источник);
2. инварианты, которые касаются этого узла (и только они);
3. интерфейсы соседей, на которые узлу разрешено опираться (через их контракты/usage);
4. явное **out-of-scope** — что узел не делает;
5. срез tools-rules: нужные инструменты и их предусловия.

Навигация по спеке родителя — через индекс (`product-rules-index.md` в корне узла:
краткое описание → ссылка). Индекс нужен: (а) родителю, чтобы составлять срез;
(б) ребёнку, чтобы **запросить** расширение среза, если чего-то не хватает. Бродить по
всей спеке самостоятельно ребёнок не должен — иначе срез перестаёт ограничивать контекст.

Индекс дочерних узлов (`nodes-index.md`) заполняется по мере создания детей и содержит
их slug, назначение, контракт и статус — он нужен для навигации и приёмки, а не для среза.

## Атомарность

Задача атомарна, если выполнены все четыре условия:

1. **нет неизвестных** — рецепт известен целиком, его можно назвать одной-двумя строками;
2. **предусловия выполнимы сейчас** — инструменты, доступы, данные;
3. **есть дешёвая проверка** — результат принимается/отвергается без экспертизы проекта;
4. **провал локален** — ошибка переделывается внутри задачи, а не пересматривает план.

Экономический порог: дробить задачу стоит, только если ожидаемая стоимость ошибки при
«сделать сразу» выше стоимости планирования, контрактов, проверки и накладных расходов
на контекст. Для мелких и понятных задач «сделать сразу» — законный выбор.

Не атомарна задача, у которой: не назван рецепт; не выполнимы предусловия; нет проверки;
или она тянет за собой интерфейс, которого ещё нет в контрактах.

## Состояние узла и возобновление

Состояние выводится из `node-reports/` — по последнему заполненному отчёту:

| Последний отчёт | Состояние | Кто работает дальше |
|---|---|---|
| specification-report | `specified` | архитектор узла (планирование) |
| planning-report | `planned` | исполнители (реализация) |
| realization-report (в работе) | `realizing` | исполнители |
| realization-report (завершён) | `realized` | тестировщик |
| verification-report (провал) | `rework` | архитектор узла → исполнители |
| verification-report (успех) | `verified` | приёмка |
| acceptance-report (принято) | `done` | родитель продолжает свой план |
| acceptance-report (правки) | `rework` | архитектор узла |
| любой этап при блокере | `blocked` | эскалация |

Каждый отчёт начинается с шапки:

```markdown
Этап: планирование
Статус: завершён | в работе | провал | блокер
Следующая роль: исполнители (flutter)
contract_version: 1.2
harness_version: 0.1
Дата: 2026-02-14
```

Это позволяет возобновить работу после перезапуска: читаем шапки отчётов, а не логи.

## Бюджет и эскалации

- Родитель выделяет ребёнку бюджет при создании узла: `tokens`, `retries`, `depth`.
- Сумма бюджетов детей ≤ бюджет родителя − резерв (~20% на интеграцию и приёмку).
- Ориентир по стадиям: спецификация ≤10%, планирование и критика ≤15%, реализация ≤55%,
  верификация ≤15%, приёмка ≤5%. Перекос — сигнал: план слишком подробный, спека незрелая
  или задача неверно разбита.
- Ретраи: `K` попыток после провала верификации (по умолчанию 2), затем эскалация.
- Эскалация содержит: проблему, доказательства, **варианты решения с ценой** (добить за
  счёт резерва / ослабить инвариант Ix / разбить иначе / остановить) и рекомендацию.
- Продуктовые вопросы (изменение поведения, ослабление инварианта) решает только
  пользователь — через архитектора проекта.

## Дисциплина артефактов

- **Один писатель.** `specification-report` — родитель; `planning-report` — архитектор
  узла; `realization-report` — архитектор узла (исполнители передают ему результаты,
  сами отчёты узла не пишут); `verification-report` — тестировщик; `acceptance-report` —
  архитектор узла и родитель.
- **История не перезаписывается.** Реализация дописывается секциями с датой и автором
  либо нумерованными ревизиями (`realization-report-002.md`).
- **Доказательства.** Каждое утверждение о проверке сопровождается воспроизводимой
  командой/артефактом и ссылкой на инвариант.
- **Версии.** `contract_version` меняется при любом изменении контракта или инвариантов;
  `harness_version` фиксирует правила, по которым строился узел. При несовпадении версий
  у ребёнка и родителя ребёнок помечается `rework` (change propagation), а его
  верификация считается недействительной до повторной проверки.

## Чеклист перед реализацией

- [ ] в `product-rules.md` есть назначение, контракт, инварианты, out-of-scope, срез;
- [ ] у каждого инструмента в `tools-rules.md` указаны предусловия;
- [ ] критика проведена, все blocker'ы закрыты письменно;
- [ ] у каждой задачи есть признак атомарности; у атомарных названы рецепт и проверка;
- [ ] есть задача интеграции и она в бюджете с резервом;
- [ ] владение файлами распределено, конфликтов нет;
- [ ] бюджеты детей не превышают бюджет узла.

## Чеклист перед приёмкой

- [ ] `verification-report.md` заполнен, каждое утверждение подкреплено доказательством;
- [ ] все инварианты узла проверены или явно помечены как непроверяемые (с обоснованием);
- [ ] архитектор узла сам проверил слаженность продукта (задача интеграции закрыта);
- [ ] `usage.md` для продукта готов (иначе он не станет инструментом);
- [ ] `acceptance-report.md` содержит решение родителя и ссылку на версию контракта.
