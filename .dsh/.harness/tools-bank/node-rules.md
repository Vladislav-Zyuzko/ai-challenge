# Правила инструмента: node (встроенный тест-раннер, без зависимостей)

harness_version: 0.1
Версия правил: 0.2
Статус: active
Проверено: 2026-09-20, Windows, Node v24.17.0
Ревизия 002 (2026-09-20): явно разрешены статические проверки файлов через `node:fs`
(структура разметки, состав атрибутов, отсутствие внешних ресурсов) — это не DOM-проверка.

## 1. Назначение

**Уместен** для прогона автотестов чистой логики на встроенном `node:test` +
`node:assert/strict` и для одноразовых скриптов проверки. Ноль зависимостей:
`npm install` не нужен и не выполняется.

**Не уместен** для проверки DOM/браузера (нет `document`), для TypeScript и сборки,
для тестов, которым нужен пакет из реестра (`jsdom`, `jest` и т. п.), для серверной
логики продукта — продукт браузерный, серверная часть вне контракта.

**Отдельно уместен** для статических проверок файлов через `node:fs`: структура разметки,
набор атрибутов (`data-key`), отсутствие внешних `src`/`href`/`@import`/`url(http`,
отсутствие `document`/`fetch` в модулях логики. Это чтение файлов, а не работа с DOM,
поэтому ограничение выше на такие проверки не распространяется.

## 2. Предусловия среды

| Предусловие | Как проверить (health-check) | Проверенный факт |
|---|---|---|
| Node.js установлен | `node --version` | `v24.17.0` (`C:\Program Files\nodejs`) |
| Встроенный `node:test` доступен | `node --input-type=module -e "import test from 'node:test'; console.log(typeof test)"` | `function` |
| `node:assert/strict` доступен | `node --input-type=module -e "import assert from 'node:assert/strict'; console.log(typeof assert.ok)"` | `function` |
| Версия ≥ 22.8 (нужны `--test-isolation=none` и определение ESM в `.js`) | сравнить `node --version` | `24.17.0` — ок |
| Тест-раннер не требует прав на создание дочерних процессов | `node --test-isolation=none --test "tests/*.test.mjs"` | работает (см. грабли) |

`npm` в этой среде не нужен; `npm --version` через PowerShell падает на
`npm.ps1 ... cannot be loaded ... not digitally signed` из-за ExecutionPolicy.
Это не мешает инструменту: пакеты не ставятся.

## 3. Как ставить задачу исполнителю

- **вход:** один тестовый файл (или одна группа тестов), перечень инвариантов,
  которые он закрывает (например I2, I3, I4), рецепт и ожидаемая команда прогона;
- **ожидаемый результат:** тесты написаны и **проходят**; имена тестов содержат
  id инварианта; вывод команды — воспроизводимое доказательство;
- **границы:** тесты импортируют только чистую логику (`src/calculator.js`) и
  стандартную библиотеку Node; ни одной установки пакетов; тест не обращается к DOM
  и не поднимает сервер;
- **отчёт исполнителя:** файл, команда, счётчики `pass`/`fail`, что не покрыто.

## 4. Как проверять результат

Каноническая команда (из папки продукта):

```powershell
node --test-isolation=none --test "tests/*.test.mjs"
```

Признак успеха: код выхода `0` и в сводке `fail 0`. Один файл можно прогнать
напрямую в текущем процессе: `node tests/calculator.test.mjs` (тоже код выхода `0`).

Проверено на образце 2026-09-20: `--test-isolation=none --test "*.test.mjs"` → `pass 1 / fail 0`;
импорт `../src/calculator.js` (ESM в `.js` без `package.json`) работает на Node 24.17.0
без предупреждений.

## 5. Лучшие практики и грабли

- Каждый тест называть по инварианту: `test('I4: 0.1 + 0.2 → "0.3"', …)` — тогда
  отчёт верификации ссылается на доказательство, а не на пересказ.
- Сравнивать форматированную строку результата, а не сырые `float`: I4 проверяется
  как `format(add(0.1, 0.2)) === '0.3'`. Проверка `0.1 + 0.2 === 0.3` всегда ложна.
- Результат-ошибку проверять по контракту (`res.ok === false`, `res.error` содержит
  текст), а не по `NaN`/`Infinity`.
- Импорт только с явным расширением: `import { add } from '../src/calculator.js'`.
- **Главная грабля среды:** `node --test` с изоляцией процессов на каждый файл
  пытается поднять дочерний процесс с pipe-каналами и в sandbox-окружении падает
  `Error: spawn EPERM` (проверено 2026-09-20). Лечение — `--test-isolation=none`
  (все файлы в одном процессе) или прямой запуск файла. Это же поведение встретится
  у любого инструмента, который сам спавнит процессы, — проверять командой, а не по памяти.
- Глобы передавать в кавычках: PowerShell не раскрывает `tests/*.test.mjs` сам,
  раскрывает Node (поддерживает glob в `--test` начиная с v22).
- Не тянуть `node_modules` ради одной проверки: всё нужное есть в stdlib.
- **Статические проверки файлов** делаются через `node:fs` + `new URL('../index.html', import.meta.url)`
  (путь не зависит от текущего каталога запуска). Проверять: контейнеры разметки, точный
  набор `data-key`, отсутствие внешних ресурсов, отсутствие DOM-API в модулях логики.
  Полезно в связке: юнит-тесты проверяют поведение, статический тест — стык «разметка ↔ ключи».
- `node --check <file.js>` работает и для ESM-синтаксиса (проверено: код 0 на файле
  с `import`/`export`) — годится как дешёвая проверка синтаксиса до запуска браузера.

## 6. Ограничения

- Нет DOM, нет браузера: UI-инварианты этим инструментом не проверяются — только
  чистая логика; DOM остаётся ручному чек-листу.
- Нет покрытия по умолчанию (`--experimental-test-coverage` есть, но в контракт
  продукта не входит и не требование).
- Нет TypeScript, транспиляции и сборки.
- `--test-isolation=none` означает общий процесс: падение одного файла может
  оборвать остальные; при росте тестов и нормальной среде предпочтительнее обычный
  `node --test`.
- Порог версии: на Node < 22.8 нет ни `--test-isolation=none`, ни надёжного
  определения ESM в `.js` — инструмент считается недоступным.
