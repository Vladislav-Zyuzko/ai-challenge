# Ревью задачи «Минимальная подстрока, содержащая все символы t» (Dart)

## Видение задачи

Это классический *Minimum Window Substring* (аналог LeetCode 76) на **скользящее окно с двумя указателями** и мультимножественным условием покрытия. Ключевая суть: нужно не «найти символы t в любом порядке» (это решалось бы проще), а найти **непрерывную подстроку**, в которой **количество каждого символа ≥ количества этого символа в t**. Вся сложность — в корректном учёте кратности и в аккуратных границах окна. Условие «при равенстве длин допустима любая» снимает с решающего необходимость лексикографических сравнений — это подарок, не усложняйте себе жизнь.

Уже в самой постановке есть недосказанности, которые решающий обязан **явно зафиксировать как допущения**, а не молча выбрать наугад:

1. Не задано понятие «символ»: кодпоинт (rune) или UTF-16 code unit? Для ASCII неважно, для эмодзи/не-BMP — критично (см. ниже).
2. Не заданы ограничения на длины `s` и `t` (обычно до ~10^5) — отсюда требование O(n+m).
3. Не сказано, что делать с пустой `t` (стандарт: вернуть `""`).
4. Не сказано про регистр/пробелы/произвольные символы — надо считать, что сравнение точное и алфавит произвольный (не только A–Z).

## Где чаще всего ошибаются в типовых решениях

### 1. Кратность символов — главный источник багов

- **Самый частый баг:** проверять валидность окна по длине (`right-left+1 >= t.length` или «окно не меньше t») вместо поэлементного сравнения частот. Это ломает все случаи с повторами: `s="a", t="aa"` обязано дать `""`, а по «длинé-окна» логике может «покрыться».
- **Баг со счётчиком «покрытых» символов:** если вести счётчик `matched`/`formed` — сколько *различных* символов сейчас удовлетворяют требуемой частоте — его надо инкрементить **только в момент перехода** «было меньше требуемого → стало равно требуемому» и декрементить **только при обратном переходе**. Типовые ошибки:
  - инкремент на *каждое* добавление символа (счётчик становится «общим числом совпадений», а не числом покрытых различных символов);
  - порча счётчика на «лишних» копиях: окно содержит больше символов, чем нужно (счётчик уходит в отрицательные дельты), и при уходе символа из окна счётчик «проскакивает» уровень и начинает врать;
  - декремент при уходе символа, которого в окне всё ещё достаточно.
  Если счётчик поплыл, окно то «валидно» при нехватке символов, то «невалидно» при полном покрытии — решение падает на тестах с дублями.
- **Сравнение частот перебором карты на каждом шаге** — не баг по сути, но убивает заявленную сложность (см. п. 3).

### 2. Пустые и крайние случаи

- `s` пустая → `""`; `t` пустая → `""`.
- `|t| > |s|` → `""` (часто забывают, но алгоритм сам это даст, если корректно инициализирован).
- Символ из `t` вообще отсутствует в `s` → `""` (важно: правая граница должна доехать до конца и корректно завершиться, не зациклившись и не вернув невалидное окно).
- `s == t` (в т.ч. однобуквенные) → вся строка.
- **Окно — вся строка целиком:** классическая ошибка — инициализировать «лучшую длину» нулём или забыть обновить ответ, когда валидным становится только окно `[0, len-1]`; результат — ошибочный `""`.
- Окно упирается в самый левый или самый правый край строки (логика сдвига левого указателя после фиксации ответа).
- `t` из одинаковых символов: `s="aabb", t="aa"` → `"aa"`, а не `"a"` и не вся строка.
- Строка вида, где минимальное окно находится в конце, а «жадный» ранний выход по первому найденному — неверен: окно после первого попадания надо продолжать сжимать слева.
- «Весь `s` является окном, но внутри есть более короткое вложение» — левый указатель должен сжимать до упора, пока условие ещё держится, и запоминать минимум **после** сжатия.

### 3. Сложность

- Ожидаемое: **O(|s| + |t|)** по времени, доп. память **O(|Σ|)** или O(|t|).
- Если валидность окна пересчитывается «с нуля» на каждом шаге правой границы (перебор карты/массива алфавита, повторное сканирование подстроки) — это O(n·|Σ|) или даже O(n²) через повторные вложенные проверки; для скрытых тестов с длинами ~10^5 это кандидат на таймаут. Допустимо только при малом фиксированном алфавите и с честной оговоркой.
- Осторожно со «склейкой» строк на каждом шаге (результат-кандидат в цикле) — квадратичная память/время; хранить только пару (начало, длина) и делать один `substring` в конце.

### 4. Юникод и специфика Dart — то, о чём забывают чаще всего

- `String.length` в Dart — это **UTF-16 code units**, а не число «символов». Индексация `s[i]` и `s.split('')` режут по code unit: эмодзи и прочие не-BMP символы (суррогатные пары) **разрезаются пополам** — получаются «символы»-сироты, которые никогда не совпадут с символами `t`.
- Главное требование — **согласованность единицы измерения**: если считаете по code unit — и режьте `substring` по code unit; если по кодпоинтам (`runes`) — индексы для `substring` обязаны соответствовать границам кодпоинтов, иначе в ответе появится битая строка с одиноким суррогатом. Смешивать «считаю по runes, режу по code-unit индексам» нельзя.
- Практичный надёжный вариант под произвольный Unicode — ключевать счётчики по числовому значению кодпоинта (`Map<int,int>`), а не фиксированным массивом на 52/128 букв; тогда не зависит от того, какие именно символы придут в тестах.
- Не полагаться на нормализацию Unicode (é как один кодпоинт против e + combining accent) — в постановке это не оговорено, значит сравнение «как есть», без нормализации.

### 5. Ошибки в выдаче результата

- Неверная семантика границ: `substring(start, start+len)` — правый индекс **исключительный**; типовые баги дают строку на символ короче/длиннее или «съедают» первый символ.
- Возврат не минимальной, а первой найденной подстроки без сжатия слева.
- Возврат конкатенации/накопления символов вместо **непрерывной подстроки исходного `s`** (нарушение контаминации — например, сбор «всех нужных букв» в порядке появления, что не является подстрокой).

### 6. Прочее

- Баг «жадности»: брать первое валидное окно и не пытаться сжать — неверно; классический контрпример `s="ABAACBAB", t="ABC"`: первый валидный фрагмент не минимален.
- Сравнение длин и хранение лучшего окна: держать пару индексов и обновлять строго при `len < bestLen` (равенство не трогаем — любая допустима, но детерминированность не помешает).
- Забывают про регистр: `s="a", t="A"` → `""` (сравнение точное).

## Чек-лист требований к итоговому решению

**Контракт**
- [ ] Ровно сигнатура `String minWindow(String s, String t)`, без переименований и лишних параметров.
- [ ] Возвращает именно подстроку исходного `s` (не перестановку, не конкатенацию), либо `""`.
- [ ] Учёт кратности: покрытие по мультимножеству, пример `s="a", t="aa"` → `""`.
- [ ] `""` только в двух смыслах: (а) нет покрывающей подстроки; (б) тривиальные пустые входы — поведение консистентное.
- [ ] При равенстве длин — любая из минимальных; при этом алгоритм обязан реально найти минимум, а не «первое подходящее».
- [ ] Сравнение символов точное, без нормализации и без приведения регистра.

**Крайние случаи (обязательные зелёные тесты)**
- [ ] `s=""`, `t=""`, `t` длиннее `s`.
- [ ] `s==t` (включая длину 1: `"a","a"` → `"a"`).
- [ ] Символа из `t` нет в `s`.
- [ ] Дубли в `t`: `"aabb","aa"`; `"a","aa"` → `""`.
- [ ] Минимальное окно = весь `s`; окно у левого края; окно у правого края.
- [ ] Строки, где первое валидное окно не минимально (жадность ломается).
- [ ] Повторяющиеся паттерны и `t`, где нужных символов ровно впритык.

**Алгоритм и сложность**
- [ ] Двухточечное скользящее окно; левая граница сжимает окно, пока условие покрытия держится.
- [ ] Счётчик покрытия корректно переживает «лишние» копии символов и уход символов из окна (переходы «меньше → равно → меньше»).
- [ ] O(|s|+|t|) времени и O(|Σ|) (или O(|t|)) памяти — без скрытых повторных сканирований.
- [ ] Кандидат хранится как (индекс, длина), подстрока извлекается один раз в конце.

**Юникод/Dart**
- [ ] Явно выбрана и **соблюдена** единица «символа» (кодпоинт или code unit) для счёта и для разрезания; суррогатные пары не разрезаются; в возвращаемой строке нет одиноких суррогатов.
- [ ] Нет квадратичного поведения из-за конкатенаций/`split` в цикле.
- [ ] Код null-safe, компилируется без предупреждений, `main()` (если есть) не влияет на чистоту функции.

**Верификация (рекомендовано)**
- [ ] Три примера из условия.
- [ ] Перекрёстная проверка на случайных коротких строках против **brute force** (перебор всех пар границ + подсчёт частот) — единственный способ поймать ошибки кратности и границ, которые «на глаз» не видны.
- [ ] Прогон с не-BMP символами (эмодзи в `s` и `t`), если претендуете на произвольный Unicode.

## Итоговая позиция критика

Решение принимается только если оно проходит «треугольник»: **мультимножественное покрытие через скользящее окно**, **корректный счётчик переходов**, **единая и безопасная работа с юникод-границами в Dart**. Типичные решения тонут именно на дублях в `t` и на границах окна (крайние случаи), а не на «идее» — поэтому ревью должно гнать в первую очередь за тестами на эти сценарии и за честной сложностью. Полный код здесь намеренно не привожу — как и требовалось, даю только критерии приёмки.
