# dsh-term

Своя интерактивная терминальная CLI для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) — тонкий клиент поверх SDK JSON-RPC протокола. Ноль внешних зависимостей, только Node.js.

## Как это работает

```
dsh-term
   │  spawn
   ▼
dsh --profile sdk   ◄── JSON-RPC 2.0 по newline-delimited stdio
   │  (initialize / session/prompt / shutdown)
   ▼
Harness runtime (полный агент: инструменты, сессии, субагенты)
```

- **Пока модель думает — в терминале переливается синим подпись «Deep diving…»** (градиент бежит по тексту); пошёл видимый ответ — анимация останавливается и текст стримится; после вызова инструмента подпись возвращается.
- **Живой счётчик токенов**: пока крутится «Deep diving…», рядом в скобках (светлее) растёт счётчик выходных токенов — `Deep diving… (237 tokens)`; когда пошёл видимый текст — счётчик тикает хвостиком за строкой ответа. Это оценка по символам стрима (калибруется по фактическому usage), шаги целые: 200…201, от 1000 — 1.1k, 1.2k. Точные цифры — в сводке после хода.
- **Стрим и живой счётчик требуют патча харнесса** (`session.assistant-stream`). В формате сессий v3 харнесс больше не пишет события `assistant/chunk`, а дельты модели ходят только внутри процесса (`agent/assistant-stream`) — SDK-сервер их не форвардит. Патч из `~/.dsh-term/harness-patches` добавляет нотификацию, и текст снова стримится. Без патча `dsh-term` не ломается: ответ печатается целиком из durable-события `assistant/message` (без стрима и без живого счётчика). Проверить этот путь при наложенном патче: `DSH_TERM_NO_STREAM=1`.
- **Метрики токенов (англ.)**: после ответа — пустая строка, линия на всю ширину терминала и блок, начинающийся с `turn`:

  ```
  (ответ модели)

  ────────────────────────────────────────────
  — turn 2 ended: completed
    tokens: in 16.2k (cache 7.9k) / out 5
    requests: 2 (this turn: 1)
    context: 8.1k / 1M (0.809%)
  ```

  Где: `in` — суммарные входные токены сессии (включая кэш-токены), `(cache …)` — сколько из них пришло из кэша (тарифицируется в разы дешевле), `out` — выходные токены (включая thinking), `requests` — сколько раз сходили в модель (в агентном ходе на один вопрос их бывает много: каждый вызов инструмента — новый запрос, и каждый заново отправляет всю историю), `context` — размер последнего запроса, то есть текущее заполнение окна.

  В многошаговых ходах (цепочка инструментов) стоимость каждого шага выводится сразу (`· step 2: in … / out …`). Потолок окна — 1M (как у адаптера DeepSeek v4; переопределить: `DSH_TERM_CTX_MAX`). В one-shot метрики идут в stderr, stdout остаётся чистым.
- **Markdown-рендер (лёгкий)**: в интерактивном TTY ответ подсвечивается — заголовки жирным синим DeepSeek, `**жирный**`, `*курсив*`, `` `код` `` голубым, кодовые блоки (```/~~~) приглушённым. Рендер ничего не добавляет и не удаляет (текст и копия не меняются), работает по чанкам: незакрытые к концу фрагмента конструкции остаются как есть, состояние кодовых блоков держится весь ход. В one-shot (`-p`) вывод остаётся raw markdown.
- **Промпт** `dsh> ` — слово «dsh» выделено жирным фирменным синим DeepSeek (#4D6BFE) для контраста (без цвета на пайпе / `NO_COLOR`).
- Активность инструментов выводится строками (`▶ bash …`, `✔ done`)
- Сессии стойкие: последняя сессия запоминается и **автоматически продолжается** при следующем запуске; есть `/resume` и `--resume`
- События субагентов (`subagent.started`) тоже рендерятся

## Первый вход: токен

При первом запуске `dsh-term` сам запросит DEEPSEEK API ключ (ввод скрыт) и сохранит его в managed-хранилище харнесса — `<home>/.credentials.yaml` (формат `version: 1` / `refs` / `records`). Дальше токен берётся оттуда автоматически; харнесс подхватывает его сам. Сменить токен — команда `/token`.

Приоритет токена: окружение (`DEEPSEEK_API_KEY`) → хранилище → интерактивный запрос.

## Запуск

```powershell
dsh-term                       # интерактивный REPL
dsh-term -p "вопрос"           # one-shot: один ответ и выход
```

One-shot режим (`-p, --print <text>`) — как `claude -p`: в stdout попадает **только ответ** (диагностика — в stderr), контролы `--format/--max-length/--stop/--max-tokens/--temperature` применяются именно к этому ответу. Выход: 0 при `completed`, 1 при ошибке. Промпт из файла — как в claude, через подстановку:

```powershell
dsh-term -p "$(Get-Content prompt.md -Raw)"
```

В one-shot автоматически добавляется дисциплина «только итоговый результат» (без описания процесса/промежуточных заметок), чтобы при перенаправлении вывода в файл попадал финальный ответ, а не рабочий нарратив агента.

```powershell
dsh-term -p "переведи в json: {…}" --format json --max-length 1000
dsh-term -p "кратко" --stop "END"            # маркер уходит с промптом
```

Изолированный home по умолчанию — `~/.dsh-term` (SDK-рекомендация: не смешивать с `~/.dsh`). Чтобы переиспользовать managed credentials из общего home:

```powershell
dsh-term --dsh-home C:\Users\<you>\.dsh
```

## Опции

| Флаг | Назначение |
|---|---|
| `--dsh-home <path>` | Harness home (default: `~/.dsh-term`) |
| `--profile <name>` | профиль рантайма (default: `sdk`) |
| `--provider <id>` | провайдер (default: `deepseek-official`; env `DSH_TERM_PROVIDER`) |
| `--model <name>` | модель (default: `deepseek-v4-flash`; env `DSH_TERM_MODEL`) |
| `--max-tokens <n>` | жёсткий кап токенов ответа (адаптер) |
| `--temperature <n>` | температура сэмплинга 0..2 (умолчание — провайдерская, 1.0); действует на агента сессии |
| `--format <spec>` | формат ответа: пресет (`json`/`plain`/`markdown`/`bullets`/`code`/`table`) или свободное описание |
| `--max-length <n>` | лимит длины ответа в символах: инструкция модели + обрезка показа с пометкой |
| `--stop <marker>` | стоп-символ: передаётся с промптом; показ обрывается при генерации маркера (сам маркер не печатается) |
| `--compress <mode>` | компрессия истории: `on` (default) · `off` · `<ratio 0..1>` (доля окна для срабатывания); env `DSH_TERM_COMPRESS` |
| `--compress-keep <n>` | сколько последних токенов держать «как есть» (default 50000 — это ≈5% окна 1M) |
| `--strategy <id>` | стратегия управления контекстом: `harness` (default) · `sliding` · `facts` · `branch` (env `DSH_TERM_STRATEGY`) |
| `--window <n>` | N сообщений для стратегий `sliding`/`facts`/`branch` (default 6; env `DSH_TERM_WINDOW`) |
| `--with-profiles` | выбрать **профиль пользователя** из меню в начале сессии (или создать первый) |
| `--user-profile <slug>` | включить конкретный профиль сразу, без меню (env `DSH_TERM_USER_PROFILE`) — для скриптов и прогонов |
| `--session <id>` | продолжить конкретную сессию (синоним: `--resume <id>`) |
| `--workspace <path>` | рабочая папка сессий (default: текущая) |
| `--dsh-bin <path>` | путь к `dsh` (default: `dsh` из PATH) |

### Контролы ответа (`--format` / `--max-length` / `--stop`)

- `--format json` → инструкция «отвечай строго валидным JSON»; любой другой текст → свободное описание формата.
- `--max-length N` → инструкция «не длиннее N символов» + жёсткая обрезка показа: `…[обрезано dsh-term: лимит N символов]`.
- `--stop "END"` → **стоп-символ передаётся с промптом** (модель получает «заверши ответ ровно маркером "END"»), и в момент, когда маркер сгенерирован в потоке, показ обрезается на нём (сам маркер не печатается).
- **Скоуп**: все три контрола действуют на **один следующий ответ**, затем автосброс.
- `--format`/`--max-length` — мягкие (инструкция в промпте); `--max-length`/`--stop` дополнительно обрезают показ на клиенте (жёстко, но сессия хранит полный текст).


### Компрессия контекста

История сжимается автоматически: последние `--compress-keep` токенов держатся «как есть»,
остальное суммирует LLM и подставляет вместо полной истории. Механизм живёт в рантайме
харнесса (плагин `compaction-basic`), а dsh-term им управляет и показывает результат —
настройки уходят харнессу патч-оверлеем (`dsh --patch`), генерируемым на лету, поэтому
Program Files править не нужно.

```
dsh-term                                           # дефолт: порог 100k, хвост «как есть» 50k
dsh-term --compress off                            # baseline: авто-компрессия выключена
dsh-term --compress 0.02 --compress-keep 3000      # агрессивный режим (для экспериментов)
```

Почему хвост такой большой: 50k — это примерно половина порога (100k), то есть при компакции
в summary уходит лишь то, что старше последних ~50k токенов. Хвост «как есть» — единственная
часть истории, которую модель видит дословно (точные куски кода, вывод инструментов, детали
последних шагов), поэтому его выгодно держать крупным, а порог — заметно выше
`префикс + хвост + размер summary`. Ориентир самого харнесса — `retainRatio 0.16`, то есть
160k при окне 1M; 6k (как было раньше по умолчанию) — это 0.6% окна, сжимать приходилось
почти всю историю.

Политика задаётся **в токенах** — это объективная величина. Считать «в сообщениях» сознательно
не стали: в агентной сессии «сообщение» — это шаг с вызовами инструментов, и размеры различаются
на порядки (реплика пользователя ~20 токенов, результат чтения файла — тысячи), поэтому любая
средняя оценка вводит в заблуждение. В строке запуска и в `/context` видно и порог, и хвост:

```
compress: on (compact at 100k tokens, keep last 50k tokens)
  compression: on (compact at 100k tokens, keep last 50k tokens)
  fixed prefix: ≈ 8k tokens (system prompt + tools) — не сжимается
  per compaction: keep last 50k verbatim, up to ≈ 42k older tokens summarized
    (это верхняя граница: хвост набирается целыми сообщениями, поэтому реально сжимается меньше)
```

Важно: `up to ≈ N` — **верхняя граница**, а не то, что сжимается на самом деле. Хвост «как есть»
набирается **целыми сообщениями** с конца, поэтому:

- если `keep` больше одного вашего ответа, хвост вырастает ступенькой на целый ответ — и всё,
  что старше него, может оказаться совсем небольшим (реальный случай: `keep 10k` ≈ два больших
  ответа, сжимать осталось 1.5k → компакция сняла 429 токенов, а вызов стоил 10.8k);
- **чтобы компакция вообще что-то сжимала, `keep` должен быть меньше размера типичного ответа**;
- и `порог ≥ префикс(≈8k) + keep + 15k` — иначе сжимаемый остаток сопоставим с размером самой
  сводки (≈1k) и экономии не будет.

Несогласованную политику CLI отмечает сразу — харнесс такую спеку **отбрасывает** (требует
`retainTokens < threshold`), и компакция молча не работает (в логе харнесса остаётся только
warning, сессия едет без сжатия):

```
compress: on (compact at 20k tokens, keep last 50k tokens)
  note: keep 50k >= threshold 20k: harness rejects this policy (retainTokens must be < threshold),
        so compaction will NOT run — raise --compress or lower --compress-keep
```

Слишком маленький сжимаемый участок тоже предупреждается: если порог вровень с неподвижным
префиксом (system prompt + инструменты ≈8k) или `порог − префикс − хвост` меньше ~5k токенов,
компакция либо сработает на каждом шаге, либо будет отказывать с
`✖ compaction failed: summary is not smaller than the shadowed content` (summary ~700 токенов
не меньше сжимаемого участка в ~270 токенов), сжигая вызовы суммаризатора впустую:

```
compress: on (compact at 12k tokens, keep last 4k tokens)
  note: compact threshold 12k is close to the fixed prefix (8k, system prompt + tools) — in agentic turns compaction will fire at once; use --compress 0.05 for a sane default
  note: only ≈ 0 tokens per compaction (threshold 12k − prefix 8k − keep 4k) — raise --compress or lower --compress-keep
```

В выводе видно, что происходит:

```
· context compacted: shadowed 4.2k → summary 843 (net ≈ −3.4k, call 14.4k) (deepseek-v4-flash)
· tool output pruned: 3.2k tokens shadowed
✖ compaction failed: summary is not smaller than the shadowed content (947 >= 947)
```

Как читать эти числа (частая путаница):

- `shadowed → summary` — что ушло из запроса и что встало на его место; **`net` — сколько
  реально снято с окна** (затенённый участок минус summary с рамкой);
- **`call` — сколько СТОИЛ вызов суммаризатора**, а не сколько снято: вход такого вызова —
  переигранный префикс разговора (system + tools + сообщения до участка), поэтому он
  сопоставим с порогом, а не с размером участка; харнесс делает так намеренно, чтобы попасть
  в KV-кэш провайдера. Входные токены почти целиком кэш-чтение, то есть дешёвые, но это
  реальный расход;
- **размер summary почти постоянный — ≈1–1.2k токенов**, независимо от размера участка:
  структура из 8 секций и рамка заданы инструкцией харнесса. Замер: участки 1k / 2.4k / 4.2k
  дали summary 1.1k / 1.2k / 1k. Поэтому компакция окупается только когда участок **на порядок
  больше** summary, а участок в 1–3k — это чистые потери (в логе такие помечаются `wasteful`);
- строка `compression: N summarize calls, X tokens` в сводке хода — это **суммарная цена**
  компакций, её надо вычитать из экономии, а не из контекстного окна; отказы тоже жгут вызов,
  но их usage харнесс в событии не пишет — отсюда пометка `, N failed` и
  `(failed calls not metered)`;
- **политика убыточна, если `call` ≫ `net`** (в примере выше одна компакция сняла 32 токена,
  потратив 9.5k). Признак: `порог − префикс(≈8k) − хвост` сопоставим с размером summary
  (~1k) — CLI предупреждает об этом на старте (`note: only ≈ N tokens per compaction`);
- компакция сама по себе **не гарантирует, что контекст уменьшится между ходами**: снятое
  может быть меньше того, что добавил предыдущий ответ.

Сводка после хода добавляет стоимость самой компрессии (иначе экономия была бы посчитана
нечестно):

```
  tokens: in 41.2k (cache 33.8k) / out 1.9k
  requests: 9 (this turn: 1)
  compression: 3 summarize calls, 2.4k tokens
  context: 9.5k / 1M (0.951%)
```

`/context` показывает текущее состояние: режим и пороги, заполнение окна, расход, последний
summary целиком (начало). В частности, отсюда видно, что компрессия «спит», пока контекст
не дошёл до `thresholdRatio × contextWindow` — при окне 1M и дефолтном 0.1 это ~100k токенов.

Что важно знать по настройке (проверено на живых прогонах):

- **порог должен быть выше системного промпта** (~8k токенов у агента харнесса): при
  `thresholdRatio 0.005` (5k) компакция пытается сработать сразу, но сжимать ещё нечего;
- **`retainTokens` жёстко меньше порога**: харнесс проверяет `retainTokens < thresholdTokens`
  и при нарушении отбрасывает политику (`TargetPressureConfigError` → warning в логе
  харнесса, компакция не работает). CLI предупреждает об этом на старте;
- **сжимаемый участок должен быть заметно больше summary** (~`maxTokens` 4096): если
  `порог − префикс − хвост` близко к нулю, харнесс отказывает
  (`✖ compaction failed: summary is not smaller than the shadowed content`) и вызовы
  суммаризации уходят впустую — измерено: при `12k/4k` три отказа за ход, `in 67.2k` на
  задачу из пяти запросов;
- **дефолт CLI — 100k / 50k**: компакция «спит», пока контекст не дойдёт до 100k, а в summary
  уходит лишь то, что старше последних 50k токенов. Короткие сессии не платят вообще ничего,
  длинные — платят за суммаризацию редко и сохраняют большой дословный хвост. Кто хочет
  измеренной экономии в токенах, а не качества, — крутит `--compress 0.02 --compress-keep 3000`
  (умеренный режим эксперимента);
- стоимость самих вызовов суммаризатора видна отдельной строкой в сводке — её нужно
  вычитать из экономии;
- `--compress off` **не отключает плагин**, а лишь выключает автокомпакцию (`auto: false`):
  сервис `compaction` нужен плагину `command-compact`, и полное отключение ломает загрузку
  дерева плагинов.

## Стратегии управления контекстом (day10)

По умолчанию контекстом управляет харнесс (компрессия из дня 9). Альтернативно контекст
собирает **клиент** — тогда в модель уходит ровно то, что решила стратегия, а режим можно
переключать **на ходу**, без перезапуска рантайма:

| Стратегия | Что уходит в модель |
|---|---|
| `sliding` | последние N сообщений, всё старше — отбрасывается |
| `facts` | блок facts (цель/ограничения/предпочтения/решения/договорённости) + последние N сообщений; facts обновляются после каждого сообщения пользователя |
| `branch` | ветки диалога от чекпоинта + последние N сообщений |

```
dsh-term --strategy facts --window 6
dsh> /strategy            # меню: стрелками выбрать режим (применится со следующего сообщения)
dsh> /branch new пилот    # чекпоинт + две ветки A и B от текущего места
dsh> /branch b            # переключиться на ветку B
```

Как это работает:

- ход идёт в **свежую** harness-сессию (id вида `ctx-<anchor>-tN`), поэтому поверхность харнесса
  не накапливает историю; в списке `/resume` служебные сессии ходов отфильтрованы;
- диалог, facts и ветки лежат в `~/.dsh-term/context/<sessionId>.json`: сессия помнит свою
  стратегию, а `/resume` её подхватывает;
- в режиме стратегии автокомпакция харнесса выключается — контекстом управляет только стратегия;
- в выводе видно, что уходит: `· контекст [facts (окно 6)]: 6 сообщений + 4 facts, 670 токенов ≈`,
  а служебные вызовы обновления facts — отдельной строкой в сводке
  (`strategy: 1 facts update, 1.6k tokens`), чтобы расход был честным;
- `/context` показывает стратегию, активную ветку, размер диалога, сами facts и расход на них.

Замеры на сценарии «собираем ТЗ» (14 сообщений, `--window 6`): `sliding` и `branch` держат
контекст ~330 токенов на ход, но к 12–14-му сообщению теряют детали из начала диалога (0 из 6
контрольных фактов); `facts` стоит ~700 токенов на ход + ~1.7k на обновление и сохраняет все 6.
Подробный разбор — `week2/day10.md`.

`/branch` — часть режима `branch`, поэтому команда **всегда приводит сессию в этот режим**
(в списке команд рядом с ней это написано, если режим другой). Ветки можно резать и от
`sliding`/`facts`, но тогда сначала произойдёт переключение режима — чтобы состояние сессии
не было двусмысленным.

## Запросы к пользователю (подтверждения и вопросы)

Агент умеет **спрашивать** — это двусторонний JSON-RPC: рантайм отправляет клиенту запрос,
клиент отвечает тем же id. `dsh-term` рисует оба случая классическими средствами (меню в
стиле `/resume`; в пайпе — нумерованным списком).

**Запрос доступа** (`approval/request` от инструмента, когда действие выходит за текущие права —
например запись вне рабочей папки):

```
Запрос доступа: pwsh · call_00_s49Rq5n3…
  причина: escalate sandbox to danger-full-access: … outside the session workspace …
доступ>
 ▸ • Разрешить                    однократно
     Разрешить всё в этой сессии   без вопросов до конца сессии
     Отклонить                    агент получит отказ (fail closed)
```

- Исходы протокола однократные (`allowed-once` / `rejected` / `cancelled` / `unavailable`);
  «разрешить всё в этой сессии» — клиентская настройка: дальше `dsh-term` отвечает
  `allowed-once` сам и пишет `· … разрешено автоматически`.
- `--auto-approve` (env `DSH_TERM_AUTO_APPROVE=1`) включает этот режим сразу — удобно для скриптов.
- Esc/отмена → `cancelled` (действие не выполняется).

**Вопрос с вариантами** (`ask_user_question` у модели; используется и ревью плана):

```
Какой вариант выбрать?
 1. Альфа
 2. Бета
 3. Гамма
 4. свой вариант… — ввести текст
выбор>
```

- Поддерживаются несколько вопросов в одном запросе, `multiSelect` (пробел — отметить,
  Enter — подтвердить), свободный текст, `detail` (для ревью плана — markdown плана) и
  подсказка «одобрить — вариант «…»» для `intent: plan-review`.
- Инструмент включается оверлеем `dsh-term-tools.patch.yml` (в base-бандле есть сервис
  вопросов, но сам инструмент не смонтирован); отключить: `DSH_TERM_NO_ASK_TOOL=1`.
  Если строка уже есть в патче профиля, дубликат не создаётся.
- Оба механизма требуют патча харнесса (answerer'ы в SDK-сервере) — см.
  `~/.dsh-term/harness-patches/`. Без патча подтверждения fail-closed, а вопросы возвращают
  ошибку инструмента.

## Профиль пользователя (персонализация, day12)

Персонализация живёт **поверх модели памяти**: долговременная память — это профиль
пользователя, и он подключается к **каждому** запросу, а не хранится в истории сессии.

```
~/.dsh-term/user-profiles/<slug>.md     # человекочитаемо, правится руками
```

```markdown
# Профиль пользователя: Кратко и по делу

## Стиль
- Отвечай на русском, коротко: вывод сразу, без преамбул.
## Формат
- Максимум 5 строк текста, затем при необходимости код.
## Ограничения
- Не добавляй раздел «Итого».
## Чего избегать
- Вежливых вступлений («Отличный вопрос!»).
```

Секции (`## Стиль`, `## Формат`, `## Ограничения`, `## Интересы и контекст`,
`## Явные просьбы`, `## Чего избегать`) разбираются при чтении, поэтому файл можно
дописывать вручную — следующий `/profile use` (или перезапуск) его подхватит. BOM в
начале файла не мешает (профиль, сохранённый Блокнотом или VS Code как «UTF-8 с BOM»,
читается как обычно).

**Как профиль попадает в модель.** Оверлеем `- id: system-prompt` с `personaPrefix`:
текст профиля становится частью system prompt, то есть виден на **каждом** запросе
сессии (и в под-агентах тоже). Перед текстом профиля идёт короткая рамка: профиль —
это выбор пользователя «сейчас», и он отменяет более ранние договорённости о стиле,
формате, языке и длине ответа из переписки. System prompt собирается при спавне
рантайма, поэтому обновление профиля помечает состояние как «грязное», и перед
следующим сообщением `dsh-term` перезапускает рантайм с тем же `sessionId` — сессия
резюмируется, меняется только системный промпт.

**Приоритет профиля над историей.** Одной рамки в system prompt мало: если в переписке
раньше звучала прямая просьба о стиле (например «эмодзи не нужны»), модель держится за
неё как за указание пользователя и игнорирует профиль. Поэтому включение и смена профиля
объявляются ещё и в **самом свежем сообщении** — префиксом к промпту, как контролы
`--format`; первый промпт в продолжаемой сессии получает такое объявление автоматически.
Проверено на сессии с противоречащей историей: с объявлением модель следует профилю
(`🙂✨👍` вместо ответа словами), без него — следует истории.

**Куда и что сохраняется** (это и есть «явный выбор» из задания):

| Слой | Где | Что | Когда попадает в промпт |
|---|---|---|---|
| Профиль пользователя | `~/.dsh-term/user-profiles/<slug>.md` | предпочтения: стиль, формат, ограничения, интересы, просьбы, чего избегать | всегда: system prompt (`personaPrefix`) |
| Краткосрочная память | транскрипт сессии (харнесс) | реплики текущего диалога | по окну/стратегии контекста |
| Рабочая память | `~/.dsh-term/context/<sessionId>.json` | `facts`/ветки/окно режима стратегий | в запрос хода (режимы `sliding`/`facts`/`branch`) |

**Обучение на ходу.** Каждое сообщение пользователя (в интерактивной сессии) разбирается
фоновым вызовом LLM: что в нём нового о стиле, формате, ограничениях, контексте. Найденное
дописывается в профиль — с дедупликацией, лимитом 6 пунктов на секцию и бюджетом ~700
токенов: при перерасходе профиль сжимается (и об этом пишет явно, чтобы правки в профиле
не менялись молча). Процесс печатает строку вида
`· профиль: +1 пункт(ов) (ограничения: 1) → в промпт со следующего хода`. Разбор не
блокирует ответ модели, а перед следующим сообщением `dsh-term` перезаписывает оверлей
(профиль мог обновиться уже после записи файла) и перезапускает рантайм — поэтому новый
пункт действительно попадает в system prompt, а не только в файл. **В one-shot (`-p`)
профиль не дообучается** — прогоны не должны менять входные данные.

**Команды:**

```
/profile                 показать профиль, его размер и файл
/profile list            список профилей (текущий помечен «*»)
/profile use <slug>      переключить профиль (без аргумента — меню)
/profile new             создать профиль: описание → LLM → заголовок ≤5 слов + пункты
/profile off             отключить персонализацию
```

**Старт сессии:** `--with-profiles` показывает меню (существующие профили + «создать
новый»); если профилей ещё нет — сразу предлагает описать первый. `--user-profile <slug>`
берёт профиль без меню. В начале сессии печатается диагностика:
`profile: «Кратко и по делу» (kratko) · ~197 токенов в system prompt · файл: …`, а в
`/context` — строка `profile:` с расходом на разбор персонализации.

Сравнение трёх профилей на одном наборе вопросов — `week3/day12`.

### Меню команд (интерактивный режим)

Все команды знать наизусть не нужно: начни вводить **`/`** — под строкой ввода появится меню команд.

- набери **`/`** — меню со **всеми** командами;
- набери **`/`** + подстроку (например `/res`) — только команды, **матчащиеся** с подстрокой (по префиксу или вхождению);
- **↑/↓** — выбор команды в меню;
- **Enter** — запустить выбранную команду (или отправить строку, если меню закрыто);
- **Esc** — закрыть меню (набранный текст остаётся).

Меню отделено от чата горизонтальной линией-разделителем; пока меню открыто, блок
периодически перерисовывается, чтобы «призрачные» копии строк после переключения
вкладок/фокуса терминала не накапливались.

Меню работает только в интерактивном терминале (TTY); при вводе из файла/пайпа команды пишутся целиком, как раньше.

### Заголовки сессий

Сессии в списке показываются не только по id — сначала идёт короткий **заголовок**, а id уходит вторичным (тусклым) текстом, как в Claude:

```
1. «объясни коротко что такое контекстное окно моде…» 2acbe5bd-837c-4620-9670-182abd39fed9
```

- **Источник заголовка** — LLM-саммаризация первого запроса: dsh-term делает отдельный дешёвый вызов API (≤10 слов, `thinking` отключён, ~85 токенов) и ставит суть запроса. Пример: «Привет! Помоги выбрать авиабилеты, проанализировав сразу несколько источников» → **«Выбор авиабилетов из разных источников»**;
- **Черновой заголовок** из первого промпта (до 48 символов) показывается сразу, а когда саммари готово — заменяется; при ошибке API остаётся черновой;
- Заголовок от харнесса (`session/title`) не перебивает наш финальный (он помечается `titleLocked` в state), но принимается, если своего ещё нет;
- **Кэш**: заголовки хранятся в `<home>/dsh-term-state.json` (`titles`), поэтому список открывается мгновенно;
- **`/resume` без аргумента** — интерактивный выбор: **↑/↓ — навигация, Enter — выбрать, Esc — отмена**; набор текста фильтрует список по заголовку/id (Esc при набранном фильтре сначала очищает его). Над списком — линия-разделитель (как у меню команд). Длинные списки показываются окном (12 строк) с пометками «… ещё N».
- **`/resume <что-то>`** строкой принимает: номер в списке, полный id, префикс id или часть заголовка;
- В пайпе/скриптах (не TTY) выбор работает как раньше — нумерованный список и ввод строкой.
- Заголовок виден в строке старта (`resuming session: «…» id`), в `/session` и в списке `/resume`.

Оговорка: сессии, созданные **до** этой фичи, показываются только по id — их логи лежат многофреймовым zstd, а Node умеет читать лишь первый фрейм (там только заголовок сессии). Заголовок появится, как только такая сессия получит новый `session/title` от харнесса.

## Примечания

- **Анимация** — только в интерактивном терминале (TTY); отключить: `DSH_TERM_NO_ANIM=1`. На пайпе поведение обычное, построчное.
- **Живой счётчик токенов** — только TTY, отключить целиком: `DSH_TERM_NO_METER=1` (если терминал ведёт себя странно). Счётчик стирается backspace-ами по своей видимой ширине, но рисуется **только когда целиком помещается в строку** (учёт табов, ANSI, служебных строк и отложенного переноса) — поэтому стирание не задевает текст ответа. Никаких `ESC 7`/`ESC 8` (сохранение курсора) он не использует: эти последовательности поддерживаются не всеми терминалами, а без них счётчик «прорастал» в вывод модели (регресс-тест: `dsh-term/tests/render-screen.test.mjs`, режим `DSH_TEST_IGNORE_SAVE=1`).
- **Сессии на диске**: `sessions/<ns-по-рабочей-папке>/<sessionId>/session.jsonl[.zstd]` (сжатие zstd по умолчанию); `/resume` находит их рекурсивно.
- **Скриптовый ввод**: stdin читается построчно; при EOF (`< file`, Ctrl+Z+Enter) после обработки всех строк CLI корректно завершается. Внимание: пайп из Windows PowerShell 5.1 в нативные процессы не закрывает stdin — для скриптов используйте редирект из файла (`cmd /c "dsh-term < in.txt"`).
- **Внутренности**: реализовано по [@deepseek-ai/dsh-sdk-protocol](C:/Program%20Files/dsh/deepseek-harness/packages/sdk/protocol/README.md): запросы `initialize` / `session/prompt` / `shutdown`; нотификации `session.event` / `session.status` / `session.assistant-stream` (живой стрим, патч) / `subagent.started` / `subagent.finished`; одна JSON-RPC 2.0 фрейма на строку; битые строки игнорируются.
- **Патчи харнесса** (`~/.dsh-term/harness-patches/`, см. `README.md` и `reapply.ps1`): (1) resume-сессий — `createSession` в `packages/sdk/server/` пробует `agents.resume`, а `create` только для новых id; (2) `--temperature`; (3) живой стрим `session.assistant-stream`. При обновлении или переустановке харнесса патчи стираются — восстановить: `reapply.ps1` (та же версия) или пере-наложить по таблице из README кит-а.
