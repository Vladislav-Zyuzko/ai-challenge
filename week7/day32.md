# День 32. Автоматизация ревью кода

Задание: пайплайн, в котором ассистент анализирует новый PR — получает diff и изменённые файлы,
использует RAG (документация + код) и выдаёт текст ревью с багами, архитектурными проблемами
и рекомендациями.

Сделано в том виде, как договорились: завели агента-ревьювера `ai-challenge-reviewer`, который
после открытия PR запускается **локально на нашей машине**, разбирает diff и оставляет
комментарии прямо в PR. Процесс ревью вынесен в отдельный скилл `/review-pr <номер|ссылка|ветка>`,
а скилл подключён завершающей фазой к публикации дня и недели.

## 1. Как это работает

```
/publish-day  ──▶ коммит → push → gh pr create ──▶ PR открыт
                                                   │
                                                   ▼
                              /review-pr <PR>  (или автоматически из publish-day)
                                                   │
        ┌──────────────────────────────────────────┴───────────────────────────────┐
        │ детерминированная часть (dsh-term/lib/review.mjs)                        │
        │  • найти PR (номер, ссылка, ветка, текущая ветка)                        │
        │  • gh pr view → метаданные, gh pr diff → diff в файл                     │
        │  • проверить, не ревьюили ли уже (по маркеру агента)                     │
        └──────────────────────────────────────────┬───────────────────────────────┘
                                                   ▼
                       отдельная сессия dsh-term -p (чистый контекст)
                       --rag project --rag project-code · deepseek-v4-flash
                       читает diff файлом, ищет по документации и коду,
                       возвращает текст ревью + машиночитаемые findings
                                                   │
                                                   ▼
                       комментарии в PR: сводный + построчные, каждый — с тегом агента
```

**Почему не GitHub Action.** У агента локальный харнесс, локальные базы RAG и Ollama —
hosted-раннер GitHub до них не дотянется. Триггером служит наша публикация, поэтому
`/publish-day` после создания PR сразу вызывает фазу ревью (`--no-review` её пропускает).
Ошибка ревью не отменяет публикацию: PR уже открыт, фазу можно повторить одной командой.

**Почему отдельная сессия.** Ревьювер работает с чистым контекстом (тот же принцип, что у
критика в `.dsh/.harness/agents/critic.md`): если он унаследует сессию автора, он будет
защищать собственные решения вместо чтения кода. Сессия запускается как `dsh-term -p` —
одноразовый режим, который не пишет состояние dsh-term и не мешает интерактивной сессии.

## 2. Корпус кода: вторая база RAG

Документации для ревью мало: нужен ещё код, чтобы сверять конвенции и находить похожие места.
Собрана отдельная база `project-code` (день 31 дал базу документации `project`):

| База | Корпус | Файлов | Чанков | Стратегия | Сборка |
|---|---|---|---|---|---|
| `project` | документация: README, `docs`, отчёты, скиллы | 84 | 749 | `structural` | 285 с |
| `project-code` | код: `.py`, `.mjs`, `.cjs`, `.js`, `.ts`, `.ps1`, `.yaml`, `.yml`, `.json` | 97 | 1269 | `fixed` | 577 с + 116 с (пересборка, 1041 чанк из кэша) |

Почему отдельная база, а не расширение документации: смешивать README с исходниками в одном
индексе значит размывать обе выдачи — вопрос «как собрать индекс» должен приводить в README,
а «где разбирается git status» — в код. Почему `fixed`: у кода нет markdown-заголовков, и
структурная стратегия режет исходники вслепую.

`.json` в пресете кода появился не сразу: без него lock-файлы вообще не доходили до фильтра
по именам (их отсекало расширение), и настройка `exclude_names` была мёртвой — это нашёл
ревьювер в первом прогоне.

```powershell
cd doc-index
python -m doc_index index --project-code --vault .. --strategy fixed
python -m doc_index search "как разбирается git status" --project-code --vault .. --strategy fixed
```

## 3. Роль и рубрика ревьювера

`.dsh/.harness/agents/code-reviewer.md` — спецификация роли: что проверяет, что считается
проблемой, шкала severity и формат вывода. Восемь пунктов рубрики: логика и границы, данные и
состояние, безопасность, архитектура и согласованность, совместимость и регрессии, тесты и
проверяемость, ресурсы, документация и отчётность.

Severity: **blocker** (нельзя вливать: потеря данных, секрет в репозитории, падение на обычном
вводе), **major** (переделка или регрессия в другом месте), **minor** (улучшение).

Вывод — ровно две части: текст ревью для комментария и машиночитаемый блок:

```markdown
<!-- FINDINGS:START -->
[{"severity":"major","title":"пустой корпус при пустых suffixes",
  "file":"doc-index/doc_index/collect.py","line":173,
  "why":"команда пишет пустой индекс и не сообщает об ошибке",
  "fix":"проверить, что suffixes непустой, и вернуть понятную ошибку"}]
<!-- FINDINGS:END -->
```

Второй блок нужен, чтобы пайплайн мог оставить замечание построчным комментарием. Если
разобрать его не удалось — ревью публикуется сводкой, и это не ошибка.

## 4. Команда `/review-pr`

```
dsh> /review-pr              # PR текущей ветки
dsh> /review-pr 42           # по номеру
dsh> /review-pr https://github.com/…/pull/42
dsh> /review-pr 42 --force   # пересобрать (без --force повтор не публикуется)
dsh> /review-pr 42 --dry-run # собрать diff и промпт, агента не запускать
```

| Шаг | Что происходит |
|---|---|
| 1 | PR ищется по номеру, ссылке, ветке или берётся PR текущей ветки; закрытый PR не ревьюится |
| 2 | `gh pr view` → метаданные и список файлов, `gh pr diff` → `out/review/pr-<номер>/diff.patch` |
| 3 | Проверяется маркер агента в комментариях и отзывах PR: ревью уже есть → выход (идемпотентность) |
| 4 | Собирается промпт (`prompt.md`), запускается отдельная сессия ревьювера |
| 5 | Ответ разбирается по маркерам, публикуется сводный комментарий и построчные замечания |
| 6 | В терминал — ссылка на PR, счётчик замечаний по severity и путь к артефактам |

**Тег агента обязателен.** Аккаунт GitHub один, поэтому комментарии агента и человека неразличимы
без метки. Каждый комментарий начинается с маркера и видимого тега:

```markdown
<!-- ai-reviewer:ai-challenge-reviewer v1 -->
**🤖 AI-РЕВЬЮ · агент `ai-challenge-reviewer`** — сгенерировано автоматически, это не комментарий автора PR.
```

Скрытый маркер нужен ещё и для идемпотентности: по нему распознаётся уже опубликованное ревью,
поэтому повторный `/publish-day` не плодит копии. Вердикт (approve / request changes) агент не
выставляет — только комментарии; решение за человеком.

## 5. Тесты

`node dsh-term/tests/review.test.mjs` — **63 проверки** без модели, сети и GitHub. `gh`
подменяется адаптером: для этого детерминированная логика вынесена в `dsh-term/lib/review.mjs`.

| Что проверяется | Примеры проверок |
|---|---|
| Выбор PR | ссылка → номер; номер без лишних запросов; текущая ветка; нет PR для ветки; закрытый PR; ошибка gh; **запрашивается SHA головы PR** |
| Идемпотентность | маркер в комментарии; маркер в отзыве; чужой комментарий не считается ревью; ошибка gh ≠ «ревью есть» |
| Промпт | роль и скилл по путям; метаданные PR; список файлов; файл с полным diff; обе базы RAG; маркеры ответа; обрезка diff, описания PR и списка файлов; запрет правок; предел замечаний |
| Разбор ответа | текст между маркерами; findings из JSON и из ```json; отброс неизвестной severity; битый JSON; отсутствие блока; не массив; пустой массив; **предел 12 замечаний и отброс лишних** |
| Позиции в патче | номер строки новой версии → позиция в diff; удалённые строки не занимают номер; строк вне патча нет |
| Тег | маркер в первой строке; видимый тег во второй; тег в построчных комментариях |
| Публикация | `pr review` → `pr comment` как запасной путь; построчно только замечания со строкой в патче; `position` и `commit_id` в вызове; ошибка построчного попадает в отчёт; провал публикации сообщается; dry-run не трогает GitHub |

Все прочие наборы остались зелёными: **245 тестов** `doc-index` (в пресете корпуса кода
появились свои проверки) и девять наборов `dsh-term`.

## 6. Что нашлось по дороге

| Что | Как выглядело | Решение |
|---|---|---|
| Заглушка `gh` на PATH не работает | `spawnSync('gh')` находит настоящий `gh.exe` даже при подмене PATH и `PATHEXT`; абсолютный путь к `.cmd` даёт `EINVAL` | логика вынесена в модуль с адаптером `gh(args)`, тесты подменяют его напрямую |
| Ограничение длины аргумента в Windows | промпт с полным diff (десятки тысяч символов) не влез бы в argv (~32k) | в промпт идёт только начало diff, полный файл агент читает инструментом |
| `-p` и состояние сессии | ревьювер — вложенный процесс dsh-term | проверено: одноразовый режим не пишет `dsh-term-state.json` (там `if (!isOneShot)`) |
| Lock-файлы в корпусе кода | `package-lock.json` попадал в индекс как «код» | `.json` добавлен в расширения пресета, lock-имена отсекаются настройкой `exclude_names` (без `.json` эта настройка была мёртвой — нашёл ревьювер) |
| Код и документация в одном индексе | поиск по коду отвечал бы отчётами | две базы: `project` и `project-code` |

## 7. Живая проверка: ревью собственного PR

PR #30 (этот самый день) открыт командой `/publish-day`, и ревью запустилось автоматически,
как и задумано. Дальше вышло интереснее, чем планировалось: агент нашёл настоящие дефекты,
и после их починки понадобилось три прогона, чтобы построчные комментарии заработали.

**Прогон 1** (530 с, 9 замечаний: 0 blocker, 3 major, 6 minor) — сводный комментарий
опубликован с тегом, построчных 0 из 9. Настоящие находки:

| Замечание | Что было |
|---|---|
| [major] `.gitignore` | артефакты ревью (`out/review/pr-N/`) не игнорируются, а `/publish-day` делает `git add -A` — следующий день закоммитил бы diff и промпт |
| [major] `--model` в `/review-pr` | значение флага оставалось в ссылке на PR: `/review-pr 42 --model x` → «PR 42 x»; в скилле флаг обещан |
| [major] тесты корпуса кода | `exclude_names` и `code_config` появились без проверок |
| [minor] длина промпта | ограничен был только diff, а описание PR и список файлов — нет: у Windows предел argv ~32 000 символов |
| [minor] предел замечаний | «до 12» был только просьбой в промпте, код его не держал |
| [minor] описание PR | статистика снималась до `git add`, поэтому новые файлы в описание не попали |
| [minor] dead config | `exclude_names` не срабатывал ни в одном пресете (lock-файлы отсекало расширение) |
| [minor] скилл и отчёт | бюджет diff в скилле (60 000) не совпадал с кодом (4000); описание базы `project-code` не соответствовало корпусу |

Все девять закрыты коммитом `bf8dbc8`: `/out/` в `.gitignore`, разбор `--model` со значением,
ограничение всех частей промпта, предел замечаний в коде, `commit_id`, dry-run через рабочую
функцию, статистика после `git add` и раздел «Как проверить», `.json` в пресете кода, тесты.

**Прогон 2** (297 с, 8 замечаний) — построчных снова 0. Причина оказалась не в агенте:
GitHub на этом аккаунте валидирует запрос по старой схеме и отвечает на `line`/`side`
«line is not a permitted key». Построчный комментарий принимается только с `position` —
номером строки внутри патча. Позиции теперь считает `patchPositions`.

**Прогон 3** (478 с) — снова 0 из 9, и это была уже моя ошибка: `resolveReviewTarget`
не запрашивал у `gh pr view` поле `headRefOid`, поэтому `headSha` был пуст, и проверка
`if (posted && slug && headSha)` молча пропускала все построчные комментарии. Поле добавлено,
ошибки построчных больше не глотаются — они печатаются в отчёте команды.

**Прогон 4** (105 с, 10 замечаний) — итог: **построчно ушло 7 из 10**, три замечания без
строки в diff остались в сводке (как и задумано). В PR сейчас 11 сводных ревью и 7 построчных
комментариев, у каждого в первой строке маркер `<!-- ai-reviewer:ai-challenge-reviewer v1 -->`,
во второй — видимый тег `🤖 AI-РЕВЬЮ · агент ai-challenge-reviewer`.

Последний прогон заодно нашёл ещё три вещи, которые я закрыл тем же днём: `--auto-approve`
у сессии ревьювера над недоверенным diff (риск: инструкции внутри PR выполняются с правами
записи — для чужих PR так делать нельзя), исключение в фазе ревью обрывало публикацию после
открытия PR (теперь обёрнуто), и кавычки в путях `+++ b/"файл с пробелом"` ломали привязку
(снимаются). Вывод для себя: **авторевью полезно не «валом замечаний», а тем, что находит
то, что автор пропустил** — из девятнадцати находок двух прогонов семнадцать были по делу.

## 8. Ограничения

- **Комментарии идут от аккаунта владельца** — тег обязателен, но технически отличить автора
  можно только по нему; отдельного GitHub-аккаунта для агента нет.
- **Ревьювер работает с `--auto-approve`**: в неинтерактивном режиме иначе не обойтись, но это
  значит, что инструкции внутри diff технически могут быть исполнены с правами записи. Для
  своих PR это приемлемо, для чужих — нет: там нужен либо запуск с подтверждениями, либо
  ограниченный набор инструментов (в dsh-term его пока нет).
- **Ревьювер не запускает тесты** и не проверяет поведение в рантайме: он читает diff, код и
  документацию. «Это сломает X» — гипотеза, помеченная как гипотеза.
- **Построчные комментарии — только к строкам из патча.** Позиция считается по diff
  (`patchPositions`); если строка не входит в изменения, замечание остаётся в сводке. Строка
  `\ No newline at end of file` в подсчёте позиций пропускается: для замечаний после неё
  позиция может уехать на единицу — на своих PR такого случая не встретилось, но это
  известное допущение.
- **Модель облачная.** Локальная 8B для ревью не годится: замеры дня 31 показали 22 факта из 36
  и выдуманные ссылки — а ревью без точных ссылок бесполезно. Модель переключается
  `--model` / `DSH_TERM_REVIEW_MODEL`.
- **`/publish-week` остаётся спецификацией**: команды для публикации недели в dsh-term нет,
  фаза ревью описана в скилле и выполняется командой `/review-pr` по номеру недельного PR.
- Ревью не перезапускается само при новых коммитах в PR: нужен явный `/review-pr --force`.

## 9. Итог

1. **Агент-ревьювер заведён**: роль и рубрика в `.dsh/.harness/agents/code-reviewer.md`, имя
   `ai-challenge-reviewer`, комментарии помечены тегом и скрытым маркером.
2. **Пайплайн запускается после открытия PR**: `/publish-day` вызывает фазу ревью автоматически
   (`--no-review` пропускает), `/review-pr` работает и вручную для любого PR.
3. **Ассистент получает diff и изменённые файлы** — `gh pr view` + `gh pr diff`; полный diff
   кладётся файлом, начало уходит в промпт.
4. **RAG используется**: две базы — документация (`project`, 749 чанков) и код
   (`project-code`, 1211 чанков), плюс файловые инструменты и git-контекст из дня 31.
5. **Ревью возвращается тремя разделами** — потенциальные баги, архитектурные проблемы,
   рекомендации — с severity и адресом `файл:строка`, плюс машиночитаемый блок замечаний.
6. **Идемпотентность и безопасность**: повторный запуск не публикует второе ревью, агент не
   правит код, не коммитит и не выставляет вердикт.
7. **Проверено на себе**: ревью собственного PR нашло 19 замечаний в двух прогонах, из них
   17 по делу — включая артефакты ревью, которые уехали бы в следующий коммит, и неработающий
   флаг `--model`. Все закрыты в этом же PR; построчные комментарии (7 из 10) привязаны
   к строкам патча, остальные остались в сводке.
