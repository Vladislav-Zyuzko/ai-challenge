# SKILLS — скиллы ai-challenge как команды dsh-term

Каждый скилл — это **команда dsh-term** и файл-спецификация в этой папке. Скиллы бывают двух видов:

- **макрос** — команда исполняет рецепт детерминированно (git/gh), не полагаясь на «свободного» агента;
- **роль** — команда делает детерминированную подготовку (проверки, скан состояния, сборка промпта) и запускает ход агента, который дальше работает по спецификации скилла.

## Реестр скиллов

| Скилл (файл) | Команда dsh-term | Вид | Что делает |
|---|---|---|---|
| [publish-day.md](publish-day.md) | `/publish-day` | макрос | коммит на ветке дня → push → PR day→week с описанием → ревью агентом |
| [publish-week.md](publish-week.md) | `/publish-week`¹ | макрос | сводка недели → PR feature/weekN→develop с итогами недели → ревью агентом |
| [review-pr.md](review-pr.md) | `/review-pr [<номер\|ссылка\|ветка>] [--force] [--dry-run]` | макрос + роль | ревью PR локальным агентом: diff + RAG (документация и код) → комментарии с тегом агента в самом PR |
| [create-project.md](create-project.md) | `/create-project [что строим] [--check <path>]` | роль | сессия архитектора проекта: опросник (что делаем → где делаем → требования) → `.project-harness` → гейт инструментов → ноды; `--check <path>` — диагностика по отчётам |
| [task-from-figma.md](task-from-figma.md) | `/task-from-figma <ОЧЕРЕДЬ> <ссылка\|текст>` | роль | задача в указанной очереди трекера по кадру Figma: закреплённый порядок вызовов инструментов **двух** MCP-серверов (`figma` + `sltracker`) |
| [support.md](support.md) | `/support [<номер>\|off]` | роль | сессия техподдержки: обращение из локального JSON + FAQ продукта (`--rag support`) + задача в `INFRA` с тегом `[DSH-TERM]` |

¹ `/publish-week` пока описан как спецификация (ручные шаги по этому файлу); команды в
dsh-term для недели нет — при публикации недели шаги выполняются по скиллу.

## Скилл `review-pr`

- Запускает **локального** агента-ревьювера (отдельная сессия dsh-term с чистым контекстом):
  GitHub-hosted раннер не дотянулся бы ни до харнесса, ни до баз RAG, ни до Ollama.
- Триггер — наша публикация: `/publish-day` вызывает фазу ревью сразу после создания PR
  (`--no-review` пропускает). Для недельного PR фаза выполняется по спецификации.
- Роль, рубрика и формат вывода — `.dsh/.harness/agents/code-reviewer.md`;
  базы: `project` (документация) и `project-code` (код).
- Комментарии публикуются от аккаунта владельца, поэтому **каждый начинается с тега**
  `🤖 AI-РЕВЬЮ · агент ai-challenge-reviewer` и скрытого маркера `<!-- ai-reviewer:… -->`
  (по нему распознаётся уже опубликованное ревью — повторный запуск не плодит копии).
- Ревью не правит код, не коммитит и не выставляет вердикт: только комментарии.
- Артефакты прогона: `out/review/pr-<номер>/` (diff, промпт, ответ агента, готовый комментарий).

## Скилл-роль `create-project`

- Работает по правилам процедурного харнесса `.dsh/.harness/` (роль — `agents/project-architect.md`).
- **Ничего не воспринимается буквально**: текст после команды — это речь пользователя
  (первое сообщение архитектору), а не путь и не параметры. Путь, стек и названия
  архитектор выясняет в диалоге и подтверждает вслух.
- Харнесс продукта создаётся **внутри проекта**: `<path>/.project-harness/`, причём папку
  архитектор проверяет инструментами (пусто / есть файлы / уже начат проект) и создаёт
  только после подтверждения.
- Детерминированная часть команды: проверка `.dsh/.harness/`, чтение версии правил,
  сборка промпта; отдельно `--check <path>` — скан `node-reports/*` (этап, статус,
  следующая роль, версии, противоречия, точка возобновления).
- Работа не начинается, пока в `.dsh/.harness/tools-bank/` нет правил нужных инструментов:
  архитектор спрашивает пользователя, собрать правила самому (A) или дополнит пользователь (B).

## Скилл-роль `task-from-figma`

- Требует **двух** MCP-серверов сразу: `figma` (локальный stdio-мост к Figma Desktop) и `sltracker`.
  Сессия запускается как `dsh-term --mcp figma --mcp sltracker`.
- Детерминированная часть команды: разбор очереди из аргумента (формат ключа), извлечение `node-id`
  из ссылки Figma (`1:23` / `1-23` / `%3A` → `1-23`), проверка, что оба сервера подключены, чтение
  спецификации и сборка промпта с закреплённым порядком вызовов.
- Агент: читает кадр инструментами Figma (выделение или `node_id`), проверяет очередь через
  `list_queues`, создаёт задачу, добавляет комментарий со ссылкой и **перечитывает** её для проверки.
- Ключ задачи из ответа `create_task` — это те данные, которые передаются между шагами: без него
  шаги 4–5 бессмысленны, поэтому порядок обязателен.
- Приёмка: в выводе видны вызовы обоих серверов, `key` совпадает в `create_task`, `add_comment`
  и `get_task`, задача открывается в трекере с описанием из спеки.

## Скилл-роль `support`

- Продукт поддержки — сам `dsh-term`: FAQ продукта лежит в `support/faq/` и проиндексирован
  отдельной базой `support` (третья база RAG, `--rag support`).
- Обращения и пользователи — локальный JSON `support-mcp/data/`, доступный **через MCP**:
  это тот вариант задания, где «CRM» — файл, а сервер поддержки отдаёт его теми же
  инструментами, какими отдавала бы удалённая система.
- Данные обращения кладёт в промпт код (`dsh-term/lib/support.mjs`), а не модель: цитаты в
  ответе должны быть дословными. Промпт режима проверяется тестом `--support-check`.
- После ответа агент заводит задачу в очередь `INFRA` трекера: у задач нет поля тегов,
  поэтому тег `DSH-TERM` живёт в префиксе заголовка `[DSH-TERM] …`.
- MCP-сервер поддержки по умолчанию только для чтения (`--readwrite` включает запись
  комментария в тикет).

## Факты окружения (проверено)

- Репозиторий: `Vladislav-Zyuzko/ai-challenge` (публичный); remote origin — HTTPS
- Авторизация: `gh` (GitHub CLI) в keyring; `git push` идёт через gh-credential-helper
- Модель веток: `main → develop → feature/weekN → weekN/dayM`
- Правила ниже обязательны и для `/publish-day`, и для `/publish-week`, и для ручных просьб «оформи коммит / запушь / открой PR»

## Правила (обязательные)

1. Прямой push — только в ветку дня `weekN/dayM`.
2. PR всегда `day → feature/weekN`; `feature/weekN → develop` и `develop → main` — только по явной просьбе.
3. Merge делает только пользователь или по его явной команде.
4. Force-push запрещён.
5. Коммит = одна логическая единица; заголовок `тип(область): смысловое описание` (Conventional Commits, русский ок).
6. PR описывается: что сделано (по файлам), зачем, как проверить.

## Как добавить скилл

1. Создай `SKILLS/<имя>.md` с рецептом (предусловия → шаги → правила). Для скилла-роли
   опиши отдельно: что делает команда детерминированно и что делает агент.
2. Добавь команду в `COMMANDS` в `dsh-term.mjs` и обработчик в `handleCommand`.
3. Внеси строку в таблицу выше.
