# Рекомендации: минимальная подстрока, содержащая все символы `t`

## 1. Алгоритм: скользящее окно с инвариантным счётчиком

Классика «Minimum Window Substring» (LeetCode 76) решается двумя указателями за один проход:

- **Правый указатель** расширяет окно, добавляя символы `s[right]`, пока окно не станет «валидным» (содержит все символы `t` с учётом кратности).
- Как только окно валидно, **левый указатель** сжимает его: пытаемся выкинуть `s[left]` и каждый раз фиксируем кандидата, пока окно не перестанет быть валидным.
- Далее снова расширяем правый. Ни один указатель не откатывается назад.

**Ключевая идея** — не пересчитывать валидность окна заново на каждой итерации (это дало бы O(n·k)), а поддерживать один инвариант:

> `formed` = число **различных** символов из `t`, для которых текущее окно уже содержит требуемое количество (включая повторы).

Валидность окна — это просто `formed == need.length` (число различных символов в `t`). Проверка становится O(1).

Правило обновления `formed`:

- при добавлении символа справа: если `have[c]` **достиг** `need[c]` (было меньше — стало равно), `formed++`;
- при удалении слева: если `have[c]` **упал ниже** `need[c]` (было равно — стало меньше), `formed--`.

Оба правила срабатывают ровно в момент пересечения порога — это и есть учёт кратности. Символы, которых нет в `t`, на `formed` не влияют вообще.

## 2. Структура кода

Одна чистая функция + опциональный `main()` с тремя примерами из условия:

```dart
String minWindow(String s, String t) {
  // ранние выходы: t пустая / t длиннее s (сразу "");
  // если словарь t пуст — тоже сразу "".
  // дальше: два указателя, два счётчика, best-индексы, в конце один substring.
}
```

Внутри не должно быть вспомогательных «проверок валидности» — вся логика живёт в цикле расширения и вложенном цикле сжатия.

## 3. Структуры данных

- **Два счётчика частот**: `Map<int, int>` (или `Map<String, int>`).
- Итоговую подстроку **не хранить строкой на каждом шаге** — хранить пару индексов `bestL`, `bestR` (длина `bestR - bestL + 1`), а `s.substring(...)` вызвать **один раз в конце**. `substring` в Dart копирует, и порт «нарезай строку в цикле» из Python превращается в O(n²) аллокаций.
- Сравнение кандидатов — по длине; при равенстве допустим любой, значит обновляем best только при строго меньшей длине.

Почему ключ лучше делать `int` (code unit), а не `String`: `s[i]` в Dart возвращает **один UTF-16 code unit как новую строку** — каждый вызов аллоцирует. Итерация по `s.codeUnits` даёт `int` без аллокаций на символ, и map на `int`-ключах быстрее и компактнее, чем на строках.

## 4. Сложность

- **Время: O(|s| + |t|)** — правый указатель проходит `s` один раз, левый суммарно тоже не более |s| шагов; построение словаря `t` — O(|t|). Каждая операция с map амортизированно O(1).
- **Память: O(|t|)** на словарь требований (окно-словарь в худшем случае тоже O(|s|), но обычно ограничен алфавитом).

Никакого вложенного перебора окна — иначе квадрат.

## 5. Подводные камни именно в Dart

1. **`s[i]` ≠ «символ» в общем случае.** Это один UTF-16 code unit. Для BMP-алфавитов (латиница, кириллица, цифры) всё корректно, но эмодзи и редкие символы — это сюррогатные пары: индексы и счётчики по code units разъедутся с реальными символами, а `substring`, разорвавший пару, вернёт строку с непарным суррогатом. Решения: (а) зафиксировать допущение «ASCII/BMP» в комментарии; (б) если важна полная Unicode-корректность — один раз сконвертировать в список code points: `s.runes.toList()` и работать с ним. Для джаджей вида «A–Z, a–z» достаточно code units, но о решении нужно сказать явно.
2. **Учёт кратности** — самая частая ошибка. Не «встретил символ из t», а «накопил столько же, сколько в t». Отсюда и пороговые `++/--` у `formed`, а не пересчёт.
3. **Null-safety**: инкременты через `(map[k] ?? 0) + 1`; проверки `have[c] >= need[c]` — только если `need` вообще содержит `c` (иначе `null >= x` — ошибка компиляции/типов).
4. **Граничные случаи** — определи поведение явно и покрой тестами: пустой `t` (я бы возвращал `""`), `t.length > s.length` (сразу `""`), совпадение «весь `s` — ответ», символы `t`, которых нет в `s` вообще (быстрый ранний выход после построения словаря), дубликаты (`s = "aab"`, `t = "aa"` → `"aa"`), ответ в самом хвосте строки.
5. **Не оптимизируй раньше времени** без алфавитной оговорки: вариант с `List<int>` фиксированного размера (под `'z' - 'A' + 1`) быстрее map, но молча ломается на символах вне диапазона. Map — безопасный выбор по умолчанию.
6. Порядок вложенных циклов: внутренний `while` по левому указателю обязан идти **после** проверки валидности и фиксации кандидата — типичная ошибка «сжать до невалидного и только потом записать ответ», из-за которой теряется минимальное окно.

## 6. Проверка

Минимум — три примера из условия (`BANC`, `a`, `""`). Стоит добавить: `s="aab", t="aa"` (дубликаты), `s="abc", t="abcd"` (нет решения), `s="bba", t="ab"` (ответ в конце — `"ba"`), `s="ADOBECODEBANC", t="AABC"` (двойная `A`). Можно прогнать сверку с наивным брутфорсом (все подстроки, проверка счётчиками) на случайных коротких строках — это ловит ошибки порогов за минуту.

Резюме: два указателя вперёд + два словаря + один счётчик `formed` как инвариант валидности, индексы вместо нарезки строк, решение по code units с задокументированной оговоркой про Unicode, O(|s|+|t|).
