# Day 18 — MCP-инструмент с отложенным и периодическим выполнением

Задание: сделать MCP-инструмент, который **сохраняет данные** (JSON/SQLite), **выполняется по
расписанию** и **возвращает агрегированный результат**. Результат задания — агент, который
работает 24/7 и периодически выдаёт сводку.

Выбранная задача: **SLNexus** (Telegram-бот над Claude Code, проект `sl-claude-box`) дважды в сутки
присылает сводку по задачам, которые прямо сейчас в работе, на ревью или на тестировании —
с исполнителем, кратким описанием и признаком обсуждения в комментариях. Утром — с пожеланием
хорошего дня, вечером — хорошего вечера.

## 1. Как получилось, что день закрыт RFC, а не кодом

Сначала я разведал сервер в поисках «где это вообще может крутиться 24/7». Оказалось, что контур
уже есть: на том же VPS рядом с трекером живёт `/opt/sl-claude-box` — `claude-worker` (Claude Code
+ gh + sshd) и `telegram-bot` (SLNexus, опрос Telegram каждые 10 с), оба Up 6 дней. То есть
и планировщик-носитель, и канал доставки, и LLM уже подняты — не нужно ни нового сервера, ни cron.

Дальше выяснилось главное: **`/opt/sl-claude-box` — не git-репозиторий**, а набор файлов, и прод
ушёл от ветки `develop` на **822 строки** (в одном `bot.py` — +613; в репозитории `README.md`
пустой, на сервере — 93 строки; ещё пять файлов есть только на сервере). В `sl-claude-box` работает
свой Claude-харнесс, и **у него на руках эти локальные правки**.

Поэтому роли разделили: с меня — разведка и спецификация (RFC в PR), реализация — на их стороне,
на актуальной базе. Писать код поверх `develop` значило бы конфликт с реальным состоянием и потерю
чужих правок.

## 2. Что нашлось в разведке

| Находка | Значение |
|---|---|
| 24/7-контур уже существует | `claude-worker` + `telegram-bot` в `/opt/sl-claude-box` (compose-проект `sl-claude-box`, Up 6 дней) |
| Планировщик | в боте его **нет**: ни cron, ни APScheduler, ни фоновой таски по времени; `run_polling` с `concurrent_updates=False` |
| Адресаты | только `ALLOWED_USER_IDS` из env (3 человека), хранилища подписчиков нет |
| HTTP-клиента в боте нет вообще | весь внешний I/O — SSH (`asyncssh`) и Telegram; `requests` в зависимостях есть, но не используется |
| Утечка секрета | бот логирует каждый `getUpdates` вместе с URL, а в URL — токен бота: он лежит в логах контейнера |
| MCP Tasks | в SDK 1.30.1 экспериментальный механизм Tasks есть (`registerToolTask`, `TaskStore`, `tasks/get\|list\|cancel\|result`), но наш клиент его не объявляет: `@deepseek-ai/dsh-mcp-client` инициализируется с пустыми `capabilities` — опора только на обычные инструменты |
| Метрики хоста из контейнера | не видны (проверять нечего) — этот источник данных отброшен сразу |

## 3. Что именно специфицировано

**Архитектура (рекомендованный вариант).** Отдельный сервис `digest-mcp` в compose-проекте
`sl-claude-box`: он же владеет расписанием (08:00/20:00 Asia/Omsk), хранением снимков (JSON +
JSONL на томе) и агрегацией, и он же рассылает сообщения тем же `TELEGRAM_BOT_TOKEN`. Это не
конфликтует с ботом: Telegram запрещает два поллера `getUpdates`, а `sendMessage` может вызывать
кто угодно. В `bot.py` добавляется только команда `/digest` — ручной прогон. Запасной вариант
(всё внутри бота + тонкая stdio-обёртка) описан, но по форме он слабее соответствует заданию.

**MCP-инструменты:** `digest_preview` (агрегат + готовый текст, без отправки), `digest_run`
(собрать сейчас, при `send=true` — разослать), `digest_history` (снимки и дельты), `schedule_list`,
`schedule_set`, `status`. Транспорты — Streamable HTTP внутри compose-сети (порт наружу не
публикуется) и stdio; авторизация bearer-токеном; никакой зависимости от харнесса.

**Контракт с трекером** проверен запросами на прод и зафиксирован с формами ответов:
`GET /api/projects/{slug}/queues`, `GET /api/queues/{key}/statuses`,
`GET /api/queues/{key}/issues?status=in_progress,review,testing`,
`GET /api/issues/{key}`, `GET /api/issues/{key}/comments?limit=1`, `GET /api/me`.

Три вещи, которые эти запросы выявили и которые иначе стоили бы отладки на месте:

- в списке задач `assignee` — **объект** `{id, displayName, avatarUrl}`, имя исполнителя есть сразу;
- `description` в списке **отсутствует** — краткое описание добирается отдельным
  `GET /api/issues/{key}` на каждую задачу, отсюда лимит `NEXUS_DIGEST_MAX_TASKS=30`;
- у статусов `review` и `testing` категория `in_progress`, поэтому фильтровать надо по `key`,
  а не по `category`.

**Расписание.** Слоты из env, таймзона `Asia/Omsk`; `zoneinfo` в образе работает (проверено),
летнего времени в Омске нет. Идемпотентность через `last_sent` по слоту за дату (перезапуск
в тот же слот не должен слать второй раз), добор опоздавших слотов в пределах часа.

**Формат сообщения.** `parse_mode="HTML"` с обязательным `html.escape` на всех значениях из API,
разбивка длинного текста по 4000 символов, группировка по очередям, живые пометки вместо пустых
полей («исполнитель не назначен», «обсуждений пока нет»), разные приветствия и пожелания для утра
и вечера. Опциональная доводка текста через воркер (`NEXUS_DIGEST_LLM=1`) — с обязательным
фолбэком на шаблон, потому что у воркера один слот задач (`_is_busy()`).

**Приёмка** — десять проверяемых критериев (A1–A10): от расчёта слота на фиксированном времени
до отсутствия токенов в логах, включая перезапуск контейнера, недоступный трекер и вызов
инструментов сторонним MCP-клиентом.

## 4. Найденные проблемы, которые важнее самой задачи

1. **Репозиторий не соответствует проду.** 822 строки живого кода не в git: правки 18 сентября
   делали прямо на сервере. `README.md` в `develop` пустой. Пока это не сведено, любой PR в этот
   репозиторий рискует конфликтом или потерей чужой работы — поэтому синхронизацию предложено
   сделать отдельным PR.
2. **Токен бота утекает в логи.** Из-за `logging.basicConfig(level=INFO)` httpx печатает URL
   `getUpdates` вместе с токеном. В RFC это отдельный пункт с двумя действиями: понизить уровень
   `httpx` до WARNING (и сделать это **до** добавления HTTP-клиента, иначе дайджест добавит ещё
   один такой поток) и перевыпустить токен у BotFather.
3. **Экспериментальные MCP Tasks нам недоступны.** Механизм в SDK есть, но клиент харнесса
   объявляет пустые `capabilities`, то есть task-хэндлы не опрашивает. Вывод зафиксирован в RFC:
   планировщик делаем свой, Tasks — только как совместимость для других клиентов.

## 6. Стык с их реализацией: что пришлось добавить в наш MCP-сервер

Их харнесс реализовал дайджест в `digest-mcp/` (коммит `50997e6` в `develop`) и, что важно,
взял данные **не из REST API трекера, а из нашего MCP-сервера из дня 17** — сознательно, чтобы
не писать второй клиент к трекеру. Свой выбор они объяснили прямо в коде: «имена инструментов
и форма их ответа принадлежат `sl-tracker-mcp`, а не нам». Поэтому они сделали терпимый парсер
ответов и переменную `SL_TRACKER_TOOLS` для переопределения имён.

Но их `tracker.py` ждал четыре инструмента, а у нас было два из них — и с другими именами:

| Ждёт их код | Было у нас | Стало |
|---|---|---|
| `list_queues(project)` | `list_queues()` без аргументов, structured как карта по слагам | `list_queues(project?)`, structured `{items:[{project,key,name}], projects:{…}}` |
| `list_issues(queue, status, limit)` | — | **добавлен** |
| `get_issue(key)` | `get_task(key)` | без изменений, лечится `SL_TRACKER_TOOLS` |
| `list_comments(key, limit)` | — | **добавлен** |

Заодно была тихая мина: наш `list_queues` отдавал карту `{"sweet-limit":[…]}` — их `_rows()`
не находит в такой форме ключ `items`/`queues`/…, считает весь объект одной строкой, не видит
`key` и возвращает пустой список очередей. То есть дайджест молча приходил бы пустым. Плоский
`items` это закрывает.

Что сделано в `sl-tracker-mcp`:

- `list_issues(queue, status?, limit?)` → `GET /api/queues/{key}/issues`, структурой
  `{queue, statuses, total, items:[…]}`; статус можно задать и ключом (`in_progress,review`),
  и именем («В работе») — как в `set_task_status`;
- `list_comments(key, limit?)` → `GET /api/issues/{key}/comments` с `total` (признак обсуждения)
  и последним комментарием;
- `list_queues(project?)` — плоский `items` рядом с прежней картой, чтобы ничего не сломать;
- тесты: 35 → **37** (новые — на фильтр по статусам, на имена статусов, на `total` комментариев),
  `typecheck` и `build` чистые; стенд трекера научился отдавать список задач.

Выкат: код синхронизирован в `/opt/sl-tracker-mcp` (бэкап `mcp-backup-2026-09-25-0252.tgz`),
образ пересобран, контейнер `sl-tracker-mcp-1` — `Up (healthy)`, в логах
`MCP-сервер слушает {"mode":"stateless","readonly":false,"allowedQueues":"INFRA,MOBILE"}`.

Проверка — их же путём: из контейнера `telegram-bot` (та же compose-сеть, что у `nexus-digest`),
по публичному адресу, с разбором ответа **копией их парсера**:

```
tools/list: 8 -> add_comment, create_task, get_task, list_comments, list_issues,
                list_queues, set_task_status, update_task_description
list_queues(project=sweet-limit): 2 -> [('MOBILE', 'Flutter задачи'),
                                       ('INFRA', 'Инфраструктурные задачи')]
list_issues(INFRA, in_progress,review,testing): total 1, строк 1
    INFRA-4 | Проверка MCP-сервера | статус in_progress «В работе»
    | исполнитель None | приоритет 50 | описания в строке нет (добирается get_task)
list_comments(INFRA-4): total 1 | последний автор zyuzko2002 | текст: Мост работает…
```

Итоговый блок для их `.env`:

```ini
SL_TRACKER_MCP_URL=https://mcp.72-56-41-79.sslip.io:8443/mcp
SL_TRACKER_MCP_TOKEN=<MCP_CLIENT_TOKEN, 64 hex>
SL_TRACKER_TOOLS={"issue":"get_task"}
```

Переопределять нужно только одно имя: `queues`, `issues`, `comments` теперь совпадают
с их значениями по умолчанию.

## 8. Честный статус

- Спецификация и её стык с реальностью закрыты: MCP-сервер дайджеста **написан их харнессом**
  (`digest-mcp/`, коммит `50997e6`), наш `sl-tracker-mcp` расширен до 8 инструментов и выкачен
  в прод, путь дайджеста проверен на боевом трекере.
- **Осталось заполнить три переменные** в `/opt/sl-claude-box/.env` и запустить сервис
  `nexus-digest` — значения готовы и приведены выше. После запуска имеет смысл прогнать
  критерии приёмки A1–A10 из RFC (расчёт слота, отсутствие отправки дважды, пустой список,
  недоступный трекер).
- Не сделано сознательно: метрики сервера (из контейнера не видны), синхронизация `develop`
  с продом (отдельный PR), перевыпуск токена бота у BotFather (нужно действие владельца),
  добавление блока в `.env.example` их репозитория (сейчас переменные есть только в compose).
