# Скилл: create-project (команда `/create-project`)

Запускает **текущую сессию как архитектора проекта**: сессия с пользователем →
первородные артефакты `.project-harness` → гейт инструментов → тело проекта →
ноды → реализация до состояния «инструмент». Умеет **возобновлять** прерванную работу
по репортам вместо того, чтобы начинать заново.

Скилл состоит из двух частей:

| Часть | Кто исполняет | Что делает |
|---|---|---|
| Детерминированная | команда `/create-project` в dsh-term | разбирает путь, проверяет наличие `.dsh/.harness`, сканирует `.project-harness` и печатает состояние (этап и следующая роль по шапкам отчётов), собирает промпт архитектора и запускает ход |
| Творческая | агент (архитектор проекта) | ведёт сессию с пользователем, пишет артефакты, проходит гейт инструментов, планирует, создаёт и запускает ноды |

## Предусловия

- Работаем внутри репозитория, где есть процедурный харнесс `.dsh/.harness/`
  (иначе команда сообщит об ошибке и ничего не сделает).
- Путь вложенного проекта: `.project-harness` создаётся **внутри проекта**, например
  `<path>/calculator/.project-harness/` — а не в корне репозитория.
- Пользователь готов к сессии вопросов (архитектор спрашивает о продукте, а не о технике).

## Шаги команды (детерминированно)

1. `dsh-term /create-project <path>` — путь можно не указывать, тогда команда спросит.
2. Команда проверяет `.dsh/.harness/README.md` и создаёт `<path>`, если его нет.
3. Определяет режим:
   - `<path>/.project-harness/` нет → **NEW**;
   - есть → **RESUME**.
4. Сканирует `<path>/.project-harness/` и печатает сводку: какие узлы есть, какие отчёты
   заполнены, какой этап последний, кто следующая роль, версии контракта и харнесса.
5. Собирает промпт: текст этого скилла + `.dsh/.harness/agents/project-architect.md`
   + сводка состояния и путь, и запускает ход.
6. `/create-project <path> --check` — только шаги 1–4, без запуска сессии
   (посмотреть, где остановились, не тратя токены).

## Что делает архитектор

### Шаг A. Прочитать правила

`.dsh/.harness/agents/project-architect.md` (роль), затем
`.dsh/.harness/product-rules/project.md`, `node.md`, `state-machine.md`, `glossary.md`.
Всё, что пишется в узлы, — по этим правилам; термины — по глоссарию.

### Шаг B. Режим RESUME (если сводка показала незавершённую работу)

1. Определить точку остановки **по репортам**, не по догадкам: последний заполненный
   отчёт узла и его шапка (`Этап / Статус / Следующая роль / contract_version /
   harness_version / Дата`).
2. Показать пользователю короткую сводку: «остановились на <узел>, этап <этап>,
   следующий шаг — <роль>, ожидаемое действие <…>» и спросить: продолжить, пересмотреть
   план или откатиться на предыдущий этап.
3. При противоречиях в отчётах (например, `realization-report` в работе, а
   `planning-report` отсутствует) — **не угадывать**: назвать противоречие, предложить
   два варианта (достроить недостающий артефакт / откатиться) и зафиксировать решение
   в `acceptance-report.md` или `planning-report.md`.
4. При расхождении `harness_version` или `contract_version` (change propagation) —
   пометить зависимые узлы как `rework` и перепроверить их до продолжения.
5. Продолжить с того этапа, который указан следующей ролью.

### Шаг C. Режим NEW: сессия с пользователем

Собрать и записать (спрашивать пачками, предлагать дефолты, фиксировать предположения):

1. **Продукт и ценность**: что делает продукт, для кого, что считается успехом.
2. **Стек и среда** → инварианты (`I1…In`): язык, платформа, обязательные технологии,
   ограничения (например «iOS 15+», «без бэкенда», «офлайн обязателен»).
3. **Границы**: что не входит (out-of-scope) — обязательный раздел.
4. **Контракт**: что продукт обещает наружу: входы, выходы, поведение, интерфейсы.
5. **Критерии приёмки**: как поймём, что продукт готов (проверяемые утверждения).

Результат — файлы проекта:

```
<path>/.project-harness/
  product-rules.md          # назначение, контракт, инварианты I1…In, область и out-of-scope
  product-rules-index.md    # карта спеки: краткое описание → ссылка
  tools-rules.md            # инструменты: зачем, правила, предусловия
  make-rules.md             # план (пишется на шаге E)
  nodes/                    # дочерние узлы
  node-reports/specification-report.md
```

Шаблон `product-rules.md` (секции обязательны):

```markdown
# Product-rules: <название проекта>
## Назначение
## Контракт
## Инварианты
- I1: <проверяемое утверждение>
## Область и границы (out-of-scope)
## Критерии приёмки
## Предположения (не подтверждено пользователем)
```

### Шаг D. Гейт инструментов (работа не начинается, пока он не пройден)

1. Из инвариантов вывести список нужных внешних инструментов (flutter, dart, node, …).
2. Для каждого проверить `.dsh/.harness/tools-bank/<tool>-rules.md` и наличие
   предусловий (установлен ли инструмент, какая версия).
3. Если правил нет — **спросить пользователя**, выбрав вариант:
   - **A. Архитектор собирает правила сам** (изучает лучшие практики, пишет
     `<tool>-rules.md`, проверяет предусловия командой);
   - **B. Пользователь дополняет** `.dsh/.harness/tools-bank/` сам (архитектор ждёт).
4. Если правил нет ни у кого — зафиксировать `blocked` в
   `node-reports/specification-report.md` и **не начинать** тело проекта и ноды.
5. Готовые инструменты занести в `<path>/.project-harness/tools-rules.md` со ссылками
   на `.harness/tools-bank/...` и предусловиями.

### Шаг E. Тело проекта

Только после гейта: создать структуру проекта под стек **по правилам инструмента**
(`flutter create`, `dart create`, …), ничего не додумывая сверх правил. Зафиксировать
в `realization-report.md`: что создано, где лежит, какой проверкой подтверждено
(сборка/запуск).

### Шаг F. Планирование и ноды

1. `make-rules.md`: задачи с зависимостями, атомарность, рецепт и проверка для атомарных,
   исполнитель, бюджет, владение файлами, задача интеграции.
2. Критик проверяет план; возражения закрываются в `planning-report.md`.
3. Неатомарные задачи → дочерние узлы (`nodes/<слаг>-node/`) со своим срезом правил;
   атомарные → исполнителям.
4. Вести узлы по машине состояний (`state-machine.md`): реализация → верификация →
   приёмка → публикация `usage.md`.
5. Проект завершён, когда стал инструментом (принят и опубликован).

## Артефакты и шапки отчётов

Каждый отчёт начинается с шапки (по ней работает восстановление):

```markdown
Этап: спецификация | планирование | реализация | верификация | приёмка
Статус: в работе | завершён | провал | блокер
Следующая роль: архитектор узла | исполнители | тестировщик | родитель | —
contract_version: 0.1
harness_version: 0.1
Дата: ГГГГ-ММ-ДД
```

## Правила (обязательные)

1. Никакого кода и структуры проекта до спецификации и пройденного гейта инструментов.
2. Инварианты — только проверяемые; непроверяемое идёт в «предположения», а не в инварианты.
3. Out-of-scope обязателен: без него узлы расширяют задачу.
4. Продуктовые вопросы решает пользователь; архитектор предлагает варианты с ценой.
5. Изменение контракта или инвариантов — новая `contract_version` (change propagation).
6. История отчётов не перезаписывается; у каждого артефакта один писатель.
7. Возобновление работы — только по репортам; при противоречиях решение фиксируется
   письменно, а не «как-нибудь».

## Эскалации

| Причина | К кому | Формат |
|---|---|---|
| Нет правил нужного инструмента | пользователь | «A: соберу сам / B: дополнишь ты» + предусловия |
| Продуктовая развилка, ослабление инварианта | пользователь | варианты с ценой |
| Не хватает бюджета | пользователь / родительский узел | добить / урезать объём / разбить иначе / стоп |
| Противоречие в отчётах при возобновлении | пользователь | достроить / откатиться, с обоснованием |
