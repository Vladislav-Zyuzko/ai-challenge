# Аналитика: «Минимальная подстрока, содержащая все символы t»

## 1. Формальная постановка

Требуется найти **непрерывный** фрагмент `s[l..r]` минимальной длины такой, что для **каждого** символа `c` выполняется:

```
count_s[l..r](c) >= count_t(c)   для всех c
```

То есть окно должно содержать `t` как **мультимножество**: повторяющиеся символы учитываются по кратности. Это классическая задача «Minimum Window Substring» (LeetCode 76). Если такого окна нет — вернуть `""`.

Ключевые свойства задачи:
- Подстрока обязана быть **непрерывной** — ответ всегда является фрагментом исходного `s` (проверка обычно сверяет именно подстроку `s`, а не «набор букв»).
- Лишние символы внутри окна (не входящие в `t`) допустимы — окно может быть «засорено», важно лишь покрытие по кратностям.
- Минимум по **длине**; при равенстве длин разрешён любой ответ, что снимает требование детерминированного выбора при ничьей.

## 2. Неоднозначности условия (решение должно зафиксировать допущения)

В условии не оговорены несколько моментов, по которым тестирующая система может иметь конвенцию:

1. **`t` пустая.** Математически пустое мультимножество покрывается любым окном, включая пустое. Разумная и стандартная конвенция: `t.isEmpty` → сразу вернуть `""`. Рекомендую реализовать именно так (и зафиксировать в комментарии), но учесть, что если в тестах `t` гарантированно непустое, поведение неважно.
2. **`s` пустая** → `""`.
3. **Регистр.** Символы сравниваются как есть: `"A"` и `"a"` — разные. Никакого lowercasing делать не надо.
4. **Кодировка.** Если строки ASCII, любой подход тривиален. Для полноценного Unicode (суррогатные пары вне BMP) в Dart есть разница между code unit'ами и runes. Судя по примерам, тесты ASCII; Map-подход от кодировки не зависит, что безопаснее.

## 3. Граничные случаи, которые обязана пережить реализация

- `t.length > s.length` → `""`.
- В `t` есть символ, отсутствующий в `s` → `""` (например `s="a"`, `t="ab"`).
- Кратность важнее наличия: `s="a"`, `t="aa"` → `""` (пример 3); `s="aaab"`, `t="aa"` → `"aa"` (не `"a"` и не `"aaa"`… точнее минимум — `"aa"`).
- `s == t` → `s`.
- Искомое окно прижато к началу/концу `s` (левый/правый указатель доходит до границы).
- Все вхождения `t`-символов расположены в одном месте, окружённом мусором: `s="xxABCxxxxx"` → `"ABC"`.
- Окно содержит дубликаты лишних символов, при этом минимальное окно — не первое найденное: `s="ABC...BCA..."`. Ответ — глобальный минимум по всем `right`, а не первый валидный.
- Все символы одинаковые с перекосом кратностей: `s="aaaa"`, `t="aa"`.
- Полное совпадение без лишних символов и с лишними — сравнение длин должно давать предпочтение чистому окну.

## 4. Подходы и сложность

| Подход | Идея | Время | Память | Вердикт |
|---|---|---|---|---|
| Полный перебор | Все `O(n²)` подстроки, проверка покрытия заново | `O(n³)` (наивно) / `O(n²·|Σ|)` с префиксными счётчиками | `O(|Σ|)` | неприемлемо для длинного `s` |
| **Скользящее окно (two pointers) + частотные карты** | Расширяем `right`, пока окно не покроет `t`; затем сжимаем `left`, пока покрытие держится; фиксируем минимум | **`O(n + m)`** — каждый указатель проходит строку один раз | `O(|Σ|)`, где `|Σ|` ≤ размер алфавита | ✅ целевой подход |
| Бинарный поиск по длине + проверка | Ответ ищем по длине `L`, валидность окна длины `L` проверяем скользящим счётчиком | `O(n log n)` | `O(|Σ|)` | хуже, но возможен как запасной |
| Минимизация интервала по позициям | Для каждого символа — список позиций в `s`, слияние | сложнее и не быстрее | — | избыточно |

Скользящее окно — **оптимально по времени**: каждый символ `s` входит в окно и выходит из него не более одного раза, поэтому `O(n)` шагов с амортизированно константной работой на шаг. `O(n + m)` — асимптотический нижний предел, т.к. нужно хотя бы просмотреть обе строки.

## 5. Детали скользящего окна (две равносильные формулировки)

Общая структура одинакова:

```
need[c] = кратность c в t
счётчик окна have[c]
right идёт по s, добавляя символы в окно
как только окно валидно — пытаемся сдвигать left вправо,
   пока оно остаётся валидным, обновляя лучший ответ
```

**Вариант A — число «закрытых» символов (`formed`).** Считаем, сколько *различных* символов `t` уже набрали нужную кратность: `formed` увеличивается, когда `have[c]` достигает `need[c]`. Окно валидно, когда `formed == need.length`.

**Вариант B — суммарное число «полезных» вхождений (`matched`).** Инкрементируем `matched`, только если добавляемый символ ещё нужен (`have[c] < need[c]` до добавления). Валидно, когда `matched == t.length`. При сжатии слева `matched` декрементируется, если удаление ломает кратность.

Вариант A чуть чище отражает суть (не зависит от общей длины `t`); вариант B проще в реализации с одной картой. Оба корректны — важно не смешивать их логику.

**Инвариант и корректность.** Для каждого фиксированного `right` сжатие доводит окно до **минимального валидного, заканчивающегося в `right`**. Любое минимальное окно всей задачи заканчивается в некотором `right`, и в этот момент оно будет рассмотрено (когда `right` впервые его «закроет», `left` не сможет сдвинуться за его начало, не сломав валидность). Значит, глобальный минимум не пропускается. Ответ обновлять только на валидных окнах после фазы сжатия (или во время неё), по критерию «длина меньше текущего минимума» (при равенстве — не перезаписывать, любая допустима).

## 6. Что обязательно должно учитывать итоговое решение (чек-лист)

1. **Хранить индексы, а не срезы.** Если на каждой итерации делать `s.substring(...)`, суммарно накопится `O(n²)` копирования. Правильно: запоминать `bestLeft`/`bestRight` и сделать один `s.substring(bestLeft, bestRight)` в конце.
2. **Точная сигнатура** `String minWindow(String s, String t)` — проверка, вероятно, вызывает функцию по имени; имя и арность менять нельзя.
3. **Кратность символов `t`** — карта `need` строится из `t`, а не множество уникальных символов.
4. **Условие валидности окна** — покрытие по всем `need[c]`, а не просто «встретил все символы из t хоть раз».
5. **Случаи `t.isEmpty`, `s.isEmpty`**, символ из `t` не найден в `s` → `""`.
6. **Обновление ответа** — только если окно валидно и короче текущего рекорда; инициализировать рекорд «бесконечностью» (`s.length + 1` или `null`).
7. **Не мутировать входные строки**, функция чистая.
8. **Совместимость с алфавитом.** `Map<String,int>` (или `Map<int,int>` по code unit) универсален. Если хочется максимальной скорости и алфавит заведомо ASCII — подойдёт `List<int>` на 128/256 ячеек с индексом `codeUnitAt`, но это оптимизация с допущением о кодировке, а не требование. Для ожидаемых ограничений по входным данным (даже `n` порядка 10⁵–10⁶) Map-решения `O(n+m)` достаточно.

Иллюстрация (фрагмент идеи, не решение): окно расширяется и сжимается только через пары указателей, вся работа с кратностями — через инкремент/декремент счётчиков при входе/выходе символа:

```dart
// need: кратности из t;  have: кратности в текущем окне [left, right)
// при добавлении s[right]:  have[s[right]]++;   при удалении s[left]: have[s[left]]--
// валидность поддерживается счётчиком закрытых/полезных символов (см. A/B)
```

## 7. Дополнительные рекомендации

- **Считывание по одному символу:** в Dart индексация по строке `s[i]` работает за константу для BMP-символов; для ASCII этого достаточно. Если вдруг появятся символы вне BMP, корректнее итерировать по code units и работать с ними как с ключами — тогда «символ» однозначен и Map не путается.
- **Не использовать рекурсию/дорогие структуры** в горячем цикле — только счётчики и два указателя, без вложенных циклов по `t` внутри шага.
- **Проверка на примерах обязательна**, но недостаточна: примеры из условия не покрывают кратности (`t="aa"`), недостающие символы и окна у границ. Стоит прогнать мини-набор: `("ADOBECODEBANC","ABC")→"BANC"`, `("a","a")→"a"`, `("a","aa")→""`, `("aaab","aa")→"aa"`, `("xxABCxx","ABC")→"ABC"`, `("abc","")→""`, `("a","b")→""`, `("ADOBECODEBANC","AABC")→"ADOBECODEBA"` (или `"CODEBANC"`… точный ожидаемый вариант — любой корректный минимум), `s==t`.
- Если тестирующая система генерирует случайные большие строки, неоптимальное решение рискует упасть по времени — закладываться на `O(n+m)`.

## 8. Итоговое резюме

Единственный подход, который стоит реализовывать, — **скользящее окно с двумя указателями и частотными картами** за `O(n+m)` по времени и `O(|Σ|)` по памяти. Основные источники ошибок — не учёт кратности, срезы в цикле (квадратичная деградация), обновление ответа на невалидных окнах, и незакрытые конвенции для пустого `t`. Корректная реализация при этом укладывается в десяток-полтора строк основного цикла; ничего сверхъестественного задача не требует, но аккуратность с инвариантом «сжатие до минимального валидного окна для каждого `right`» — решающий фактор.
