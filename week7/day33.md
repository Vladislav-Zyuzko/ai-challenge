# День 33. Мини-сервис поддержки пользователей

Задание: сервис, который отвечает на вопросы пользователей продукта, использует базу знаний
(FAQ/документацию), учитывает контекст пользователя и его обращений, а данные о пользователях
и тикетах берёт через MCP (CRM или JSON), и отвечает на вопрос вида «почему не работает
авторизация», опираясь на данные тикета.

Продукт в этом проекте — сам `dsh-term`, поэтому поддержка сделана для него: сессия `/support`
разбирает обращение из локального хранилища, отвечает по FAQ продукта и **заканчивает разбор
задачей в разработку** — в очередь `INFRA` трекера с тегом `[DSH-TERM]` в заголовке.

## 1. Что где

| Требование задания | Как закрыто |
|---|---|
| мини-сервис поддержки пользователей | команда `/support [<тикет>]` в dsh-term (плюс флаг `--support` для входа сразу в обращение) |
| отвечает на продуктовые вопросы | база FAQ продукта `support` (5 заметок + README продукта) → инструмент `rag_search`, ответы со ссылками и цитатами |
| использует базу знаний (FAQ/документация) | та же база: 5 заметок FAQ + `dsh-term/README.md`, проиндексированы пресетом `--support-docs`, 87 чанков |
| учитывает контекст пользователя и тикета | слепок обращения в системном промпте (кодом, из JSON) + MCP-инструменты `support_get_ticket` / `support_get_user` |
| данные через MCP (JSON) | свой MCP-сервер `support-mcp`: тикеты и пользователи из двух JSON-файлов, 4 инструмента только для чтения |
| «почему не работает авторизация» по данным тикета | сценарий `s-01`: обращение T-1042 ровно про это; ответ снимает ложный диагноз «авторизация» и цитирует переписку |
| **итог обращения — тикет в разработку** | `mcp__sltracker__create_task`: очередь `INFRA`, заголовок `[DSH-TERM] …`, описание «Откуда / Симптом / Диагноз / Что сделать / Как проверить» |

## 2. Как это работает

```
                  /support T-1042   (или dsh-term --support T-1042)
                          │
        ┌─────────────────┴──────────────────────────────────────────────┐
        │ детерминированная часть (dsh-term/lib/support.mjs)             │
        │  • tickets.json + users.json → слепок обращения                │
        │  • промпт режима: данные + правила ответа + правило задачи     │
        │  • подключить базу FAQ `support` и MCP `support` / `sltracker` │
        │  • перезаписать оверлеи (personaPrefix + mcp-client) → рестарт │
        └─────────────────┬──────────────────────────────────────────────┘
                          ▼
        сессия поддержки (обычный агент dsh-term)
          rag_search (база support) · mcp__support__*  ·  файлы, git-контекст
                          │
                          ▼
        ответ пользователю  ──▶  create_task(queue=INFRA, title="[DSH-TERM] …")
```

Почему данные обращения кладёт код, а не модель: ответ поддержки должен ссылаться на факты —
«у вас 0.9.4 на Windows 11», «в переписке адрес 4000», «вы писали это 14.10 в 09:12».
Пересказ таких фактов моделью стоит дорого проверять и теряет детали, поэтому слепок собирает
`supportDigest()` из JSON, а `--support-check` печатает ровно тот текст, который увидит модель.

## 3. Хранилище и MCP-сервер поддержки

`support-mcp/` — маленький проект на Python (MCP SDK) вокруг двух файлов:

```
support-mcp/data/users.json    u-101 Ирина Соколова (team, Windows 11, 0.9.4) … u-104 Артём Ковалёв
support-mcp/data/tickets.json  T-1042, T-1051, T-1058, T-1063, T-1070 (закрыт), T-1077
```

| Инструмент | Что отдаёт |
|---|---|
| `support_list_tickets(status)` | список обращений: номер, тема, пользователь, статус, число сообщений |
| `support_get_ticket(ticket_id)` | карточка: тема, теги, компонент, пользователь и вся переписка |
| `support_get_user(key)` | пользователь по id, почте или имени |
| `support_find_tickets(query)` | поиск по теме, тегам, компоненту и тексту переписки |
| `support_add_comment(ticket_id, text)` | комментарий в обращение — **только с `--readwrite`** |

Решения, которые оказались важны:

- **ошибки — текстом, а не исключением.** Нет обращения, нет пользователя, пустой запрос —
  инструмент возвращает объяснение с подсказкой («открытые: T-1042, T-1051, …»). Иначе модель
  видит падение инструмента и не может сказать пользователю причину;
- **чтение по умолчанию.** Запись в тикет включается флагом `--readwrite`: демонстрация не
  должна молча править данные, а сценарий «агент дополнил тикет» пока не нужен;
- **ответы текстом, а не JSON.** Агент читает их как есть: разбор структуры стоил бы токенов и
  ошибок.

Проверка соединения без сессии:

```powershell
node dsh-term/dsh-term.mjs --mcp-check support
#   соединение установлено (support · protocol OK · 1001 мс), инструментов: 4
#   ожидаемая добавка к промпту: ≈ 185 токенов на каждый запрос
```

Тот же сервер подключён пресетом `--mcp support`: `python -m support_mcp.server`, каталог
пакета едет в `PYTHONPATH`. Пресетов стало четыре (`github`, `sltracker`, `figma`, `support`).

## 4. FAQ продукта и третья база знаний

FAQ — то, что делает из «чат-бота» поддержку: без него ответы опираются на общие знания модели
про CLI, а не на поведение конкретной версии.

| Файл | О чём |
|---|---|
| `01-zapusk-i-klyuchi.md` | первый запуск, `/token`, `has no configured model`, `DSH_TERM_OLLAMA` |
| `02-lokalnaya-model.md` | локальная модель: маршрут, `--llm-check`, 40–60 с, 8B и инструменты, Q4/Q8 |
| `03-oshibki-i-limity.md` | 429 и `max_parallel_requests`, отсутствие `Retry-After`, `No connected db` |
| `04-mcp-i-bazy.md` | MCP-пресеты, тулсеты, цена в промпте, `--mcp-check`, `--rag`, `/help` vs `/rag-brief` |
| `05-komandy-i-seansy.md` | команды, сессии, `/publish-day` и ревью, цвет, сам режим `/support` |

База собирается существующим конвейером `doc-index` — добавлен только пресет корпуса:

```powershell
cd doc-index
python -m doc_index index --support-docs --vault .. --strategy structural
# [structural] чанков 87, посчитано 0, из кэша 87, 0.2 с
# индекс: support-index/out/index.db · support-index/out/index_structural.faiss
```

В `.dsh/rag.json` появилась четвёртая база (`support`, `out: support-index/out`, `minDense 0.45`).
Корпус — **6 файлов, 63 078 символов, 87 чанков**: пять заметок FAQ (11 793 символа) и
`dsh-term/README.md` продукта (51 285 — он и даёт основную массу чанков). `structural` выбран
потому, что FAQ — это markdown-заголовки, и вопрос «почему 429» должен попадать в раздел, а не
в соседний по номеру строки фрагмент. README продукта в корпусе не случайно: половина вопросов
пользователей — про флаги и команды, и ответ должен браться из документации продукта, а не из
общих знаний модели.

состав корпуса проверяем: `support-index/out/chunks_structural.json` перечисляет источники
чанков (сверено ревьювером — именно эта сверка и нашла лишний файл, см. раздел 9).

## 5. Режим `/support`

```
dsh> /support             # меню открытых обращений (пять из шести)
dsh> /support T-1042      # сразу в обращение
dsh> /support off         # выключить режим
```

```powershell
dsh-term --support T-1042                 # сессия начинается в режиме поддержки
dsh-term --support-check T-1042           # что уйдёт в системный промпт (без модели)
dsh-term --support T-1042 -p "вопрос"     # один ответ, без интерактивной сессии
```

Что делает команда детерминированно:

1. читает обращение и карточку пользователя, собирает слепок (номер, тема, статус, компонент,
   дата, пользователь, тариф, ОС, версия, заметки, теги, вся переписка дословно);
2. дописывает базу `support` к базам сессии — RAG-сервер один на все базы, поэтому он
   пересобирается целиком, а не добавляется вторым процессом;
3. добавляет MCP-серверы `support` и (если есть `SL_MCP_TOKEN`) `sltracker`; без токена режим
   не ломается — правило задачи переключается на текстовый вывод, и это сказано и в консоли,
   и в промпте;
4. перезаписывает оверлей системного промпта и перезапускает рантайм: `personaPrefix` и точки
   монтирования фиксируются при спавне;
5. печатает, что вошло в режим и что не удалось: FAQ, трекер, переписка, число сообщений.

Промпт режима — 3 234 символа (≈800 токенов) и три части: данные обращения, правила ответа,
правило задачи. Начало (реальный вывод `--support-check T-1042`):


## 6. Тикет в разработку: очередь `INFRA` + тег `[DSH-TERM]`

Требование «пусть после обращения агент формирует тикет в разработку» реализовано как
обязательный шаг после ответа:

```
mcp__sltracker__create_task(queue: "INFRA",
  title: "[DSH-TERM] <что починить, коротко>",
  description: <markdown по шаблону>)
```

У задач трекера **нет поля тегов** (`create_task(queue, title, description, status, priority)`),
поэтому тег живёт в префиксе заголовка — это записано и в промпте, и в скилле, чтобы модель не
пыталась искать несуществующее поле. Шаблон описания одинаков во всех задачах, поэтому их можно
сравнивать: «Откуда (обращение + пользователь) / Симптом (дословная формулировка) / Диагноз /
Что сделать / Как проверить».

Живые задачи из прогонов:

| Задача | Из обращения | Заголовок |
|---|---|---|
| `INFRA-5` | T-1042 | `[DSH-TERM] Старт падает с «provider "local" has no configured model» — ошибка не объясняет причину (DSH_TERM_OLLAMA и имена моделей маршрута)` |
| `INFRA-6` | T-1051 | `[DSH-TERM] 429 при локальной модели: нет Retry-After и повтора — сырой отказ вместо ожидания` |

Фрагмент `INFRA-6` из трекера (проверено `get_task`):

```
## Откуда
- обращение поддержки: T-1051 — «Ответы падают с 429 после третьего запроса»
- пользователь: Артём Ковалёв <a.kovalev@example.ru> · тариф solo · Windows 11 · dsh-term 0.9.4

## Диагноз
Дефекта в модели нет: локальный провайдер ходит в Ollama через сервисный слой (LiteLLM), поэтому
действуют лимиты сервиса — `rpm` и лимит параллелизма (`max_parallel_requests`); FAQ
support/faq/03-oshibki-i-limity.md, строки 2–13. …
Проблема UX: LiteLLM без базы не отдаёт `Retry-After` (тот же файл, строки 14–19), и dsh-term
показывает пользователю сырой 429 без паузы и автоповтора…
```

Задача создаётся, только если обращение выявило дефект или пробел; для чистого «как
пользоваться» агент пишет строкой «Задача в разработку: не требуется — причина». Обе живые
задачи — про дефекты, и в обеих первая галочка плана действий действительно про продукт
(сообщение об ошибке и повтор при 429), а не про окружение пользователя.

- **s-08** — ответ за 17 с без единого поиска: «dsh-term: 0.9.4 · ОС: Windows 11 · С нами:

Первый прогон дал **7/9**: два сценария не прошли, и оба раза причина была разная.

| Что | Разбор |
|---|---|
| s-01 «снят ложный диагноз» | моя ошибка в проверке: модель написала «Это не авторизация… Ключ… к ошибке не относится», а регулярка ждала «не проблема авторизации». Формулировка модели шире моего шаблона — расширил проверку, ответ не менялся |
| s-07 «запрошены данные» | **настоящая находка**: на вопрос про код `X-77` агент отвечал про тему обращения (падающий старт), а не про сам вопрос. Правило 4 переписано: «скажи это прямо, первой строкой… не подменяй вопрос темой обращения»; после правки — 2/2, и ответ начинается словами «в базе и в обращении этого нет» |

Ещё наблюдение из прогона: на s-07 агент сделал `grep` по репозиторию, нашёл строку `X-77` в
файле сценариев и прочитал его. Вреда не было (там только вопрос), но это значит, что
**сценарии оценки лучше держать вне рабочей папки агента** — иначе он может увидеть ожидаемые
признаки.

Один настоящий баг в существующем коде нашёлся именно этой задачей. В режиме поддержки в
сессии оказываются **два** stdio-сервера (RAG и поддержка), и оверлей `mcpPatchYaml` писал блок
`env:` один раз на весь файл: у второго сервера `PYTHONPATH` уезжал в `args`, харнесс падал на
`bad indentation of a mapping entry`, рантайм не поднимался вовсе. До этого в сессии никогда не
бывало двух stdio-серверов с `env`, поэтому баг не проявлялся. Исправлено (свой `env:` на
каждый сервер) и закрыто тестом на два сервера в одном оверлее.

## 10. Ограничения

- **Модель облачная.** Локальная 8B для поддержки не годится: замеры дня 31 — 22 факта из 36 и
  выдуманные ссылки, а ответ поддержки без точных ссылок бесполезен. Переключается `--model`.
- **Тикетов в хранилище шесть, и они фикстуры.** Это демонстрация контракта «данные → MCP →
  промпт → ответ → задача», а не боевая поддержка: нет истории изменений, вложений, SLA, оценки
  качества ответа и обратной связи пользователя.
- **Запись в обращение не включена.** `support_add_comment` есть, но режим читающий: агент не
  дописывает итог в тикет, а переносит его в задачу разработки.
- **Режим перезапускает рантайм** (иначе не сменить системный промпт) — вход в `/support` стоит
  ~1 с и обрывает текущий ход, если он был.
- **`SL_MCP_TOKEN` берётся из окружения.** Без него режим работает в текстовом варианте задачи;
  токен ни в оверлеи, ни в файлы не попадает (`!!js`-выражение читает env рантайма).
- **Один тикет на сессию.** Смена обращения — `/support <номер>`, то есть новый слепок и снова
  рестарт; диалог «сначала T-1042, потом T-1051 в одной истории» не поддерживается.
- **Сценарии оценки видны агенту**: они лежат в рабочей папке, и на s-07 модель их прочитала.
  Для честной оценки их стоит выносить во временный каталог (вне `--workspace`).
- **Шум stderr от MCP-сервера.** FAISS печатает «Loading faiss…» в stderr python-сервера, и в
  `-p` он попадает в вывод рядом с ответом; на ответ не влияет, но парсить вывод мешает.

## 11. Итог

1. **Мини-сервис поддержки есть**: `/support [<тикет>|off]`, флаг `--support`, диагностика
   `--support-check` — режим собирается из трёх источников (данные обращения, FAQ продукта,
   трекер) и честно деградирует, если чего-то нет.
2. **Контекст пользователя и тикета учитывается** — слепок в системном промпте собирает код, а
   не модель; тест проверяет дословность переписки, версии и тегов.
3. **Данные приходят через MCP**: свой сервер `support-mcp` (JSON вместо CRM, чтение по
   умолчанию, ошибки текстом) плюс `sltracker` для задач.
4. **RAG работает**: база FAQ продукта (87 чанков), ответы со ссылкой на заметку и строками —
   это видно в каждом прогоне (`⛭ rag/rag_search base="support"`).
5. **После обращения создаётся задача в разработку**: очередь `INFRA`, тег `[DSH-TERM]` в
   префиксе заголовка (поля тегов у трекера нет), описание по шаблону; живой пример —
   `INFRA-5` и `INFRA-6`.
6. **Проверено живьём**: 11 сценариев, 9 из 9 продуктовых и 2 с трекером; прогон нашёл
   настоящий дефект промпта (подмена вопроса темой обращения) и настоящий баг оверлея.
7. **Тесты**: 78 проверок режима, 18 проверок MCP-сервера, 247 тестов `doc-index` — плюс все
   прежние наборы dsh-term зелёные.
