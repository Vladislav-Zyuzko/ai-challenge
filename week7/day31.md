# День 31. Ассистент разработчика

Задание: подключить RAG к документации своего проекта (README, `docs`, описания схем и API),
связать ассистента с проектом через MCP (минимум — текущая git-ветка) и сделать команду
`/help`, которая отвечает на вопросы о структуре проекта по документации и контексту.

Собрано на том, что уже есть в репозитории: индекс `doc-index` (дни 21–24) и `dsh-term`
(дни 25–30). Нового кода — минимум; новое здесь в том, **что** индексируется и **откуда**
ассистент берёт текущее состояние проекта.

## 1. Как устроен ассистент

```
вопрос «/help …» ──▶ dsh-term
                       │
                       ├── MCP-сервер doc-index:  rag_search, rag_bases,
                       │                          git_branch, git_status,
                       │                          git_diff, project_files
                       │
                       └── строгий путь (мимо агента): doc_index brief
                             ├── фрагменты документации проекта (RAG)
                             ├── живой контекст git (ветка, HEAD, изменения)
                             └── ответ по контракту + машинная проверка
```

Три решения, которые здесь стоит объяснить:

1. **`/help` идёт мимо агента.** Ответ собирается тем же строгим путём, что в дне 24:
   контекст и данные git вкладываются в промпт кодом, форма ответа гарантирована, источники
   и цитаты проверяются кодом. Причина та же, что в дне 26: локальная 8B-модель теряется
   среди двух десятков инструментов харнесса, а здесь выбирать инструменты не нужно.
2. **GitHub MCP не закрывает минимум задания.** Официальный remote-сервер (пресет
   `--mcp github`, день 16) знает ветки и PR **на GitHub**, но не рабочее дерево: какая ветка
   выкачана сейчас, что изменено, что не закоммичено — это локальные факты. Поэтому контекст
   проекта читается локальным git, а GitHub MCP остаётся полезным дополнением (вопросы про PR).
3. **Документация — корпус, код — нет.** Индексируются README, `docs`, отчёты по дням, правила
   и скиллы. Исходники описывают проект иначе, и поиск по ним отвечает на другие вопросы,
   добавляя шум: вопрос «как собрать индекс» должен приводить в README, а не в `indexer.py`.


## 3. MCP: ассистент получает контекст проекта

Наш MCP-сервер (`doc_index.mcp_server`) получил флаг `--repo` и четыре инструмента. Проверено
прямым опросом сервера по stdio — агент видит ровно шесть:

```
rag_search · rag_bases · git_branch · git_status · git_diff · project_files
```

| Инструмент | Что отдаёт |
|---|---|
| `git_branch` | ветка, HEAD, тема последнего коммита (минимум задания) |
| `git_status` | изменённые, новые и удалённые файлы рабочего дерева |
| `git_diff` | статистика изменений (полный diff с лимитом — отдельной функцией) |
| `project_files` | список файлов под контролем git, с фильтром по подстроке |

Безопасность: белый список read-only подкоманд (`rev-parse`, `status`, `diff`, `log`, `branch`,
`show`, `ls-files`), вызов без оболочки, проверка что каталог — репозиторий, обрезка вывода.
Инструменты регистрируются только при `--repo`: цена инструментов в промпте измерена в дне 16,
и лишние описания в обычной сессии с базой знаний не нужны.

## 4. Команда `/help`

Три режима в одной команде:

- `/help` — список команд (как раньше);
- `/help <команда>` — справка по команде (как раньше);
- `/help <вопрос>` — ответ по проекту: документация из базы плюс живой контекст git.

Двусмысленность разбора («`/help model` — это команда или вопрос про модель?») решена правилом
«аргумент совпал с именем команды → справка, иначе → вопрос», и в конце ответа печатается
подсказка, как запросить справку по команде.

В промпт данные git уходят отдельным блоком с правилом: вопросы о текущем состоянии разбирать
по нему и **не** добавлять блоки `ИСТОЧНИКИ` и `ЦИТАТЫ` — цитировать там нечего, а данные git
не являются фрагментом базы. Без этого правила строгий контракт заставлял модель отвечать
«Не знаю» на вопрос «какая сейчас ветка».

Пример реального ответа (сессия `dsh-term --rag project`):

```
## КОНТЕКСТ ПРОЕКТА
- ветка: week7/day31 · HEAD c36a836 · Merge pull request #28 …
- изменено файлов: 14
  - M .dsh/rag.json
  - M doc-index/doc_index/rag.py
  …
## ОТВЕТ
Работа идёт на ветке `week7/day31`, HEAD — коммит `c36a836` («Merge pull request #28 …»).
Не закоммичено 14 изменённых файлов: …
**Проверка:** источники 0/0 реальны · цитаты 0/0 дословны · выдуманных 0 · фрагментов 14
```

## 5. Проверка: 12 вопросов о проекте

документации (как собрать индекс, чем отличаются стратегии чанкинга, что делает `/rag-brief`,
как устроен сервис дня 30, что показало сравнение квантований, как подключить GitHub MCP,

| Ложных отказов | 0 | 1 |

Отдельно проверен вопрос о текущем состоянии («на какой ветке идёт работа и что не
закоммичено») — тот, ради которого вообще нужен git-контекст:

- **облачная модель:** ответила верно (ветка `week7/day31`, HEAD, список из 14 файлов),
  источников и цитат не добавляла, выдуманных ссылок 0;
- **локальная `qwen3:8b`:** ветку назвала верно, но всё равно построила блоки `ИСТОЧНИКИ` и
  `ЦИТАТЫ` и приписала строку из блока git случайно найденному фрагменту
  (`week2/day10.md`) — проверка честно показала «выдуманных 1». Усиление правила в промпте
  не помогло: модель продолжает следовать контракту дня 24 сильнее, чем добавленному правилу.

Вывод: **для вопросов о текущем состоянии локальная 8B пока не годится**, и это тот же вывод,
что в днях 26 и 29 — слабая модель не удерживает сложный контракт. Механика при этом работает:
подмена данных ловится, а не прощается.

## 6. Что нашлось и починено по дороге

| Что | Как выглядело | Починено |
|---|---|---|
| Каталог индекса и каталог пакета — одно поле | У базы проекта пакет `doc_index` живёт в `doc-index`, а индекс — в `project-index/out`; с одним полем поиск пошёл бы в чужой индекс, а CLI запускался бы не из того каталога | Поле `out` у базы (`--base-out`, `out` в реестре), `outDir` в параметрах CLI |
| MCP-сервер запускался без `--repo` | Инструменты проекта не регистрировались вовсе: агент не мог ответить даже про ветку | `dsh-term` передаёт рабочую папку сессии в `--repo` |
| Разбор `git status` съезжал на символ | `_git` срезал пробелы, а в porcelain первый символ — статус рабочего дерева: `README.md` превращался в `EADME.md` | Формат `-z` (NUL-разделитель) и разбор без обрезки |
| Кириллица в путях git | `git status` отдавал `"\320\275\320\276\320\262\321\213\320\271.md"` в кавычках | Тот же `-z`: git не квотирует пути в этом режиме |
| Скрытые каталоги целиком исключались | `.dsh/SKILLS/publish-day.md` — документация проекта, но путь начинается с точки | `allow_dirs` в настройках корпуса |
| Гигантские файлы в корпусе | `tokenizer.json` на 16 МБ попал бы в эмбеддинги | `max_file_bytes` и исключение `models/` |

## 7. Ограничения

- **Локальной 8B нельзя доверять строгий контракт с блоком git**: она приписывает данные git
  фрагментам базы (раздел 5). Механика проверки это ловит, но пользователю прилетает ответ
  с выдуманной ссылкой.
- **Порог отказа настроен на другом корпусе.** Пол `min_dense = 0.5` подобран в дне 23 на
  хранилище Obsidian; на документации проекта один законный вопрос (p05) получил отказ по
  порогу (лучшее совпадение 0.47). Нужен свой свип по этому набору — набор для него теперь есть.
- **Индекс устаревает.** Отчёты пишутся каждый день; сборка обновляется командой из раздела 2,
  но автоматики «обнови, если появились новые коммиты» нет.
- **Код в корпус не входит** — по замыслу; вопросы вида «в какой функции это реализовано»
  остаются за пределами ассистента.
- Судья-модель в прогоне не вызывалась (`--no-judge`): метрика смысла в таблице отсутствует.

3. **`/help` отвечает на вопросы о структуре**: 10 из 10 отвечаемых вопросов в строгом формате,

4. **Живой контекст работает**: вопрос о ветке и незакоммиченных изменениях решается данными
   git, а не поиском по документации — облачная модель отвечает верно и без выдуманных ссылок.
5. **Разница моделей измерена**: облачная покрывает 32 факта из 36 и не выдумывает источников;
   локальная — 22 из 36 и три ошибки в ссылках. Для ассистента разработчика локальная модель
   годится как демонстрация, но не как рабочий инструмент.
