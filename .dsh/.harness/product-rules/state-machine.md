# Машина состояний узла

Описывает этапы работы узла, переходы между ними и артефакт, которым заканчивается
каждый этап. Корневой узел проходит ту же машину; отличие только в том, что на этапе
спецификации его «родитель» — пользователь (в лице архитектора проекта).

## Схема

```
                    ┌──────────────────────────────────────────────┐
                    │                                              │
 [inception] ──► SPECIFIED ──► PLANNED ──► REALIZING ──► REALIZED ─┼─► VERIFIED ──► DONE
 (только корень)     │            │            ▲             │      │      │          │
                     │            │            │             │      │      │          ▼
                     │            │         rework           │   rework    │      [инструмент]
                     │            │            │             │      │      │      (usage.md)
                     │            ▼            └─────────────┴──────┘      │
                     │        [BLOCKED] ◄──── эскалация ──── любая точка ─┘
                     └──────────────► (возврат к спецификации при противоречии в правилах)
```

## Этапы

### 1. Спецификация

| | |
|---|---|
| **Вход** | родительский контракт и срез; для корня — запрос пользователя |
| **Кто** | архитектор-родитель (в корне — архитектор проекта вместе с пользователем) |
| **Что делает** | пишет `product-rules.md` узла: назначение, контракт, инварианты `I1…In`, область и out-of-scope, срез спеки; пишет `tools-rules.md`: нужные инструменты и их предусловия |
| **Выход** | `node-reports/specification-report.md` |
| **Критерий перехода** | контракт и инварианты зафиксированы; у каждого инструмента указаны предусловия; out-of-scope назван |
| **Дальше** | архитектор узла запускается **с чистым контекстом** (срез + отчёт) |

Контракт формирует родитель: узел не придумывает себе обещания. Если при планировании
выясняется, что контракт неполон или противоречив, — это возврат на спецификацию
(запрос родителю), а не самовольное расширение.

### 2. Планирование (и критика)

| | |
|---|---|
| **Вход** | `product-rules.md`, `tools-rules.md`, правила из `.harness/` |
| **Кто** | архитектор узла; затем — критик (отдельная сессия) |
| **Что делает** | архитектор составляет `make-rules.md`: задачи, зависимости (DAG), признак атомарности, рецепт и проверка для атомарных, исполнитель, бюджет, владение файлами, задача интеграции. Критик проверяет план и выдаёт нумерованные возражения с severity |
| **Выход** | `node-reports/planning-report.md` (план + возражения + как закрыты) |
| **Критерий перехода** | ни одного незакрытого `blocker`; продуктовые вопросы эскалированы и решены |
| **Дальше** | реализация (исполнители и/или дочерние узлы) |

Планирование — единственная точка, где запускается критик. Для мелких узлов (порог
задаётся родителем: например, ≤2 задачи и нет risk-флагов) критика может быть
пропущена, но тогда это явно отмечается в `planning-report.md`.

### 3. Реализация

| | |
|---|---|
| **Вход** | `make-rules.md`, `tools-rules.md`, срез |
| **Кто** | исполнители (агенты инструментов) под оркестрацией архитектора узла; для неатомарных задач — дочерние узлы (рекурсивно проходят все этапы) |
| **Что делает** | исполнители выполняют атомарные задачи (одна задача — один исполнитель с инструкцией инструмента); архитектор узла создаёт дочерние узлы, следит за зависимостями и **сам собирает продукт** и проверяет слаженность |
| **Выход** | `node-reports/realization-report.md` (дописывается по ходу: что сделано, где лежит, какие проверки листов пройдены) |
| **Критерий перехода** | все задачи плана закрыты или помечены; задача интеграции выполнена; продукт собран и запускается |
| **Дальше** | верификация |

Реализация не начинается, пока план не утверждён (шаг 2). Если по ходу выяснилось, что
задача не атомарна, — она выделяется в дочерний узел, а не «дожимается» подручными
средствами.

### 4. Верификация

| | |
|---|---|
| **Вход** | `product-rules.md` (правила + инварианты), контракт, `usage.md` инструментов, собранный продукт |
| **Кто** | тестировщик (свежая сессия; не делит контекст с исполнителями) |
| **Что делает** | пишет проверки двух классов: приёмочные (от спеки, чёрный ящик) и юнит/интеграционные (с учётом языка и сущностей); запускает; собирает воспроизводимые доказательства |
| **Выход** | `node-reports/verification-report.md` |
| **Критерий перехода** | все инварианты проверены или обоснованно помечены непроверяемыми; доказательства приложены |
| **Дальше** | приёмка (при успехе) или `rework` (при провале) |

Тестировщик вправе забраковать спеку: если требования противоречивы или непроверяемы,
он фиксирует `blocker` **до** написания тестов и эскалирует через архитектора узла.

### 5. Приёмка

| | |
|---|---|
| **Вход** | `verification-report.md`, `realization-report.md`, контракт и инварианты, `usage.md` |
| **Кто** | архитектор узла (сдаёт) и архитектор-родитель (принимает) |
| **Что делает** | родитель проверяет продукт против контракта (в том числе стыки с соседями), принимает или назначает правки с указанием, какой пункт контракта нарушен |
| **Выход** | `node-reports/acceptance-report.md` |
| **Критерий перехода** | решение зафиксировано со ссылкой на `contract_version` |
| **Дальше** | узел `done`; продукт становится инструментом (публикуется `usage.md`); родитель продолжает свой план |

Приёмка — не пересказ отчёта тестировщика. Родитель проверяет то, за что отвечает он
сам: соответствие контракту и работоспособность в составе родительского продукта.

## Переходы и отказы

| Ситуация | Переход | Ограничение |
|---|---|---|
| Провал верификации | `VERIFIED → REWORK`: архитектор узла → исполнители → верификация заново | ≤ `K` ретраев (по умолчанию 2), затем эскалация |
| Противоречие в product-rules | `→ SPECIFIED`: запрос родителю на изменение правил | изменение правил = новая `contract_version` |
| Неатомарная задача в реализации | задача → дочерний узел, остальные продолжаются | дочерний узел получает бюджет из резерва |
| Блокер (нет инструмента, нет доступа, спорный продукт) | `→ BLOCKED`: эскалация с вариантами и ценой | продуктовая развилка — только к пользователю |
| Нехватка бюджета | `→ BLOCKED`: эскалация с вариантами (добить / урезать объём / разбить иначе / стоп) | без вариантов эскалация не принимается |
| Изменение контракта родителя | зависимые узлы → `REWORK`, верификация недействительна | change propagation, см. `node.md` |

## Артефакты и владельцы

| Артефакт | Этап | Писатель | Обновление |
|---|---|---|---|
| `product-rules.md` | спецификация | родитель (уточняет архитектор узла в рамках среза) | при смене контракта — новая версия |
| `tools-rules.md` | спецификация, уточняется в реализации | архитектор узла | дополняется заметками |
| `make-rules.md` | планирование | архитектор узла (с учётом критика) | ревизии при пере-планировании |
| `specification-report.md` | спецификация | родитель | один раз |
| `planning-report.md` | планирование | архитектор узла | ревизии |
| `realization-report.md` | реализация | архитектор узла (исполнители передают результаты) | **дописывается** (append-only) |
| `verification-report.md` | верификация | тестировщик | ревизии по числу прогонов |
| `acceptance-report.md` | приёмка | архитектор узла + родитель | один раз на версию контракта |
| `usage.md` (в корне узла) | публикация | архитектор узла | при изменении контракта |

## Контекст ролей (что читает каждая роль)

Сборка контекста — часть работы харнесса: агент получает только свой срез.

| Роль | Читает | Не читает |
|---|---|---|
| Архитектор проекта | запрос пользователя, правила `.harness/`, корневой узел | внутренности дочерних узлов (только их отчёты о приёмке) |
| Архитектор узла | `specification-report`, свой `product-rules.md`/`tools-rules.md`, правила `.harness/` | историю родителя, реализацию соседей |
| Критик | `make-rules.md`, `product-rules.md` (инварианты), `tools-rules.md`, рубрику из `agents/critic.md` | реализацию, переписку исполнителей |
| Тестировщик | `product-rules.md` (правила + инварианты), контракт, `usage.md` инструментов, код продукта | рассказ исполнителей о том, как они это делали |
| Исполнитель | инструкцию инструмента (`.harness/tools-bank/...`), одну задачу, её рецепт и проверку | план целиком, историю узла |

## Правила, которые нельзя нарушать на переходах

- Не начинать реализацию без утверждённого плана и закрытых blocker'ов.
- Не переходить к верификации, пока архитектор узла сам не собрал продукт (задача интеграции).
- Не принимать узел без `verification-report.md` с доказательствами.
- Не публиковать инструмент без `usage.md`.
- Не перезаписывать историю отчётов и не менять `product-rules.md` без поднятия версии.
