# Day 17 — свой MCP-сервер вокруг API трекера задач

Задание: реализовать свой MCP-сервер вокруг любого API (регистрация инструмента, описание
входных параметров, возврат результата), подключить его к агенту, **вызвать инструмент из
приложения и использовать результат**.

Сделано вокруг личного трекера задач **SL Tracker** (`github.com/Vladislav-Zyuzko/sl-tracker`,
NestJS + PostgreSQL, прод на собственном VPS). Код сервера — `sl-tracker-mcp/` в корне
репозитория, он же собирается и выкатывается на тот же сервер рядом с трекером.

## 1. Что получилось

MCP-сервер `sl-tracker-mcp` (Node 22 + официальный `@modelcontextprotocol/sdk`), шесть
инструментов, два транспорта, ноль зависимостей от dsh:

| Инструмент | Вход | Что делает | Эндпоинт трекера |
|---|---|---|---|
| `create_task` | `title*`, `description?`, `queue?`, `status?`, `priority?` | создать задачу (статус — ключом `in_progress` или именем «В работе») | `POST /api/queues/{key}/issues` |
| `update_task_description` | `key*`, `description*` | заменить описание (пустая строка — очистить) | `PATCH /api/issues/{key}` |
| `add_comment` | `key*`, `body*` | добавить комментарий (Markdown) | `POST /api/issues/{key}/comments` |
| `get_task` | `key*`, `includeComments?` | прочитать задачу (+комментарии) | `GET /api/issues/{key}` |
| `set_task_status` | `key*`, `status*` | сменить статус (переход любой → любой, D-10) | `PATCH /api/issues/{key}` |
| `list_queues` | — | справочник: проекты → очереди → статусы (`ключ=«имя»`) | `GET /api/projects…`, `/api/queues/{key}/statuses` |

Шестой инструмент появился не «до кучи»: без справочника агент угадывал бы ключи очередей
(`DEV`) и имена статусов. Пять инструментов из задания — это операции, шестой — навигация.

Что ещё внутри:

- **транспорты**: `Streamable HTTP` (удалённо, эндпоинт `/mcp`) и `stdio` (локально:
  Claude Desktop, MCP Inspector) — один и тот же набор инструментов;
- **авторизация**: клиенты предъявляют `Authorization: Bearer <SL_MCP_TOKEN>`; сервер ходит
  в трекер с PAT участника (`SL_API_TOKEN`). Это два разных секрета с разными правами;
- **защита**: проверка `Origin` (пустой разрешён, посторонний → 403), обязательный bearer,
  `/healthz` голым `ok` без деталей;
- **предохранители**: `SL_MCP_READONLY=1` выключает все изменяющие инструменты,
  `SL_MCP_ALLOWED_QUEUES` сужает запись до перечисленных очередей — независимо от прав владельца;
- **отказ старта при пустом токене**: compose эти переменные не страхует, поэтому сервер
  падает с сообщением, где взять токен (требование харнесса sl-tracker из ревью).

Схема:

```
dsh-term (агент)  ──Bearer SL_MCP_TOKEN──▶  sl-tracker-mcp  ──Bearer PAT──▶  SL Tracker API
Claude Code       ──Streamable HTTP─────▶  /mcp, /healthz   ─────────────▶  /api/issues, …
Claude Desktop    ──stdio (локально)────▶  тот же код                      (права владельца токена)
```

## 2. Как это делалось: сначала RFC, потом код

Правки в трекере делал **не я** — в том репозитории свой Claude-харнесс. Поэтому работа
разделилась:

1. ресёрч трекера (ветка `develop`, OpenAPI на 198 КБ, схемы БД, деплой-обвязка);
2. **RFC + две спецификации** в корне `sl-tracker` (PR #1): PAT-эндпоинты, бот-идентичность,
   доступы, маршрут Caddy, порядок выката, критерии приёмки;
3. решение владельца: **бот не нужен** — токен принадлежит участнику проекта, скоуп равен
   его роли; PAT на 365 дней; экран токенов делаем сразу;
4. их харнесс реализовал (PAT как разновидность сессии с `purpose='pat'`, эндпоинты
   `/api/tokens`, экран `/me/tokens`, профиль compose `mcp`, site-блок Caddy), оставил
   разбор расхождений в PR;
5. я ответил на их вопросы и написал MCP-сервер.

Полезный побочный результат: их проверка нашла **дыру в моём же RFC** — kill-switch
(`destroyAllForUser`) для годовых токенов не работал, потому что TTL Redis-ключа (365 дней)
переживал TTL множества сессий пользователя (≈31 день). Исправлено на их стороне
(`min(SESSION_TTL_SECONDS, remaining)`) и закрыто тремя регрессионными тестами.

## 3. Вызов из приложения: агент и результат

Полный сценарий задания пройден дважды — тестом и живьём из dsh-term.

**Тест** (`tests/mcp-http.test.ts`): поднимается фальшивый SL Tracker (те же маршруты, что
в их сквозном тесте `mcp-smoke.e2e-spec.ts`), к нему подключается **настоящий MCP-клиент**,
и проходит цепочка «создать → описать → прокомментировать → сменить статус → прочитать».

**Живьём**: агент в dsh-term получил задачу и сам вызвал четыре инструмента:

```
mcp: включён sltracker · read-write, toolsets=all · запрашиваю список инструментов…
  mcp: sltracker · 6 tools · сырые схемы ≈ 1k → в промпте ≈ 470 tokens · sl-tracker-mcp · 54 мс
⛭ sltracker/list_queues
⛭ sltracker/create_task title="Проверить MCP-мост" description="создано агентом через MCP" queue="DEV"
⛭ sltracker/add_comment key="DEV-1" body="иду проверять"
⛭ sltracker/set_task_status key="DEV-1" status="in_progress"
```

Ответ агента:

```
Ключ задачи: DEV-1 — «Проверить MCP-мост»
Статус: in_progress («В работе»)
Последний комментарий: иду проверять
```

То есть результат не просто «получен» — он использован: агент прочитал справочник, создал
задачу по данным из него, дописал комментарий и перевёл статус, а потом отчитался данными
из ответов инструментов.

## 4. Проверки (что и чем подтверждено)

| Что | Чем проверено | Результат |
|---|---|---|
| Соединение, `tools/list`, шесть инструментов | `tests/mcp-http.test.ts` + `scripts/smoke-live.ts` | 6 инструментов, у каждого описание и JSON-схема входа |
| Полный сценарий задания | сквозной тест «клиент → сервер → трекер» | создать → описать → прокомментировать → сменить статус → прочитать |
| Вызов из агента | dsh-term с `--mcp sltracker` | четыре вызова, ответ по данным инструментов |
| Отказ старта при пустом токене | три процессных теста + запуск контейнера | код возврата 1, сообщение перечисляет переменные |
| Префикс `/api` не теряется | юнит-тест `apiUrl()` | `http://api:3000` + `/issues/DEV-1` → `…/api/issues/DEV-1` |
| 401 от трекера читается как «доступ кончился» | прогон против **боевого** трекера с фиктивным PAT | `[machine_access_expired] … Выпустите новый токен` |
| Без токена — 401, чужой `Origin` — 403, без `Origin` — можно | тесты HTTP-слоя | 401 с `WWW-Authenticate`; 403 на `https://evil.example` |
| `SL_MCP_READONLY=1` выключает запись | тест + прогон | изменяющие инструменты отвечают `[forbidden] … только чтение`, API не вызывается |
| `SL_MCP_ALLOWED_QUEUES` | тест | запись вне списка запрещена, чтение работает |
| Образ собирается и работает | `docker build` + запуск контейнера | `/healthz` → `ok`, healthcheck `wget` внутри образа |
| Регресс dsh-term | `tests/mcp.test.mjs`, `tests/profile.test.mjs` | 14 + 8 проверок зелёные |

Всего: **35 тестов** MCP-сервера + 22 регрессионных в dsh-term; `npm run typecheck` и
`npm run build` чисто.

## 5. Цена в промпте

Инструменты MCP уезжают в контекст модели на каждом запросе, поэтому их размер — часть решения.
Мой сервер специально компактный:

| Сервер | Инструментов | Сырые схемы | После регистрации в харнессе |
|---|---|---|---|
| `sl-tracker-mcp` | 6 | ≈1k токенов | **≈470 токенов** |
| GitHub MCP (day16) | 25 | ≈16.3k | ≈7.5k |

Разница — в дисциплине описаний: у моих инструментов короткие формулировки и только
необходимые поля. Плюс `SL_MCP_READONLY`/allowlist уменьшают не цену, а риск.

## 6. Деплой и подключение

Инструкция целиком — `sl-tracker-mcp/docs/DEPLOY.md`: пошагово, с проверкой после каждого
шага, ротацией токенов, откатом и таблицей типовых ошибок. Коротко порядок такой:

```
1. sl-tracker develop → deploy.sh        (PAT-эндпоинты и экран токенов)
2. UI: профиль → Доступ → Токены доступа → создать на 365 дней
3. git clone ai-challenge → /opt/sl-tracker-mcp
4. .env: COMPOSE_PROFILES=mcp, SL_MCP_DOMAIN, MCP_BUILD_CONTEXT,
         MCP_SL_API_TOKEN=<PAT>, MCP_CLIENT_TOKEN=<openssl rand -hex 32>,
         MCP_DEFAULT_QUEUE, MCP_READONLY
5. caddy validate → Valid configuration
6. docker compose build mcp && up -d && ps (healthy)
7. снаружи: /healthz → 200, POST /mcp без токена → 401, scripts/smoke-live.ts → 6 инструментов
8. у себя: $env:SL_MCP_URL / $env:SL_MCP_TOKEN → dsh-term --mcp sltracker
```

Подключение к dsh-term — двумя переменными окружения и флагом (пресет `sltracker`):

```powershell
setx SL_MCP_URL   "https://mcp.72-56-41-79.sslip.io:8443/mcp"
setx SL_MCP_TOKEN "<MCP_CLIENT_TOKEN>"
dsh-term --mcp sltracker         # на старте: «6 tools · в промпте ≈ 470 tokens»
# в сессии: /mcp  /mcp tools  /mcp refresh
```

Работает и с другими харнессами, потому что сервер стандартный: Claude Code — `.mcp.json`
с `type: http`, `url` и заголовком `Authorization`; Claude Desktop и Inspector — через
`stdio` (сервер запускается локально процессом).
