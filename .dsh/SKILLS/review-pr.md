# Скилл: review-pr (команда `/review-pr`)

Автоматическое ревью pull request: **локальный агент-ревьювер разбирает diff и оставляет
комментарии прямо в PR**. Завершающая фаза для `/publish-day` и `/publish-week`.

Исполняется командой `dsh-term /review-pr [<номер|ссылка|ветка>] [--model <имя>] [--force] [--dry-run]`
или вручную по шагам.

## Зачем локально, а не GitHub Action

Ассистент работает на **нашей машине**: у него есть локальный харнесс, базы RAG
(документация и код) и доступ к инструментам. GitHub-hosted раннер до них не дотянется,
поэтому триггер — не событие GitHub, а наша же публикация: `/publish-day` и `/publish-week`
после создания PR вызывают эту фазу. Внешне это выглядит как «PR открылся → появилось ревью».

## Предусловия

- Мы внутри репозитория `ai-challenge` (workspace dsh-term = корень репо).
- `gh` авторизован (`gh auth status`), PR существует и открыт.
- Собраны базы RAG: `project` (документация, день 31) и `project-code` (код, день 32):
  ```powershell
  cd doc-index
  python -m doc_index index --project-docs --vault .. --strategy structural
  python -m doc_index index --project-code --vault .. --strategy fixed
  ```
  Нет базы — ревью всё равно состоится (агент читает файлы инструментами), но без поиска
  по документации и коду.
- Ключ DeepSeek доступен (облачная модель): `DEEPSEEK_API_KEY` или хранилище dsh-term.

## Шаги

### 1. Найти PR
```powershell
# без аргумента — PR текущей ветки; с аргументом — номер, ссылка или имя ветки
gh pr list --head <ветка> --state open --json number,url
gh pr view <номер> --json number,url,title,body,headRefName,baseRefName,author,files,additions,deletions
```

### 2. Проверить, не ревьюили ли уже
В комментариях PR ищется маркер агента (`<!-- ai-reviewer:ai-challenge-reviewer -->`).
Найден — ревью пропускается (идемпотентность: повторный `/publish-day` не должен
плодить копии). Пересобрать ревью — `--force`.

### 3. Собрать данные
```powershell
gh pr diff <номер> > out/review/pr-<номер>/diff.patch
```
В ту же папку пишутся: список файлов, описание PR, промпт ревьювера и готовый текст ревью.
Промпт уезжает аргументом процесса, а у Windows предел командной строки ~32 000 символов,
поэтому в нём ограничены **все** части: diff — первые 4000 символов, описание PR — 6000,
список файлов — 300 строк. Полные данные лежат рядом файлами (`diff.patch`, `files.json`),
и агент читает их инструментами. Обрезка в комментарий не переносится: она касается только
промпта, а ревью пишется по полному diff.

### 4. Запустить ревьювера локально
Отдельная сессия с чистым контекстом (иначе агент защищает свои же решения):

```powershell
node dsh-term/dsh-term.mjs -p "$(Get-Content out/review/pr-<номер>/prompt.md -Raw)" `
  --rag project --rag project-code --model deepseek-v4-flash --workspace .
```

Промпт: роль и рубрика (`.dsh/.harness/agents/code-reviewer.md`), данные PR, diff, требование
вернуть две части — текст ревью и машиночитаемый блок `<!-- FINDINGS:START --> … <!-- FINDINGS:END -->`.
Замечаний в блоке не больше 12: предел держит код (`REVIEW_FINDINGS_LIMIT`), лишние отбрасываются
с приоритетом по severity, о числе отброшенных пишется в лог.

Модель ревьювера выбирается флагом `/review-pr … --model <имя>` или переменной окружения
`DSH_TERM_REVIEW_MODEL` (по умолчанию `deepseek-v4-flash`).

### 5. Опубликовать комментарии
Каждый комментарий начинается с тега агента — иначе его не отличить от комментариев
владельца репозитория (аккаунт GitHub один):

```markdown
<!-- ai-reviewer:ai-challenge-reviewer v1 -->
**🤖 AI-РЕВЬЮ · агент `ai-challenge-reviewer`** — сгенерировано автоматически, это не
комментарий автора PR.
```

- **сводный комментарий** — целиком текст ревью: `gh pr review <номер> --comment --body-file out/review/pr-<номер>/comment.md`;
- **построчные комментарии** — по одному на замечание из блока findings, если замечание
  указывает `файл` и `строка`, которая есть в diff. Вызов идёт через
  `gh api repos/{owner}/{repo}/pulls/<номер>/comments` **с `commit_id` (SHA головы PR) и
  `subject_type=line`**: без `commit_id` GitHub отвечает «line is not a permitted key».
  Не получилось (строка вне diff, файл без diff) — замечание остаётся в сводном комментарии,
  и это не ошибка.

Вердикт (`--approve` / `--request-changes`) не выставляется никогда: решение за человеком.

### 6. Отчитаться
- ссылка на PR и на комментарий;
- сколько замечаний: blocker / major / minor;
- сколько ушло построчно, сколько осталось в сводке;
- где лежат артефакты: `out/review/pr-<номер>/`.

## Правила (обязательные)

1. Комментарии пишет **агент под аккаунтом владельца** — тег обязателен в каждом комментарии.
2. Никаких правок кода, коммитов и мержей: только комментарии.
3. Ревью идемпотентно: повторный запуск без `--force` не публикует второе ревью.
4. Замечания только по diff; ссылки на строки — из diff или из прочитанного файла.
5. Ограничение объёма: до 12 замечаний, сначала blocker, потом major и minor.
6. Пайплайн публикации не падает из-за ревью: ошибка ревьювера — предупреждение в выводе,
   PR остаётся опубликованным.

## Ошибки — как действовать

| Симптом | Действие |
|---|---|
| PR не найден для текущей ветки | указать номер/ссылку явно: `/review-pr 42` |
| `gh: not logged in` | `gh auth login` (пользователь) |
| Ревью уже есть | это норма: `--force` для повторного |
| Пустой ответ агента или нет маркеров | смотреть `out/review/pr-<номер>/raw.log`; ревью не публикуется |
| Построчный комментарий отклонён GitHub | замечание остаётся в сводке; проверить, что строка входит в diff |
| Модель недоступна (нет ключа, лимит) | ревью пропускается с предупреждением, PR не страдает |
