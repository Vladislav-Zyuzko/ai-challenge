# RFC: машинный доступ к SL Tracker для MCP-сервера

- **Статус:** предложение (нужно решение владельца)
- **Дата:** 2026-09-24
- **Автор:** внешний оркестратор (сессия ai-challenge, задача MCP)
- **Адресат:** Claude-харнесс репозитория `sl-tracker` (оркестратор + сабагенты `sl-backend-engineer`, `sl-qa`, `sl-frontend-engineer`)
- **Основание:** пользователь решил — делаем **PAT-эндпоинты**, а машинной идентичности
  **не заводим**: токен принадлежит **участнику проекта**, поэтому объём прав совпадает
  с его ролью в проекте.

---

## 1. Зачем

Рядом с трекером ставится **`sl-tracker-mcp`** — отдельный MCP-сервер, который даёт агентам
(dsh-term, Claude Code, любой MCP-клиент) пять операций над задачами:

| Инструмент MCP | Что делает | Эндпоинт SL Tracker |
|---|---|---|
| `create_task` | создать задачу с заголовком и описанием | `POST /api/queues/{key}/issues` |
| `update_task_description` | изменить описание | `PATCH /api/issues/{key}` |
| `add_comment` | добавить комментарий | `POST /api/issues/{key}/comments` |
| `get_task` | прочитать задачу | `GET /api/issues/{key}` |
| `set_task_status` | сменить статус | `PATCH /api/issues/{key}` |

**Функциональности API уже хватает** — все пять операций и справочники (`/api/projects`,
`/api/projects/{slug}/queues`, `/api/queues/{key}/statuses`) существуют и покрыты OpenAPI.
Не хватает только одного: **способа предъявить API машинный доступ**. Сегодня сессию
создаёт лишь OAuth-колбэк Яндекса, то есть неинтерактивный клиент войти не может.

Этот RFC описывает минимальные аддитивные изменения в SL Tracker, которые закрывают ровно
эту дыру, и не меняет ничего в существующих сценариях веб-клиента.

## 2. Что уже есть (и почему мы это переиспользуем)

| Механизм | Факт из кода | Следствие для решения |
|---|---|---|
| Две стратегии сессии | `SessionGuard`/`extractToken`: cookie `sl_session` **или** `Authorization: Bearer <id>.<verifier>` (ADR-0002) | bearer уже работает: `PAT` не требует нового способа аутентификации |
| Формат токена | `<sessionId>.<верификатор 32 байта>`, в БД только HMAC-SHA256 с `SESSION_SECRET` (`session-token.ts`) | PAT хешируется тем же механизмом, дамп БД не даёт предъявить токен |
| TTL и продление | `SESSION_TTL_SECONDS = 30 дней`, `touch()` продлевает при использовании | для PAT нужен **явный** срок (см. §5.3) |
| Отзыв доступа | `AccessListService.remove` → `sessions.destroyAllForUser(userId)` | отзыв доступа **немедленно гасит и PAT** владельца — готовый kill-switch |
| Кэш | Redis: `sl:session:<id>`, `sl:sessions:by-user:<userId>` | PAT автоматически получает быстрый путь проверки и корректный отзыв |
| Список доступа | `access_entries` (email, `source`: config/manual/invitation, `isInstanceOwner`) | токен выпускается тому, кто уже в списке; заводить никого не нужно |
| Членство в проекте | `project_members` (role: admin/member/reader) | роль владельца токена и есть скоуп машинного доступа (§5.2) |
| Идентичности | `identities` (provider/external_id) нужны только для **входа** | машинный доступ не логинится, поэтому идентичностей не касается |
| Bootstrap из env | `AccessBootstrapService`: `ACCESS_LIST_BOOTSTRAP_EMAILS` применяется идемпотентно на старте | не нужен: новых пользователей не появляется |

## 3. Решение (обзор)

1. **PAT = долгоживущая bearer-сессия с назначением `pat`.** Не новая сущность
   аутентификации, а расширение уже существующей: добавляем в `sessions` три аддитивных
   поля (`label`, `purpose`, `token_prefix`). Так PAT бесплатно получает хеширование,
   Redis-кэш, скользящий `lastSeenAt` и отзыв вместе с доступом.
2. **API управления токенами** (self-service): `POST /api/tokens`, `GET /api/tokens`,
   `DELETE /api/tokens/{id}`. Токен всегда выпускается **самому пользователю** из его
   cookie-сессии — никаких «выдать токен за другого».
3. **Отдельного машинного пользователя нет.** Токен принадлежит участнику проекта: задачи и
   комментарии создаются **от его имени**, объём прав совпадает с его ролью (`admin`/`member`/
   `reader`), и никаких дополнительных ролей, записей доступа и членства заводить не нужно.
   Убрать машинный доступ = отозвать токен (или отозвать доступ — тогда погаснут все сессии).
4. **Маршрут для MCP** в Caddy (`{$SL_MCP_DOMAIN}` → контейнер `mcp:8080`), плюс сам
   контейнер — отдельный compose-проект на сети `sl-tracker_default`.
5. **MCP-сервер** (`sl-tracker-mcp`) ходит в API по внутренней сети
   (`http://api:3000`) с PAT участника. Он не знает про dsh, зависит только от HTTP API.

Детали реализации — в двух спецификациях:

- [`SPEC-PAT-API.md`](SPEC-PAT-API.md) — схема БД, миграция, эндпоинты, DTO, правила
  доступа, тесты, экран в вебе.
- [`SPEC-MCP-DEPLOY.md`](SPEC-MCP-DEPLOY.md) — что добавить в `infra/` (Caddy, compose, env)
  и как это проверяется.

## 4. Границы (что сознательно НЕ делаем)

- **Не** реализуем OAuth-авторизацию для MCP-сервера: PAT в заголовке достаточно для
  личного трекера; OAuth (RFC 9728 / protected resource metadata) — возможное развитие,
  но не в этой итерации.
- **Не** добавляем MCP-ресурсы и промпты: только инструменты (`tools`).
- **Не** трогаем существующие маршруты и их поведение: все изменения аддитивные.
- **Не** выдаём PAT по логину/паролю и не заводим локальный логин.
- **Не** создаём отдельного бот-пользователя: машинный доступ — это доступ участника,
  вынесенный в токен. Отсюда же следует, что «скоуп MCP» = роль этого участника в проекте,
  и расширять её специально не нужно.
- **Не** даём PAT управлять токенами (см. §5.4) — иначе утечка токена размножается.
- **Не** храним PAT в открытом виде нигде: ни в БД, ни в Redis, ни в логах.

## 5. Ключевые проектные решения

### 5.1 PAT — это сессия, а не новая таблица

Альтернатива — отдельная таблица `api_tokens` со своим путём проверки в guard. Отвергнута:
это второй механизм аутентификации в горячем пути запроса, дублирование кэша, хеширования
и семантики отзыва. Расширение `sessions` даёт всё то же одной миграцией и без изменений
в `SessionGuard`.

### 5.2 Токен принадлежит участнику проекта

Машинный доступ не должен требовать отдельной сущности: токен выпускается человеку, который
уже состоит в проекте. Следствия — все приятные:

- **скоуп совпадает с ролью**: `reader` токеном ничего не изменит, `member`/`admin` — сможет
  ровно то, что может в интерфейсе; никаких «специальных ролей для агента» и расхождений с UI;
- **не нужно заводить пользователя**: ни `users`, ни `access_entries`, ни `project_members`,
  ни `identities` — токен ссылается на существующего человека;
- **авторство честное**: задачи и комментарии подписаны человеком, который выдал токен
  (для агента это ожидаемо: он работает «за» владельца токена);
- **отзыв тривиален**: отозвал токен — машинный доступ кончился; отозвал доступ человеку —
  погасли и его сессии, и все его токены.

Обратная сторона, которую надо помнить: **токен = права человека**, включая необратимые
действия. Поэтому у MCP-сервера есть собственные предохранители (`SL_MCP_READONLY`,
allowlist очередей — см. `SPEC-MCP-DEPLOY.md`), а срок токена ограничен (см. §5.3).

### 5.3 У PAT явный срок, у сессии — скользящий

Сессия живёт 30 дней и продлевается при использовании — для браузера это правильно.
Для токена, который лежит в env контейнера, «тихое» продление означало бы бессрочный
доступ. Поэтому **решено пользователем: срок PAT — 365 дней по умолчанию** (выбирается из
пресетов 30 / 90 / 365 при создании), срок **не продлевается** автоматически, а бессрочных
токенов не бывает вовсе: вечный секрет в конфиге — это то, что потом забывают отозвать.
`lastSeenAt` продолжает обновляться для аудита, поэтому «мёртвый» токен видно в списке.

### 5.4 PAT не управляет токенами

`POST /api/tokens` и `DELETE /api/tokens/{id}` требуют **браузерной (cookie) сессии**
владельца. Запрос с PAT получает `403 pat_cannot_manage_tokens`. Так утечка токена не
даёт выпустить новые или отозвать чужие; управление остаётся в руках человека.

### 5.5 Права токена — права его владельца

MCP действует **от имени человека-владельца токена** и подчиняется тем же правилам: список
доступа, членство и роль в проекте, проверки на «автор/исполнитель — участник проекта».
Никаких обходов ACL: если человека убрать из проекта или отозвать ему доступ, MCP немедленно
теряет возможности — и заодно все его токены. Если роль `reader` — изменяющие инструменты
получат от API 403, и MCP-сервер обязан показать это внятной ошибкой, а не «тихо не сделать».

## 6. Требования к результату (acceptance criteria)

Проверяются на живом инстансе (`https://tracker.72-56-41-79.sslip.io:8443`).

1. **Токен выпускается владельцем.** Из-под cookie-сессии участника
   `POST /api/tokens {"name":"dsh-mcp","expiresInDays":365}` возвращает токен **один раз**,
   а `GET /api/tokens` показывает имя, префикс, срок и `lastSeenAt`, но не секрет.
2. **Токен работает как сессия владельца.** `curl -H "Authorization: Bearer <token>" …/api/me`
   → 200 и **тот же `userId`**, что у cookie-сессии, из которой токен выпущен.
3. **Скоуп совпадает с ролью.** Токен создаёт задачу в очереди проекта, где владелец состоит:
   автор задачи — владелец токена. В проекте, где владелец не состоит (или не состоит вообще),
   API отвечает 403/404 — MCP-сервер показывает это как ошибку инструмента.
4. **Отзыв немедленный.** `DELETE /api/tokens/{id}` → 204, следующий запрос с этим токеном →
   401 `session_expired`. Отзыв доступа владельцу (`DELETE /api/access-entries/{id}`) гасит
   **все** его сессии и токены.
5. **PAT не управляет токенами.** `POST /api/tokens` с PAT → 403 `pat_cannot_manage_tokens`.
6. **Веб-клиент не сломан.** Вход по Яндексу, cookie-сессии, инвайты, отзыв доступа —
   без изменений; существующие тесты API зелёные; миграция применяется на пустой БД и на
   БД с данными (аддитивные колонки с дефолтами).
7. **Секрет не течёт.** Токен отсутствует в БД (только HMAC), в Redis (только hash),
   в логах и в ответах `GET /api/tokens`.
8. **Экран «Токены доступа» работает** (в объёме этой итерации): список с префиксом,
   сроком и последним использованием; создание с выбором срока (по умолчанию 365 дней);
   токен показывается **один раз** и копируется; отзыв из списка; пустое состояние и ошибки
   (409 лимит, 403, сеть) — по `SPEC-PAT-API.md` §5.

## 7. План внедрения (для здешнего харнесса)

| Шаг | Кто | Результат |
|---|---|---|
| 1 | `sl-backend-engineer` | Миграция + схема + `SessionService` (label/purpose/prefix, срок, список, отзыв) |
| 2 | `sl-backend-engineer` | `tokens` модуль: контроллер, DTO, правила (self-only, cookie-only), rate limit, Swagger |
| 3 | `sl-qa` | Юнит/integration/e2e по §6; проверка, что PAT не управляет токенами, что отзыв гасит всё и что скоуп совпадает с ролью |
| 4 | `sl-frontend-engineer` + `sl-designer` | **В этой итерации:** экран «Токены доступа» в профиле (список / создание с выбором срока / одноразовый показ / отзыв) — `SPEC-PAT-API.md` §5 |
| 5 | оркестратор | `infra/`: site-блок Caddy + переменные (`SPEC-MCP-DEPLOY.md`), обновление `docs/api`, ADR |
| 6 | оркестратор | Деплой на сервер и проверка AC на живом инстансе |

Оценка: шаги 1–3 — примерно один рабочий цикл backend-агента с ревью; шаг 4 — отдельный
цикл фронта (экран входит в эту итерацию); шаги 5–6 — короткие. Заводить пользователя,
членство и роли не нужно вовсе — это и есть выигрыш решения «токен принадлежит участнику».

## 8. Риски

| Риск | Как снижаем |
|---|---|
| Токен утечёт из env контейнера | срок по умолчанию 365 дней, `GET /api/tokens` показывает `lastSeenAt`, отзыв одной командой, PAT не размножается |
| Токен = права человека, включая необратимое | предохранители MCP-сервера (`SL_MCP_READONLY`, allowlist очередей), срок токена, видимый `lastSeenAt`; при роли `reader` запись невозможна в принципе |
| Миграция заденет прод | только `ADD COLUMN ... DEFAULT ...` и новый enum-тип; проверка на копии БД; `down`-сценарий — откат кода при совместимой схеме |
| MCP-сервер станет «дыркой» в трекер | отдельный домен, обязательный bearer для MCP-клиентов, Origin-проверка, режим readonly, allowlist очередей — см. `SPEC-MCP-DEPLOY.md` |

## 9. Решения пользователя (зафиксировано)

1. **Машинной идентичности нет**: PAT принадлежит участнику проекта, скоуп равен его роли (§5.2).
2. **Срок PAT — 365 дней** по умолчанию (пресеты 30 / 90 / 365), без автопродления; бессрочных
   токенов не бывает (§5.3).
3. **Экран «Токены доступа» делается в этой итерации** — вместе с backend-частью; первый токен
   выпускается из интерфейса, а не запросом из консоли.
4. **PAT-эндпоинты** — способ доступа (вместо CLI-скрипта и вместо статического токена в env
   трекера).

Открытых вопросов к владельцу не осталось.
