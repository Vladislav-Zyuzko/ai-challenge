## Короткое вступление

Чтение JSON-файла в Node.js — это всегда **две независимые операции**, и ошибки у них разные. Первая — чтение с диска (`fs`), она падает с системными ошибками и свойством `err.code` (`ENOENT`, `EISDIR`, `EACCES`). Вторая — разбор текста (`JSON.parse`), она бросает `SyntaxError` без `code`, зато с указанием позиции. Если смешать эти два шага в одном `try`, вы потеряете информацию о том, что именно сломалось: файла нет или файл есть, но битый. Поэтому в примерах ниже они разведены на два блока `try/catch`.

Ниже — разбор по пунктам, полный рабочий пример (я проверял его на Node v24.17.0 под Windows) и список подводных камней, включая специфичную для Windows проблему с BOM.

## Разбор по пунктам

**1. Синхронный вариант уместен только на старте приложения.** `fs.readFileSync(path, 'utf8')` проще читается и не требует `await`, но блокирует event loop на всё время чтения. Для конфига, который читается один раз при запуске CLI-утилиты, это нормально; в HTTP-сервере, который обслуживает запросы, синхронное чтение большого файла затормозит всех клиентов. Альтернатива, которую я отбросил, — читать синхронно «потому что короче»: на сервере это скрытая деградация под нагрузкой.

**2. Асинхронный вариант — `await fs.promises.readFile(...)`.** В современном коде это основной путь: `const raw = await fs.promises.readFile(file, 'utf8')` не блокирует цикл событий, и ошибки приходят в тот же `try/catch`. Можно использовать и колбэк-форму `fs.readFile(file, 'utf8', cb)`, но тогда обработка ошибок расползается по вложенным функциям; я её не рекомендую, кроме случаев, когда вы пишете код для очень старой кодовой базы.

**3. Различайте ошибки по `err.code`, а не по тексту сообщения.** Проверено на Windows: чтение несуществующего файла даёт `code=ENOENT`, `syscall=open`; чтение каталога вместо файла — `code=EISDIR`, `syscall=read`; нет прав — `EACCES`/`EPERM`. Сравнение `err.message.includes('no such file')` сломается при смене локали или версии Node, а `err.code` — стабильный контракт. Отброшенная альтернатива — проверять существование через `fs.existsSync` перед чтением: это гонка (файл может исчезнуть между проверкой и чтением), и правильнее ловить `ENOENT` по факту.

**4. `JSON.parse` бросает `SyntaxError` без `code`, но с координатами.** В Node 20+ сообщение содержит и смещение, и строку с колонкой. В моём тесте на файле `{ "name": "broken", }` (висячая запятая — в JSON она запрещена, в отличие от JS-объектов) получилось: `Expected double-quoted property name in JSON at position 20 (line 1 column 21)`. Полезно пробрасывать это сообщение наверх как есть — оно сразу говорит, куда смотреть.

**5. Пустой файл — это тоже ошибка разбора, а не «пустой объект».** Для файла нулевой длины `JSON.parse('')` даёт `SyntaxError: Unexpected end of JSON input`. Если пустой конфиг для вас допустим, обрабатывайте это явно (`if (raw.trim() === '') return {}`), иначе получите падение на ровном месте.

**6. Главная ловушка Windows — BOM в начале файла.** Я специально воспроизвёл её: `Set-Content -Encoding utf8` в Windows PowerShell 5.1 записывает UTF-8 **с BOM**, и `JSON.parse` на таком файле падает с `Unexpected token '\uFEFF'`. Причина в том, что `fs.readFileSync(file, 'utf8')` декодирует байты, но BOM не удаляет. Лечится одной строкой `raw.charCodeAt(0) === 0xfeff ? raw.slice(1) : raw`; именно так в примере ниже. Это стоит запомнить: файлы, отредактированные в «Блокноте» или сгенерированные старым PowerShell, легко приходят с BOM.

**7. `require('./config.json')` — плохой выбор для конфигов.** Он работает и даже возвращает объект (в тесте — `demo`), но результат попадает в кэш модулей: повторный `require` вернёт старые данные, даже если файл изменился, а для «горячей» перезагрузки нужен `delete require.cache[require.resolve(...)]`. Плюс на битом JSON ошибка приходит обёрнутой и без вашей обработки. Отброшенные альтернативы: `require` для конфига, который меняется в рантайме, и `import ... with { type: 'json' }` для того же — статический импорт тоже кэшируется на весь процесс.

**8. `import ... with { type: 'json' }` хорош для фиксированных данных.** Это нативный способ (Node 22+, в Node 24 синтаксис `assert { type: 'json' }` уже не поддерживается — в моём тесте он упал с сообщением, что нужен import attribute типа json). Важная деталь для Windows: при динамическом импорте путь вида `C:\...` не принимается, нужен URL — используйте `pathToFileURL(file).href`, что я и проверил: с `pathToFileURL` импорт вернул `demo`.

**9. `JSON.parse` не проверяет структуру — только синтаксис.** Файл `{"port": "3000"}` разберётся без ошибок, а потом сломается где-то в другом месте. Поэтому после парсинга полезна явная проверка полей, а на сложных конфигах — схема (Zod, Ajv). В примере ниже есть минимальная проверка типа.

**10. Не глотайте ошибки молча.** Конструкция `catch {}` с возвратом `{}` — самая частая причина «почему приложение работает не с той конфигурацией». Правильная развилка: «файла нет, это допустимо» → вернуть `null` или дефолт; «файл есть, но битый» → падать громко с понятным сообщением и `cause`, чтобы стек указывал на исходную ошибку.

## Пример кода

Файл `read-json.cjs` — переиспользуемая функция чтения с разделённой обработкой ошибок:

```js
// read-json.cjs — проверено на Node v24.17.0 (Windows)
const fs = require('node:fs');

class ConfigError extends Error {
  constructor(message, { cause } = {}) {
    super(message, { cause });      // опция cause доступна с Node 16.9
    this.name = 'ConfigError';
  }
}

// Убирает BOM (U+FEFF), который пишут PowerShell 5.1 и «Блокнот»
function stripBom(text) {
  return text.charCodeAt(0) === 0xfeff ? text.slice(1) : text;
}

async function readJson(file, { optional = false } = {}) {
  let raw;
  try {
    raw = await fs.promises.readFile(file, 'utf8');   // шаг 1: диск
  } catch (err) {
    if (err.code === 'ENOENT' && optional) return null;
    if (err.code === 'ENOENT') throw new ConfigError(`Файл не найден: ${file}`, { cause: err });
    if (err.code === 'EISDIR') throw new ConfigError(`Ожидался файл, а не каталог: ${file}`, { cause: err });
    if (err.code === 'EACCES' || err.code === 'EPERM') {
      throw new ConfigError(`Нет прав на чтение: ${file}`, { cause: err });
    }
    throw new ConfigError(`Не удалось прочитать ${file}: ${err.code ?? err.message}`, { cause: err });
  }

  try {
    return JSON.parse(stripBom(raw));                 // шаг 2: разбор текста
  } catch (err) {
    throw new ConfigError(`Некорректный JSON в ${file}: ${err.message}`, { cause: err });
  }
}

// Синхронный близнец — для запуска CLI, где блокировка не важна
function readJsonSync(file) {
  const raw = fs.readFileSync(file, 'utf8');
  return JSON.parse(stripBom(raw));
}

module.exports = { readJson, readJsonSync, ConfigError };
```

Использование с валидацией и аккуратным завершением:

```js
// main.cjs
const path = require('node:path');
const { readJson, ConfigError } = require('./read-json.cjs');

(async () => {
  try {
    const cfg = await readJson(path.join(__dirname, 'config.json'));
    if (!Number.isInteger(cfg.port)) {
      throw new ConfigError('Поле "port" должно быть целым числом');
    }
    console.log(`Слушаем порт ${cfg.port}`);
  } catch (err) {
    if (err instanceof ConfigError) {
      console.error(`Конфигурация не загружена: ${err.message}`);
      if (err.cause) console.error(`  причина: ${err.cause.code ?? err.cause.name}`);
      process.exitCode = 1;     // не process.exit(1): иначе часть вывода в stdout может не долететь
    } else {
      throw err;                // всё неожиданное пусть падает громко
    }
  }
})();
```

Что этот код реально выводит на проверенных данных: для корректного файла — `demo` и порт 3000; для отсутствующего — `Файл не найден: ...`; для каталога — `code=EISDIR`; для битого JSON — `Некорректный JSON в ...: Expected double-quoted property name in JSON at position 20 (line 1 column 21)`; для файла с BOM — успешный разбор (без `stripBom` было бы `Unexpected token '\uFEFF'`).

## Что учесть

- **`process.exit(1)` против `process.exitCode = 1`.** Первый завершает процесс немедленно и может обрезать ещё не сброшенный вывод в stdout при перенаправлении в файл. Второй даёт Node завершиться штатно. Исключение — если нужно гарантированно прервать зависшие операции.
- **`JSON.parse(Buffer)` работает.** Проверено: `JSON.parse(await readFile(file))` без `'utf8'` тоже возвращает объект, потому что Buffer приводится к строке. Но неявное преобразование скрывает, что вы работаете с текстом, и BOM всё равно останется — лучше указывать `'utf8'` явно.
- **Ошибку `cause` стоит логировать.** Она сохраняет исходный `SyntaxError` или системную ошибку, и в Node 16.9+ выводится в трейсбеке отдельным блоком `[cause]`, что сильно ускоряет диагностику.
- **Проверить самому можно следующее:** версию рантайма — `node -v`; наличие BOM — `fs.readFileSync(file,'utf8').charCodeAt(0) === 0xFEFF`; реальные коды ошибок — `try { fs.readFileSync(dir, 'utf8') } catch (e) { console.log(e.code, e.syscall) }`; кэширование `require` — дважды вызвать `require('./config.json')` после правки файла и увидеть старые данные.

## Итого

1. Читайте файл и парсите JSON **разными `try/catch`**: на диске ловите `err.code` (`ENOENT`, `EISDIR`, `EACCES`), при разборе — `SyntaxError` с позицией. Так сообщение об ошибке сразу указывает на настоящую причину.
2. Для сервера берите `await fs.promises.readFile(file, 'utf8')`, для стартового конфига CLI допустим `readFileSync`; `require` и `import ... with { type: 'json' }` кэшируются на весь процесс и не годятся для данных, которые меняются в рантайме.
3. Обязательно снимайте BOM (`charCodeAt(0) === 0xfeff`) — на Windows это самый частый источник загадочного `Unexpected token '\uFEFF'` при внешне валидном JSON, и не забывайте валидировать структуру после успешного `JSON.parse`.
