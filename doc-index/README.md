# doc-index — локальный индекс документов с эмбеддингами

День 21: пайплайн индексации — **чанкинг → эмбеддинги → индекс с метаданными → поиск**,
и сравнение двух стратегий чанкинга на размеченном наборе вопросов.
День 22: **RAG поверх этого индекса** — вопрос → поиск чанков → объединение с вопросом →
ответ агента, плюс сравнение с режимом «без RAG» на контрольном наборе.
День 23: **второй этап после поиска** — фильтр по порогу, реранкер bge-reranker-v2-m3
и query rewrite, плюс сравнение пайплайнов по качеству ответа и чистоте контекста.
День 24: **источники, цитаты и режим «не знаю»** — строгий контракт ответа
(`ОТВЕТ` + `ИСТОЧНИКИ` + `ЦИТАТЫ`), машинная проверка цитат на дословность
и обязательный отказ при слабом контексте.
День 25: **длинные сценарии чата** — проверка на 2 диалогах по 10–15 сообщений:
не теряется ли цель, остаются ли источники в каждом ответе, что реально
попадает в память задачи.

Корпус — хранилище Obsidian `effective-ai` (заметки про AI SDLC: карточки понятий,
конспекты кластера, ЗУН-матрицы). Хранилище открывается **только на чтение**: ничего
в него не пишется, все артефакты лежат в `out/`.

## Что сделано

| Шаг | Реализация |
|---|---|
| Сбор корпуса | `collect.py`: обход хранилища, frontmatter (теги, источник), чистка разметки Obsidian, нумерация строк сохраняется |
| Чанкинг | `chunk.py`: две стратегии — `fixed` (окно 1000 символов, перекрытие 150) и `structural` (иерархия заголовков + хлебные крошки) |
| Эмбеддинги | `embed.py`: локальная Ollama, модель `bge-m3` (1024 измерения, 8192 токена контекста), кэш по хешу текста |
| Индекс | `store.py`: SQLite (метаданные + текст + FTS5) **и** FAISS **и** JSON-выгрузка |
| Поиск | `search.py`: векторный (FAISS) + лексический (FTS5/BM25), слияние через RRF |
| Сравнение | `evaluate.py`: 23 вопроса с эталонами → `recall@1`, `recall@5`, `MRR` |
| RAG-ответ | `rag.py` + `agent.py`: вопрос → поиск чанков → промпт → ответ агента харнесса |
| Сравнение режимов | `compare.py`: контрольный набор, покрытие фактов и слепое судейство моделью |
| Фильтр и реранкинг | `rerank.py`: порог (абсолютный и маржа от top-1), cross-encoder `bge-reranker-v2-m3` через ONNX, эвристика по термам, MMR |
| Query rewrite | `rewrite.py`: multi-query через LLM + слияние RRF, раскрытие аббревиатур словарём |
| Настройка порога | `sweep.py`: перебор порогов на размеченном наборе, выбор по precision при recall@5 = 1.0 |
| Сравнение пайплайнов | `pipelines.py`: 6 пайплайнов (без RAG, baseline, порог, эвристика, cross-encoder, rewrite+фильтр) |
| MCP-сервер | `mcp_server.py`: поиск по базе как инструмент агента (stdio, MCP SDK) — база вместо промпта |
| Источники и цитаты | `citations.py`: разбор строгого ответа, проверка дословности цитат и реальности источников |
| Проверка дня 24 | `verify.py`: обязательные источники и цитаты, судья «цитаты подтверждают ответ», режим «не знаю» |
| Проверка дня 25 | `chat_scenarios.py`: разбор длинных диалогов — источники по ходам, удержание цели, память задачи |
| CLI | `cli.py`: `index`, `search`, `evaluate`, `stats`, `ask`, `control`, `sweep`, `compare`, `verify`, `brief`, `fetch-reranker` |

## Метаданные чанка

`chunk_id`, `source`, `file`, `title`, `section`, `breadcrumb`, `folder`, `tags`,
`links`, `doc_source`, `start_line`, `end_line`, `n_chars`, `n_tokens_est`, `merged`, `text`.

Две стратегии дают **одинаковую** схему — иначе сравнение было бы нечестным.
`start_line`/`end_line` настоящие, по ним чанк открывается в Obsidian в том же месте.

## Запуск

Зависимости: `pyyaml`, `numpy`, `faiss-cpu` (см. `requirements.txt`) и локальная Ollama
с моделью:

```powershell
ollama pull bge-m3          # 1.2 ГБ, один раз
```

Для реранкера (день 23) нужен ONNX-веса `bge-reranker-v2-m3` (567 МБ):

```powershell
python -m doc_index fetch-reranker   # качает в doc-index/models/, в git не попадает
```

Без этой модели всё работает, кроме пайплайнов `cross` и `full` — команда скажет об этом
и продолжит без реранкера.

```powershell
cd doc-index
python -m doc_index stats                                  # корпус и чанки, без модели
python -m doc_index index --strategy fixed,structural,structural_nobc
python -m doc_index search "чем агент отличается от модели" --strategy structural
python -m doc_index evaluate                                # сравнение стратегий
python -m doc_index ask "что такое агентный харнесс?" --mode both   # RAG и без RAG
python -m doc_index control                                 # контрольный набор целиком
python -m doc_index sweep                                   # настроить порог отсечения
python -m doc_index compare                                 # сравнить 6 пайплайнов
python -m doc_index verify                                  # источники, цитаты, режим «не знаю»
```

Для режимов `ask`, `control` и `compare` нужен **агент харнесса**: используется Python SDK
из установки `deepseek-harness` (`python/sdk/src`) и учётные данные из `~/.dsh-term`. Пути
переопределяются переменными `DSH_SDK_SRC` и `DSH_HOME`; рантайм поднимается один раз на
весь прогон, каждый вопрос идёт отдельной сессией, поэтому вопросы не влияют друг на друга.
По умолчанию же для замеров берётся чистый вызов модели (`--backend api`): у агента есть
инструменты, и он может выйти за пределы переданного контекста.

Параметры чанкинга переопределяются флагами (`--fixed-size`, `--fixed-overlap`,
`--structural-max`, `--structural-min`), корпус — `--vault`, артефакты — `--out`.

## MCP-сервер: база знаний как инструмент агента

Кроме режима «фрагменты в промпт» (`ask`, `control`) индекс умеет отдаваться агенту
**инструментом**: `mcp_server.py` поднимает MCP-сервер по stdio, а агент вызывает
`rag_search`, когда считает нужным. Так база не занимает контекст постоянно, но остаётся
доступной; ответ приходит с источником и строками.

```powershell
# автономно (для отладки): инструменты печатаются по протоколу MCP
python -m doc_index.mcp_server --base effective-ai=C:\path\to\doc-index

# в сессии dsh-term — через реестр .dsh/rag.json
dsh-term --rag effective-ai
```

Инструменты: `rag_search(query, k, base)` и `rag_bases()`. Поиск идёт путём дней 21–23, плюс две
надстройки, нужные именно инструменту:

- **раскрытие аббревиатур** (`ЗУН` → «знания умения навыки») вторым запросом со слиянием через
  RRF — без него вопрос «что такое ЗУН-матрица» давал косинус 0.469 и база считалась неотвечающей;
- **пол применимости** (`--min-dense`, по умолчанию 0.5): относительная маржа фильтрует только
  среди результатов, поэтому на вопрос вне корпуса инструмент отвечает «ответа нет», а не отдаёт
  лучшее из плохого. Замеры: у «своих» вопросов top-1 после раскрытия начинается с 0.55,
  у чужих не поднимается выше 0.45.

Параметры: `--margin`, `--min-dense`, `--min-keep`, `--candidates`, `--strategy`, `--no-expand`.

## Источники, цитаты и режим «не знаю» (день 24)

Команда `verify` прогоняет контрольный набор в **строгом режиме** и проверяет ровно то,
что требует задание:

```powershell
python -m doc_index verify                       # 12 отвечаемых + 3 вне корпуса
python -m doc_index verify --min-dense 0.6       # строже порог отказа
python -m doc_index verify --no-judge            # без судьи, только машинные проверки
```

Для одного вопроса есть `brief` — та же строгая форма, но без набора и статистики:

```powershell
python -m doc_index brief "что такое MCP и какую задачу решает?"
python -m doc_index brief "во что верит база" --no-filter     # без порогов, для сравнения
python -m doc_index brief "что такое гейт" --judge            # добавить оценку судьи
```

Команда печатает `ОТВЕТ` + `ИСТОЧНИКИ` + `ЦИТАТЫ` и строку машинной проверки
(`источники 2/2 реальны · цитаты 2/2 дословны · выдуманных 0`), а ниже порога — шаблон отказа.
Ею пользуется команда `/rag-brief` в dsh-term: она идёт мимо агента, поэтому форма ответа
гарантирована кодом, а не инструкцией.

Ответ запрашивается контрактом:

```
ОТВЕТ: <2–5 предложений>
ИСТОЧНИКИ:
- [1] <chunk_id> · <заметка> · <раздел>
ЦИТАТЫ:
- [1] «<дословный фрагмент из источника 1>»
```

Чтобы модель могла назвать `chunk_id`, в строгом режиме шапка фрагмента в контексте
подписана им и строками (`[1] chunk_id=… · источник · раздел (строки 7–10)`). Промпты
дней 22–23 при этом не меняются: строгий контракт включается только флагом.

Что считается проверкой:

| Требование | Как проверяется |
|---|---|
| Источники есть в каждом ответе | блок `ИСТОЧНИКИ` не пуст |
| Источники не выдуманы | каждый названный источник (chunk_id или имя заметки) есть среди найденных фрагментов |
| Цитаты есть в каждом ответе | блок `ЦИТАТЫ` не пуст |
| Цитаты дословны | нормализованный текст цитаты найден в тексте **того фрагмента**, на который ссылается её номер; многоточие внутри цитаты допускается |
| Смысл совпадает с цитатами | отдельный вопрос судье: «подтверждают ли цитаты утверждения ответа?» 0–2 |
| Режим «не знаю» | на вопросы вне корпуса (`answerable: false`) ответ обязан быть отказом с просьбой уточнить; ответы с запрещёнными формулировками ловятся отдельно |

**Порог отказа** (`--min-dense`, по умолчанию 0.5) работает в коде, а не в промпте: если
лучший косинус ниже порога, модель не вызывается вовсе — возвращается шаблон «Не знаю +
уточните». Правило в промпте остаётся страховкой на границе.

## Длинные сценарии чата (день 25)

Задание требует проверить на 2 диалогах по 10–15 сообщений, что ассистент не теряет цель
и продолжает выдавать ответы с источниками. Сценарии прогоняются как **живые сессии
dsh-term** (стратегия `facts` + `--rag`), расшифровка сохраняется, а проверка считается здесь:

```powershell
# прогон сценариев (dsh-term, живая сессия, ~5 минут на сценарий)
node dsh-term/tools/run-scenario.mjs --list
node dsh-term/tools/run-scenario.mjs s1-mcp
node dsh-term/tools/run-scenario.mjs s2-quality

# проверка расшифровок и отчёт
python -m doc_index.chat_scenarios out/chat-s1-mcp.json out/chat-s2-quality.json
python -m doc_index.chat_scenarios out/chat-*.json --no-judge    # только машинные проверки
```

Что считается по каждому ходу:

| Мера | Как проверяется |
|---|---|
| Источники из базы | упоминание заметки, которая **есть в индексе**; ссылки на файлы проекта (`README.md`, `*.py`) считаются отдельно — у агента есть файловые инструменты |
| Ссылка на строки | «строки N–M» в ответе |
| Цитаты дословны | нормализованный текст цитаты найден в корпусе |
| Цель диалога | судья по цели сценария и последним ходам (0–2): ноль — ответ ушёл в сторону |
| Ограничения | формулировки, которых не должно быть после того, как пользователь их запретил |
| Память задачи | что записано в файле состояния сессии dsh-term (`context/<id>.json`) |
| Отказ вне корпуса | «не знаю» + просьба уточнить вместо выдуманного ответа |

Отчёт: `out/chat-scenarios.md` + `out/chat-scenarios.json`.

## Тесты

```powershell
python -m unittest discover -s tests
```

162 теста: чистка разметки и нумерация строк, границы чанков, хлебные крошки, склейка
коротких секций, заголовки внутри код-блоков, FTS-запрос, слияние RRF, выдача
с метаданными, сборка RAG-промпта (различие режимов только в блоке контекста),
проверка покрытия фактов и разбор оценки судьи, пороги отсечения (абсолютный,
маржа, запрет пустого контекста), эвристика по термам, MMR, диспетчер реранкинга,
разбор вариантов rewrite и слияние multi-query, сквозные пайплайны на заглушках,
инструменты MCP-сервера, разбор строгого ответа и проверка цитат (пересказ вместо
цитаты, цитата не из того фрагмента, выдуманный источник, цитата с многоточием),
шаблон отказа и поиск запрещённых формулировок.
Сеть, Ollama, модель и агент для тестов не нужны: эмбеддер, поиск, LLM и
cross-encoder подменены детерминированными заглушками.

## Артефакты в `out/`

- `index.db` — SQLite: чанки, FTS5, эмбеддинги, кэш;
- `index_<стратегия>.faiss` — векторный индекс;
- `chunks_<стратегия>.json` — выгрузка чанков с метаданными;
- `metrics.md`, `metrics.json` — сравнение стратегий чанкинга (день 21);
- `rag-comparison.md`, `rag-answers.json` — сравнение режимов с RAG и без (день 22);
- `sweep.md`, `sweep.json` — настройка порога отсечения (день 23);
- `rerank-comparison.md`, `rerank-answers.json` — сравнение пайплайнов (день 23);
- `rerank_scores.json` — кэш оценок cross-encoder (считать заново не нужно).
