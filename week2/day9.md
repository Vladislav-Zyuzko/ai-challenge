# День 9. Управление контекстом: сжатие истории

**Результат:** агент `dsh-term` умеет работать со сжатием истории — последние N токенов диалога
передаются «как есть», остальное заменяется summary, summary хранится отдельно и подставляется
в запрос вместо полной истории. Сравнение трёх режимов на одном сценарии: контекст сокращается
на 78%, чистый расход токенов — на 24%, качество ответов не падает.

## 1. Что реализовано

| Требование задания | Реализация | Как проверить |
|---|---|---|
| «последние N сообщений как есть» | `--compress-keep <токены>` — хвост диалога не сжимается (выравнивается по парам вызов-результат инструментов). Считаем **в токенах, а не в сообщениях**: в агентной сессии «сообщение» — это шаг с инструментами, размеры различаются на порядки, поэтому токены — объективная метрика | `dsh-term --compress-keep 50000`, строка запуска `compress: on (compact at 100k tokens, keep last 50k tokens)`, `/context` |
| «остальное заменяем summary» | авто-компакция: старые сообщения заменяются сводкой | `· context compacted: shadowed 4.2k → summary 843 (net ≈ −3.4k, call 14.4k)`, где `net` — снятое с окна, `call` — стоимость вызова суммаризатора |
| «каждые ~10 сообщений» | триггер по «давлению» на окно: `--compress <ratio>`, то есть по фактическому объёму контекста (порог `ratio × окно`) | `--compress 0.02` → `compact at 20k tokens` |
| «summary хранить отдельно и подставлять вместо полной истории» | summary пишется отдельным событием `compaction/summary` и подставляется как сообщение вместо сжатого диапазона; текст доступен целиком | `/context` → блок `last summary` |
| «агент, который экономит токены» | режим включён по умолчанию; экономия подтверждена замерами | таблица в разделе 3 |

Дополнительно (управление и наблюдаемость в CLI):

- `--compress on | off | <ratio 0..1>` — режим компрессии (env `DSH_TERM_COMPRESS`);
- `--compress-keep <токены>` — «последние сообщения как есть» в токенах (по умолчанию 50000 —
  примерно половина порога и ≈5% окна 1M: хвост «как есть» это единственная часть истории,
  которую модель видит дословно, поэтому его выгодно держать крупным);
- настройки передаются рантайму патч-оверлеем `dsh --patch`, который `dsh-term` генерирует на лету:
  установленный харнесс не правится;
- `--compress off` выключает не плагин, а автоматическую компакцию (`auto: false`): сервис
  компакции нужен соседнему плагину ручной команды, полное отключение ломает загрузку дерева;
- `/context` — режим и пороги, заполнение окна, расход, последний summary;
- в сводке хода — стоимость самой компрессии:
  `compression: 4 summarize calls, 68.2k tokens` (иначе экономия считалась бы нечестно);
- ошибки не глотаются: `✖ compaction failed: summary is not smaller than the shadowed content`.

Проверка токенной политики (живой прогон `dsh-term --compress 0.01 --compress-keep 2000`):

```
compress: on (compact at 10k tokens, keep last 2k tokens)
  note: compact threshold 10k is close to the fixed prefix (8k, system prompt + tools) — in agentic turns compaction will fire at once; use --compress 0.05 for a sane default
  compression: on (compact at 10k tokens, keep last 2k tokens)
  fixed prefix: ≈ 8k tokens (system prompt + tools) — порог должен быть заметно выше
```

Сгенерированный для рантайма патч (то, что реально применяется к профилю):

```yaml
- id: compaction-basic
  config:
    auto: true
    thresholdRatio: 0.01
    retainTokens: 2000
    maxTokens: 4096
```

## 2. Методика сравнения

Один и тот же сценарий (`week2/context_management/turns.txt`, 8 ходов) прогоняется в отдельных
чистых home и новых сессиях:

- в начале диалога вводится «иголка» — код проекта `KX-42`;
- 5 ходов по 300 слов (океаны, горы, пустыни, леса, реки) — чтобы история росла;
- в конце два контрольных вопроса: код проекта; сколько тем и что было пятым.

Метрики берутся из вывода `dsh-term` и из логов сессий; качество — из ответов на контрольные
вопросы (сопоставление «вопрос → ответ» по логу).

| Режим | Команда |
|---|---|
| без сжатия | `--compress off` |
| сжатие, агрессивно | `--compress 0.009 --compress-keep 300` |
| сжатие, умеренно | `--compress 0.02 --compress-keep 3000` |

## 3. Результаты

| Метрика | без сжатия | сжатие (агрессивно) | сжатие (умеренно) |
|---|---|---|---|
| Суммарный вход агента (`tokens: in`) | 1.37M | 494.9k | 965.8k |
| из них кэш | 1.35M | 425.0k | 920.2k |
| Суммарный выход (`out`) | 27.0k | 21.9k | 26.9k |
| Запросов к модели | 45 | 49 | 58 |
| **Финальный контекст** | **46.3k** | **10.1k (−78%)** | **15.1k (−67%)** |
| Компакций / отказов | 0 / 0 | 61 / 25 | 4 / 0 |
| Сжато (shadowed) | 0 | 96.7k | 23.5k |
| Стоимость суммаризации (вход+выход всех summary-вызовов) | 0 | 689.2k | 68.2k |
| **Итого токенов (агент + суммаризация)** | **1.40M** | **1.21M (−13.7%)** | **1.06M (−24.1%)** |

### Качество ответов

| Проверка | без сжатия | со сжатием (агрессивно) |
|---|---|---|
| Код проекта (`KX-42`) назван | да | да |
| Число тем (пять) | да | да |
| Пятая тема (реки) | да | да |
| **Итог** | **3/3** | **3/3** |

Ответы на контрольные вопросы в режиме со сжатием:

- «KX-42»
- «Пять тем — океаны, горы, пустыни, леса и реки, и пятыми по счёту были реки.»

То есть сжатие не потеряло ни «иголку» из первого хода, ни структуру диалога.

## 4. Выводы

1. **Механизм работает и экономит**: контекст сокращается в 3–4.5 раза, вход агента — на 64%,
   при этом ответы не деградируют (3/3 против 3/3 на контрольных вопросах).
2. **Политика важнее «силы» сжатия.** Агрессивные настройки дают самый компактный контекст,
   но 25 из 86 попыток отклонены (`summary не меньше сжимаемого участка`), а потраченные на
   попытку токены не возвращаются — чистая экономия 13.7%. Умеренные настройки: 4 компакции,
   ни одного отказа, чистая экономия 24.1%.
3. **Размер summary почти постоянный — ≈1–1.2k токенов** (структура из 8 секций + рамка заданы
   инструкцией харнесса), поэтому выигрыш зависит только от размера сжимаемого участка. Замер
   на живом прогоне: участки 1k / 2.4k / 4.2k → summary 1.1k / 1.2k / 1k, то есть **net**
   (снятое с окна) −112 / −1.2k / −3.2k, а цена вызова при этом 10–14.6k. Отсюда рабочее
   правило: участок должен быть на порядок больше summary, иначе компакция — чистые потери
   (CLI помечает такие строки `wasteful` и предупреждает о политике на старте). Порог вдобавок
   должен быть выше системного промпта (~8k токенов): при слишком низком пороге компакция
   срабатывает там, где сжимать нечего.
4. **`retainTokens` — это и есть «последние N сообщений»**: если хвост сопоставим с историей,
   сжимаемый участок получается крошечным и харнесс отказывается от компакции. Дефолт CLI
   поднят до 50k (было 6k — 0.6% окна, то есть сжимать приходилось почти всю историю; ориентир
   самого харнесса — `retainRatio 0.16`, то есть 160k при окне 1M). Дополнительно харнесс
   требует строгого `retainTokens < thresholdTokens`: при нарушении политика отбрасывается
   (`TargetPressureConfigError`), компакция молча не работает — CLI предупреждает об этом
   на старте и в `/context`.
5. Компрессия «спит», пока контекст ниже порога: при окне 1M и дефолтном `thresholdRatio 0.1`
   это ~100k токенов — в коротких сессиях выигрыша нет вовсе, поэтому для эксперимента
   порог понижался.

## 5. Ограничения и отклонения от буквы задания

- **Политика измеряется в токенах, а не в сообщениях** — сознательное решение: сообщение в
  агентной сессии это шаг с вызовами инструментов, и его размер варьируется от ~20 токенов
  (короткая реплика) до тысяч (результат чтения файла), поэтому счётчик сообщений требует
  средней оценки и вводит в заблуждение. Токены — фактическая, объективная величина: порог
  (`--compress`) и хвост (`--compress-keep`) задаются и измеряются в них.
- **Сравнение изолирует только авто-компакцию**: прунер длинных результатов инструментов
  включён в обоих режимах (в сценарии инструменты не использовались).
- **Оценка качества детерминированная** (три контрольные проверки по логу), без LLM-судьи;
  для более строгого сравнения можно добавить судью с фиксированной рубрикой.
- Стоимость посчитана в токенах, без перевода в деньги (кэш-токены тарифицируются дешевле,
  поэтому денежная оценка будет ниже «сырых» цифр).

## 6. Воспроизведение

```powershell
cd week2\context_management
Invoke-Expression (Get-Content .\run_ab.ps1 -Raw)   # прогон «без сжатия» и «со сжатием» → runs/*.txt
node .\analyze.mjs                                  # разбор метрик и качества → result.md

# умеренная политика отдельно
dsh-term --compress 0.02 --compress-keep 3000       # ввод из turns.txt
```

Файлы: `week2/context_management/{input.md, turns.txt, run_ab.ps1, analyze.mjs, result.md, summary.md}`,
сырые прогоны — `runs/{baseline,compress,compress-mod}.txt`.
Реализация — `dsh-term/dsh-term.mjs` (флаги `--compress`, `--compress-keep`, события компакции,
команда `/context`), документация — `dsh-term/README.md`.
